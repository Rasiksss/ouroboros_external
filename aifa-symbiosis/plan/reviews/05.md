# Ревью · шаг 05 · Опорная запись: инструменты

Ревьюер: Claude Code, Opus 5.5 (Medium), чистый контекст · 16.10.2026

**Вердикт: блокеры.** Инструмент в целом сделан хорошо: правила с причинами, метки вместо стирания,
окна независимых событий, честные «разрешённые различия». Две записи `_selftest` я прошёл руками,
и на них нормализатор снимает только то, чего экран не показывает. Но на синтетике я воспроизвёл два
случая, где нормализатор **прячет различие, которое увидит пользователь**:
- **Б1.** Статус шага плана: отметки `index: -1` («последний шаг» на экране) и `index: N` одного и
  того же шага сортируются как независимые.
- **Б2.** Текст карточки результата: `source_ref` выводится в строке «Источники:» и бывает
  смысловым (`formula_id`, `concept`), а нормализатор маскирует его как идентификатор.

Кроме того, записывающий клиент не распознаёт конец хода, который завершился сбоем или отменой:
журнал кончается `error` без `done` (В1).

## 2. Вертикальное ревью: ход на стенде → запись → нормализация → сравнение

### 2.1. Записи `_selftest` вручную

Поток обеих записей: `session_id`, 2× `thinking`, 3–4× `text_delta`, `text_segment_end`, `usage`,
`completed`. После нормализации — 4 события.

| Снято / изменено | Читает ли экран | Вывод |
|---|---|---|
| `schema_version`, `event_id`, `run_id`, `sequence`, `occurred_at` | нет: `unwrapRunEvents` отбрасывает конверт | верно |
| `thinking` ×2 | только подпись состояния (`applyChatEvent` → `thinking`) | верно, ADR-0015 |
| `text_segment_end` | нет: ветка возвращает `msg` без изменений | верно |
| `text_delta` 4 → 1 | склеивает `content + ev.text` | верно для этих записей (вызовов инструментов нет, эвристика «хвоста» ниже не срабатывает) |
| `usage`: все числа → `<n>` | `model`, токены, `cost_usd`, `turns` в `msg.usage`; `project_total` в `usage_total` | токены и стоимость — по F5. Счётчики (`turns`, `user_turns`) маскируются сверх причины правила (З2) |
| `session_id`, `usage.turn.project_id` → метки | `session_id` только сохраняется для следующего хода | верно |
| `completed` → `done` | закрывает графы | оставлено, верно |

### 2.2. Правила, которых в `_selftest` нет: сверка с редьюсером экрана

- **`fold_tool_output`** зеркалит экран: закрывается последний открытый такт с тем же именем, из
  результата экран читает только `ok` и `reason`. Порядок `tool_output` относительно текста экран
  не видит (меняется только подпись `thinking`). Верно.
- **`sort_independent`, `node_run`**: ключ нормализатора `(atom_name, atom_version)` грубее
  ключа экрана `atom|version|args_fingerprint` (`projects.ts`, `nodeToken`). Порядок внутри ключа
  сохраняется, поэтому скрыть различие правило не может; в худшем случае даст ложное. `plan_graph`
  разрывает окно. Верно.
- **`sort_independent`, `plan_step`** — **Б1**.
- **`label_identifiers`**: для случайных значений (`doc_id`, `file_id`, UUID, хэши) верно.
  Для `source_ref` — **Б2**.
- **`merge_text_delta`**: «нарезка не видна» верно не всегда. У экрана есть эвристика хвоста
  (`applyChatEvent`, `text_delta`): при пустом `content` дельта, начинающаяся со строчной
  кириллицы, доклеивается в последнюю заметку ленты. Результат зависит от нарезки первой дельты
  после инструмента. Между старым и новым AIFA это разрешено ADR-0015: новая служба шлёт одну
  дельту, и склеенная форма совпадает с тем, что покажет новый экран. Но «почему» в правиле
  неточное (З1).

### 2.3. Отказные пути клиента

Проверял по `run_orchestrator._drive`: при исключении и при отмене журнал получает
`{"type":"error"}`, затем `close()`. `done` при этом **не** пишется
(`run_orchestrator.py:454-460`, `close` в `:153`). Клиент считает концом хода только `completed`
и `session_lost` (`golden_record.py:159-163`). Поэтому ход, кончившийся сбоем, запишется как
6 переподключений без новых событий, а затем `ClientError` «поток обрывается» — **В1**.

## 5. Замечания по уровням

### Блокеры

**Б1. Перестановка отметок одного шага плана скрывается** — `aifa/tests/golden/golden_normalize.py:264`.
Ключ сортировки — `(name or "ход", str(index))`. На экране же (`projects.ts`, `plan_step`) один и
тот же шаг адресуется двумя способами:
- `index < 0` — это «последний шаг линии»;
- если линии с таким именем нет, отметка уходит в **первую** линию (`Math.max(0, findIndex)`).

Две отметки одного шага получают разные ключи и при сортировке меняются местами.
Воспроизведение (проверено): план из 4 шагов; запись A — `[step 3 running, step -1 done]`,
запись B — `[step -1 done, step 3 running]`. Нормализованные потоки равны, хотя в B шаг на экране
навсегда остаётся «в работе». Эмиттера `-1` в репозитории я не нашёл (станция переводит индекс
как есть, `station_turn.py:553`), но экран эту форму поддерживает, и правило обязано её учитывать.
Исправление: считать ключ так же, как экран: разрешить `index < 0` по известной длине линии
(из предыдущего `plan`), неизвестное имя — в первую линию. Либо не сортировать `plan_step` с
`index < 0` и без известной линии. Плюс тест «две отметки одного шага разными адресами — порядок
сохраняется».

**Б2. Смысловое `source_ref` маскируется как идентификатор** — `golden_normalize.py:109` (`ID_KEYS`).
Карточка результата показывает `source_ref` в «Источники: …» (`typed-result-view.tsx:22-30`).
Значение бывает смысловым: `formula_def.formula_id` (`calc_formula.py:266`), `args.concept`
(`graph_atoms.py:563`), `"<evidence_id>,<reference_id>"` (`assess_rule.py:122`). Метка по первому
появлению прячет замену одного значения другим, если рисунок совпадений тот же. Воспроизведение
(проверено): `typed_result` с `source_ref="formula.roe"` и с `"formula.roa"` нормализуются
одинаково. Пользователь увидит другую формулу в источниках, сравнение скажет «равны».
Исправление: убрать `source_ref` из `ID_KEYS`; UUID внутри строки уже заменяет `UUID_RE`. Плюс
тест «другой `source_ref` — различие». Заодно проверить остальные ключи по тому же признаку:
`nonce`, `metric_id`, `output_id`, `evidence_id` случайны (`new_id`), оставить можно.

### Важно

**В1. Ход, кончившийся сбоем или отменой, не записывается** — `golden_record.py:159-163`.
Журнал службы на этом пути кончается `error` без `done` (`run_orchestrator.py:454-460`).
Клиент не считает `legacy error` концом хода и после `MAX_RESUMES` падает с «поток обрывается».
Наборы приёмки (шаг 06) содержат и отказные ходы. Исправление: признать концом и `error`, если
поток после него закрылся (как экран: `error` → `terminal = true`). Плюс тест на журнал
`[…, error]` без `completed`. Попутно: `session_lost` в журнале всегда сопровождается `done`, а
клиент выходит, не дочитав его. Тогда запись короче того, что видит экран, и `done` закрывает
графы.

**В2. Нет теста на записанном фрагменте настоящего SSE** — `test_golden_client.py:150-163`.
Подставной сервер собирает поток вручную. Таблица связности промпта ревью требует фрагмент
настоящего потока `run_orchestrator`: реплей, хвост и `ping`. Живой прогон 16.10 дал такой поток,
но сырые байты не сохранены. Исправление: снять один короткий поток (`curl -N` на `_selftest`-ход)
в фикстуру и разбирать её через `iter_sse`.

**В3. При таймауте и исчерпании переподключений ход на стенде не отменяется** —
`golden_record.py:151-156`. Клиент бросает `ClientError`, а ход продолжает работать на dev. Повторный
запуск запишет новый ход, и на стенде будут идти два. Промпт требует «нагрузку на dev сверх
нескольких ходов — не делать». Исправление: при отказе вызвать
`POST /chat/runs/{id}/cancel` (ручка есть).

**В4. Файлы-результаты сравниваются только по имени** — `golden_compare.py:211-225`. Ограничение
известно и записано в P43 (б). Но размер и `sha256` пишутся и игнорируются даже для форматов без
времени внутри (csv, md, txt). Кроме того, словарь по имени склеивает два файла с одним именем.
Предложение: сравнивать `sha256` для детерминированных форматов, у xlsx/docx — хотя бы наличие и
число файлов. Остальное остаётся за шагами 18 и 20 (P43).

### Замечания

- **З1.** `golden_normalize.py:57-61`: в «почему» у `merge_text_delta` сказано «нарезка не видна».
  У экрана есть эвристика строчного хвоста, и она зависит от нарезки. Причина правила — ADR-0015,
  так и написать.
- **З2.** `golden_normalize.py:83-86`: `mask_usage_numbers` маскирует и счётчики (`turns`,
  `user_turns`, `turns_total`, `calls`). Причина правила говорит только о токенах и стоимости. Экран
  счётчики сейчас не показывает, но удвоение хода по `user_turns` было бы видно.
- **З3.** `golden_record.py:90-101`: `final_answer` не учитывает, что экран переводит прозу в
  заметку на `extract_start` (`use-chat-run.ts:573-581`). Поле `answer` может включать прозу, которую
  экран ответом не показывает.
- **З4.** `golden_compare.py:244-257`: различие по ADR-0026 разрешено и в обратную сторону (старая
  сторона отказала, новая приняла). ADR описывает только отказ на новой стороне.
- **З5.** `golden_client.py:59`: вложенная функция `need` (PRINCIPLES §В, 2.1).
- **З6.** Список стендов задан в двух местах: `golden_client.py:20` и `test_dev_config.py`
  (`GOLDEN_HOSTS`). F9 мог бы импортировать константу клиента или сверять их между собой.
- **З7.** `golden_client.py:166-174`: редирект переносит заголовок `Cookie` на любой хост.
  Стоит запретить редиректы (`HTTPRedirectHandler` без следования) или проверять `check_stand`
  на итоговом адресе.
- **З8.** `golden_client.py:176-179`: из `Set-Cookie` берётся только первый заголовок и
  перезаписывается любым следующим. Если служба выставит второй cookie, сессия потеряется.
- **З9.** `iter_sse` (`golden_client.py:189`) склеивает строки `data:` без `\n`. По спецификации
  SSE разделитель — перевод строки. Для JSON это безопасно, только пока служба пишет `data` одной
  строкой.

## 6. Что сделано хорошо

- Метки вместо стирания: подмена ссылки остаётся различием, есть тест.
- Новый тип конверта превращается в `envelope:<тип>`, а не пропадает (экран его тихо бросает,
  запись — нет).
- Разрешённые различия считаются и выводятся с номером ADR, а не стираются молча.
- Живой прогон нашёл и закрыл два настоящих дефекта (`usage.turn.project_id`, кодировка консоли).
