## Вертикальное ревью

Путь: `POST /chat/turns` (`api/main.py:1553`) → owner-фильтр документов (`_chat_turn_docs`, как
раньше) → `pinned_tool` пуст → `_start_ouroboros_turn` (`main.py:1520`) → `start_run(OuroTurn)` и
`remember(TurnRecord)` с `chat_id = project_id or session_id` → `OuroTurn._events`
(`chat_turn.py:43`): `session_id` → `TurnGateway.events` → WS ouroboros (шаг 08) → задача корня →
`skill_read distribution:aifa-planning` → `ext_13_r_aifa-engine_aifa_goal` → `EngineCall.__call__`
(`plugin.py:87`): тело `{"ctx", "args"}`, `run_id = ctx.transport["source_message_id"]`,
`Authorization`, `X-Trace-Id`, `X-Agent-Id` через `aef_tracing` → `POST /internal/ouro/v1/aifa_goal`
→ `token_refusal` → `ToolApi.handle` (`tool_api.py:57`): привязка, роль → `tool_call` в журнал хода
→ `GoalTool` → `StandardPath` → конвейер (`plan_graph`, `node_run`, `typed_result`) → `ouro_view.goal`
→ `tool_output(ok)` → текст модели без изменений → финал корня → `text_delta`, `text_segment_end`,
`done(status=succeeded)` → `subscribe_versioned` (`run_orchestrator.py:734`) → SSE `completed`.

Пройден сам на живом ouroboros: порядок событий, имя `financial_pipeline` на экране, таблица службы
в третьем запросе модели, описание `aifa-planning` целиком в каталоге — совпадают с заявленным.

По границам:
- **Фронтенд → служба.** Поля `QueryRequest` прежние; фронтенд шлёт `doc_ids` проекта на каждом ходе
  (`web/src/components/workspace/use-chat-run.ts:910-917`), поэтому то, что новые ходы не пишут
  сессию агента (`_chat_turn_docs` берёт её документы только при пустых `doc_ids`), потери документа
  на повторном ходе не даёт. `arch`, `web_search` на новом пути не читаются — ветки OpenClaw сняты
  (ожидаемо). Ветка `pinned_tool` — прежняя (О3, R36).
- **Служба → ouroboros (WS).** Без изменений шага 08; `trace_id` хода — новый uuid на ход.
- **ouroboros → плагин.** `ToolContext` — настоящий; стоп ядра доходит до инструмента
  (`ouroboros/agent/loop_tool_execution.py:308`), поэтому опрос `ctx.stop_requested()` не мёртвый.
  Идентичность — из `ctx.scope` (минтит транспорт), `args` уходят отдельным полем — инвариант 7 цел.
- **Плагин → `tool_api`.** §3.0 соблюдён буквально (ADR-0047 п. 4): один запрос, опрос остановки раз в
  секунду, отмена запроса в `finally`, сетевой сбой → `СБОЙ_СЛУЖБЫ: …; повтори вызов`. Отказы токена —
  теперь текст грамматики §3.0 (P65 З2 закрыт). Ответ возвращается без разбора при любом HTTP-статусе
  (тест на 401/404/500/503) — см. З3 про тела, которые пишет не `ouro_view`.
- **`tool_api` → журнал хода → экран.** `tool_call`/`tool_output` на каждый привязанный вызов;
  `УТОЧНИ` и `ЖДИ` — `ok=true`, `ОТКАЗ`/`СБОЙ_СЛУЖБЫ` — `ok=false` (§2.5). Экран закрывает такт по
  `tool_output` (`web/src/lib/projects.ts:2111`) — см. З2.
- **Финал → SSE.** `done.status=succeeded` после ответа ouroboros; ходы без ответа и `pinned_tool` —
  как были (тест на реплее журнала, P62).

Отказные пути:
- «Стоп» во время `aifa_goal`: ядро → `ctx.stop_requested()` → плагин отменяет запрос и отвечает
  `СБОЙ_СЛУЖБЫ: вызов остановлен вместе с ходом`; служба снимает задание по концу хода (C3.4, шаг 09).
  Обе половины проверены порознь (плагин — `test_plugin_transfer.py:125`, служба — тесты шага 09),
  через живой ouroboros — нет (В1).
- Служба недоступна / нет адреса или токена — `СБОЙ_СЛУЖБЫ`, навык велит повторить один раз и сказать
  пользователю, что расчёт недоступен. Проверено модульно.
- Служба молчит дольше 300 с — тайм-аут ядра и `httpx` совпадают (P69, замечание реализации).

### Замечания
- **З1.** `X-Agent-Id` на dev не уходит: `AGENT_SYSTEM_CONFIGURATION_AGENT_ID`/`AGENT_ID` нет ни в
  `ouroboros.env.example`, ни в compose. Инвариант 6 это разрешает, но F12 (б) проверен только с
  подставленным `current_agent_id` (`test_headers.py:140`); если идентификатор агента на dev нужен —
  обязательный набор ADR-0027 и снимок F9.
- **З2.** `tool_output` пишется только после возврата `_run` (`tool_api.py:71-73`); `_run` ловит
  `Exception`, но не `CancelledError`. Отмена обработчика (остановка процесса службы, отмена задачи
  uvicorn) оставит на экране такт `financial_pipeline` «running» без закрытия. `try/finally` вокруг
  `_run` закрыл бы его как `ok=false`.
- **З3.** Плагин отдаёт модели любое тело (`plugin.py:113`) — правильно по §3.0, но тела, которые
  пишет не `ouro_view`, вне грамматики C3.2: например, сбой зависимости `get_tool_api` до `handle` даёт
  `Internal Server Error` от Starlette с 500. Закрывается обработчиком исключений роутера службы
  (ответ `СБОЙ_СЛУЖБЫ`), не логикой в плагине. Там же: `httpx.InvalidURL` (кривой `AIFA_ENGINE_URL`)
  не `HTTPError` и уйдёт исключением в ядро, а не `СБОЙ_СЛУЖБЫ`.
- **З4.** `.rules/testing.md`: «DI over monkeypatch» — `monkeypatch.setattr(aef_tracing,
  "current_agent_id", …)` (`test_headers.py:140`) вместо `monkeypatch.setenv(
  "AGENT_SYSTEM_CONFIGURATION_AGENT_ID", …)`, который правило прямо называет безопасным и который
  проверил бы настоящий путь чтения; свой `Wire` вместо `tests/helpers/http_double.py` (там нет
  транспорта для `AsyncClient`, так что отступление объяснимо — стоит сказать об этом в тесте).
- **З5.** Новые ходы не пишут серверную сессию агента: `GET /chat/history/{session_id}`
  (`main.py:2690`) для чатов, начатых после шага 10, вернёт 404, а для старых — без новых ходов.
  Это зона шага 11 (история из ouroboros), выкатка — шаг 12, так что пользователи не заденут; в
