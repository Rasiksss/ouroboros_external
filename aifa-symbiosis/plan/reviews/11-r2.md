### Важно
**В1. Две одновременные правки записи сессии на PostgreSQL теряют ходы молча.**
`store/state.py:195–221` (`SqlStateStore.mutate`): `SELECT … FOR UPDATE`, затем `DELETE` + `INSERT` той же строки.
В PostgreSQL (READ COMMITTED) вторая транзакция, ждавшая замка, после фиксации первой не находит строку (она удалена,
новая не входит в снимок её запроса), получает `None` и пишет документ с нуля. Для `session_turns` это значит:
`_TurnAdded` второго хода (`session_turns.py:61–64`) оставляет в записи один новый ход, а `_RootNamed`
(`session_turns.py:72–77`) при `None` пишет `{"turns": []}` — история сессии теряет все прежние ходы, без ошибки.
На dev состояние — база (`deploy/dev/engine.env.example:28`). Дефект `mutate` старый и касается всех видов состояния,
но доработка впервые полагается на него для истории и проверяет только на SQLite.
Воспроизведение (выполнено, скрипт вне git): записать ход `run-1`; поток A — `state.mutate(CHAT_SESSION, …,
изменить=медленный(_RootNamed("run-1","root-1")))` с паузой 1,5 с внутри; поток B через 0,3 с — `record_turn(…, run_id="run-2")`.
Итог: `до: {'turns': [run-1]}` → `после: {'turns': [run-2]}` — ход `run-1` и его корень пропали.
Когда достижимо: конец хода N (`on_root` в `finally`) совпал со стартом хода N+1 той же сессии — две вкладки, «Стоп» и
сразу новая реплика; окно — длительность транзакции, вероятность мала, последствие — молчаливая потеря истории.
Как закрыть: `mutate` правкой строки на месте (`UPDATE … WHERE` после `FOR UPDATE`, вставка — `INSERT … ON CONFLICT DO
NOTHING` с повторным чтением), тест на PostgreSQL (`FINENGINE_TEST_DATABASE_URL`) с двумя потоками. → P81.
