## 5. Замечания

### Важно

**В1. Состав согласованной чистки не записан; §2 противоречит журналу.**
`PROGRESS.md` §2 «Список чистки диска dev» по-прежнему говорит: «только вариант Б; А и В не
утверждены». На стенде выполнены ещё «А-мини» (14 тегов `finengine-backend:rollback-*`/`candidate-*`,
то есть точки отката старого AIFA) и «В+Д+Е+Ж+З+И»: каталоги `~/aifa-slice31-*`, кэши, `/tmp`,
включая `/tmp/pytest-of-root`, ревизии snap, `journalctl --vacuum`, 5 образов. В R25 записано
«владелец утвердил В+Д+Е+Ж+З+И», но что значит каждая буква, в репозитории нет. Для А-мини строка
R24 описывает принятие ADR-0036, а слово владельца про сами 14 тегов прямо не приведено. Сверить
«строго по согласованному списку» поэтому можно только с журналом самой сессии.
Воспроизведение: `grep -n 'Список чистки' PROGRESS.md` и `cat ~/aifa-sym-cleanup-*.txt`.
Следующий шаг: владелец подтверждает, а §2 получает точный состав А-мини и В…И (что входит в
каждую букву) с датой. → P37.

**В2. README по букве не воспроизводится.**
- `aifa/deploy/dev/smoke/run.sh` записан в git как `100644` (`git ls-files -s`). На стенде он
  исполняемый только благодаря локальному `chmod` (`git diff`: `old mode 100644 / new mode 100755`).
  На свежем клоне `aifa/deploy/dev/smoke/run.sh` из README (п. 9) падает с `Permission denied`.
- Раздел «Открытое» (`README.md:147–157`) устарел и противоречит записи: «ADR-0037 (решение
  владельца) … пока вариант не выбран», «ADR-0036 (предложено)», «свободно ≈2 ГБ». Строка 73 —
  «ADR-0034, предложено». Все три ADR приняты, свободно 5,9 ГБ.
- П. 3 «шаг 04: только кэш сборки» и строка 156 не отражают выполненную чистку (В1).
Следующий шаг: `git update-index --chmod=+x` (или `bash …/run.sh` в README), правка «Открытого».
→ P38.

**В3. Дымовая 2a засчитывает успехом любое исключение.**
`smoke/ws_chat.py:66–69`: `except Exception` → «OK отказ рукопожатия». Ouroboros лежит, имя не
разрешилось, таймаут — 2a всё равно PASS. Это проверка доверенной границы, и ложное «зелёное» здесь
опасно. В `run.sh 2` упадёт хотя бы 2b, но `run.sh` с 2a отдельно этого не поймает.
Воспроизведение (выведено из кода, не запускалось): `ws_chat.py --no-owner --url
ws://nosuchhost:8080/ws` в одноразовом контейнере сети `aifa-sym-internal` → `OK`. Следующий шаг: принимать только `InvalidStatus` с кодом 403 (или
закрытие 1008), остальное — FAIL. Плюс негатив «рукопожатие с заголовками принято», чтобы
проверка падала на открытом контуре. → P39.

**В4. Workstation контура без лимитов ресурсов на хосте, общем с prod.**
`compose.yml`: `mem_limit` есть только у `ouroboros` (`:24`) и `engine` (`:142`). У `workstation`,
который исполняет код модели (`code_exec`) и код атомов, нет ни `mem_limit`, ни `pids_limit`, ни
`cpus`: `docker stats` показывает предел 5,785 ГиБ, то есть всю память хоста. Старый
`workstation-svc` запущен с `SESSION_RLIMIT_CPU_SEC`, `EXEC_TIMEOUT_SEC`, `RUNTIME_MODE`,
`SANDBOX_BINARY`, `ROOTFS_*` (имена из `docker inspect`). Новый идёт на значениях по умолчанию.
Swap занят уже 2,26 из 4 ГБ. P5 закрыт замером лёгкой нагрузки, а этот риск в нём не назван.
Следующий шаг (шаг 12 или раньше): лимиты `workstation` в compose. Сверить настройки рантайма с
`workstation-svc` и записать расхождения: от них зависит паритет вычислений атомов с опорной
записью (F5). → P40.

**В5. Правка ядра не прошла Definition of Done ouroboros.**
Корневой `CLAUDE.md`/`AGENTS.md` требует `/code-review` диффа в чистом контексте и
`./scripts/check.sh`. Ни того, ни другого не было: запись 04 сама это называет (P9, P22). Моё
чтение (§3) дефектов не нашло, но это ревью шага, а не `/code-review` ядра. Следующий шаг: прогнать
`/code-review` на `5258338..3bc6c13 -- new_core ouroboros docs tests openspec` до слияния 04 в `dev`.
→ P41.

### Замечания

- **З1.** P32 (F9 не читает `environment:` compose, нет проверки имён против схем) по R15 закрывался
  шагом 04, но не сделан. Запись 04 это признаёт. Нужен шаг-закрыватель: §4 P32 остаётся «открыто»
  без номера шага.
- **З2.** `smoke/run.sh:52–55`: маркер дымовой 3 считает любой `exec:stream` в логе с момента
  старта, а `--expect 4` ищет подстроку «4» в ответе. Параллельный ход дал бы ложный PASS. Лучше
  фильтровать по `task_id` хода. Отступление от постановки («в логе вызов `code_exec`») записано
  честно: ouroboros имени инструмента не пишет.
- **З3.** `smoke/room.py`: проверка «переменных службы нет» смотрит окружение `exec`, которому сам
  скрипт передаёт `env: {}`. Утечку из окружения контейнера Workstation (там есть
  `WORKSTATION_CREATE_SECRET`) она не ловит, если песочница не изолирует. Сейчас изоляция есть
  (`['LC_CTYPE','PATH']`). Стоит добавить явную проверку `WORKSTATION_CREATE_SECRET ∉ env`.
- **З4.** `restore_base.py:77–83` режет слои и историю, но `config.config` (Env, User, WorkingDir,
  Entrypoint) оставляет от верхнего образа AIFA. Сейчас утечки нет: `workstation-svc:local` —
  `User=aef`, `WorkDir=/app`, Env без AIFA-ключей. Но если слой AIFA когда-нибудь добавит
  `ENV`/`WORKDIR`, они уйдут в «базу» молча. Тест на это не проверяет.
- **З5.** ADR-0036 п. 4 («секрет создания не проверяется») сделан чтением `app/`. Старый
  `workstation-svc` на `/health` отвечает 401, так что какой-то контроль доступа у старой сборки
  есть (вероятно, мост `start.sh`). Стоит одной строкой записать, откуда 401, чтобы не путать
  с ADR-0028 п. 3.
- **З6.** ADR-0028 допускает `127.0.0.1:18180`, но публикуется весь порт, а не только `/ready`.
  Любой пользователь или процесс хоста с доверенными заголовками становится любым владельцем. Риск
  принят ADR, на общем хосте его стоит помнить.
- **З7.** `PROGRESS.md` §4: в строках P2, P3, P30, P33, P34, P36 статус склеен со столбцом
  «Следующий шаг» без `|`, в строке 5 ячеек вместо 6. P35 говорит «свободно 6,9 ГБ», сейчас 5,9
  (пересборка R26; §1 верен).
