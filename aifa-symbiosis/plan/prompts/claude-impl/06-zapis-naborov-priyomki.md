## Постановка задачи
Записать поведение нынешнего AIFA на наборах приёмки и вывести из записей схемы событий экрана —
это эталон, с которым сравнивается каждый следующий этап.

## Описание
- **Сценарии**: S0–S5 и А1–А8 — точно по определениям в `34-status.md` (документы, реплики,
  тумблеры, ожидаемый итог). Расхождение определения с каталогом `SCENARIOS.md` — по
  `34-status.md`, расхождение — в отчёт тестировщику (§4).
- **Документы**: те же файлы, что при приёмке частей 12 и 15; где лежат — найти по `34-status.md`.
  Файлы-документы в git не кладём, если они больше 5 МБ или не публичные — в записи хранится
  `sha256` и путь источника; решение — в отчёт.
- **Запись** записывающим клиентом шага 05 на старом dev AIFA, каждый сценарий — дважды (для
  оценки нестабильности). Длинные сценарии — с сервера под `nohup`, если с локальной машины ход
  рвётся.
- **P6**: проверить, принимает ли нынешний AIFA XLS/DOC (код `ingestion/` и один пробный
  `POST /documents/upload` небольшим файлом). Принимает — внести в разрешённые различия сравнения
  с ADR-0026.
- **Схемы событий (F5 а)**: из записей вывести JSON Schema каждого типа события SSE →
  `aifa/contracts/events/<type>.schema.json`; проверка: каждое событие всех записей проходит свою
  схему. Схемы — вместе с **предложенной** ADR «снимок событий экрана» (снимки контрактов меняются
  только с ADR, F13); принимает владелец.
- **Нестабильность**: пары записей одного сценария сравниваются; неустранимые различия
  (недетерминизм модели) — классифицировать: что нормализатор может снять, что останется
  «ожидаемым разбросом» для F5 (б) (например, формулировка ответа). Итог — таблица в
  `aifa/tests/golden/README.md`.

## Образ целевого результата
- `aifa/tests/golden/S0…S5, A1…A8/` — по две записи каждого сценария, нормализуемые.
- `aifa/contracts/events/*.schema.json` + тест F5 (а) зелёный на всех записях.
- `aifa/tests/golden/README.md` — состав набора, документы, известный разброс, разрешённые
