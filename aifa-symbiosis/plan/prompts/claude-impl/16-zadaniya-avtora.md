## Постановка задачи
Дать любой подзадаче ouroboros общие операции службы — регистрацию нового атома, отчёт в ленту
экрана и ожидание подзадачи планировщиком — так, чтобы служба не знала, какой навык у подзадачи
(ADR-0041). Автор пока остаётся в службе (`atom_author.py`) и сдаёт код тем же путём регистрации;
поведение пользователя не меняется.

## Описание
- **`atom_intake`** — одно место проверки и регистрации атома: контракт (правила `check_request`),
  входы `requires` есть в `Case`, один прогон в разовой комнате на настоящих входах, результат по
  `output_schema`, регистрация `eph.<name>@<версия>` (версия = хэш контракта и кода), исходник в
  `Case`; ≤ 3 неудачных регистрации одного имени за ход; лимит новых атомов `RunLimits`; сбой
  станции попытку не тратит; событие `author_attempt` на каждую проверку (тот же эмиттер, что
  `_report_author_attempt`). `atom_author.py` переводится на `atom_intake` — без второй копии
  проверки.
- **`aifa_register_atom`** — вход в `atom_intake` из любой задачи хода; ответы — §3.1.
- **`aifa_report`** — `ok`/`error`: событие `author_attempt` (`atom` = `label`, номер попытки —
  счётчик по `label` в ходе, `code` — если передан); `done`: только из подзадачи, без события,
  завершает её ожидание; ≤ 20 отчётов на задачу ouroboros.
- **`subtask_waits`** и **`aifa_wait(task_id)`**: подзадача хода запоминается по первому её вызову
  или кадру; завершена по первому из: кадр итога из `turn_gateway` (точка расширения шага 08),
  `aifa_report(status="done")`; итог — текст подзадачи; ещё не виденный `task_id` — `ЖДИ` по
  истечении `wait_sec` с подсказкой `get_task_result`.
- **Привязка** (§3.0): вызов принимается от корня или задачи с `root_task_id` = корень хода;
  `aifa_finish` и `aifa_goal` из подзадачи — `ОТКАЗ не_та_роль`; вызовы
  `LoopSession` одного хода — по одному.
- **`aifa_move`**: атом с кодом в `new_atoms` по-прежнему уходит в `atom_author.py` (до шага 17,
  ADR-0029).
- **Плагин**: регистрация `aifa_register_atom`, `aifa_report`; `task_id` в `aifa_wait`; снимок
  схем по ADR-0042; бюджет F4.

## Образ целевого результата
- Регрессия: поведение как после шага 15; атомы автора службы регистрируются через `atom_intake`.
- Контрактный тест на настоящем ouroboros с подставной моделью: корень вызывает
  `schedule_task("Навык: <фикстурный навык>. …")` → `aifa_wait(task_id)` → подзадача:
  `aifa_state` → `aifa_report error` → `aifa_register_atom` (первая — `ОТКАЗ`, вторая — `ГОТОВО`) →
  `aifa_report done` → корень получает итог → `aifa_move` с `eph`-атомом → `aifa_finish`.
  C4.1, C4.3–C4.7 зелёные; C4.2 — живой (Workstation), пропускаемый.
