## Постановка задачи
Сделать внутренний HTTP API службы, через который ouroboros вызывает инструменты: защита,
привязка вызова к ходу, роли, фоновые задания с длинным опросом, единый формирователь ответов
`ouro_view` — и два инструмента: `aifa_goal` и `aifa_wait`.

## Описание
- **`tool_api`**: роутер `/internal/ouro/v1/<tool>`; `Authorization: Bearer` (токен — поле
  `Settings`, сравнение за постоянное время); тело `{ctx, args}` по §3.0; привязка: прогон по
  `run_id`, активен, `owner_id`/`chat_id` совпадают; роли по §3.0 (`aifa_finish` и `aifa_goal` — только корень, `task_depth == 0`);
  передача корня хода в `turn_gateway` (интерфейс шага 08). Отказы — коды §3.0 через `ouro_view`.
- **Задания**: длинная работа — фоновое задание хода; инструмент ждёт до 240 с отрезками ≤ 20 с
  (длинный опрос на стороне службы; отрезок — чтобы плагин мог проверить отмену, шаг 10), затем
  `ЖДИ job=<id>`; отмена хода (`cancel_run`) отменяет задания хода; задание чужого хода —
  `ОТКАЗ задание_не_найдено`.
- **`ouro_view`** — единственный модуль, который превращает доменные результаты в текст для
  ouroboros: первая строка — код; таблица результатов как «Полученные артефакты»
  (`render_state`/`describe_execution` — **переиспользовать**, не переписывать); предел
  `result_limit` 12 000, длинное — частями (§3.0); границы текста документа нет (ADR-0040):
  значения артефактов в таблице результатов — полностью.
- **`aifa_goal`**: аргументов нет; цель — исходное сообщение прогона (служба сохраняет его при
  создании хода — добавь это в создание прогона, не меняя ручку); документы хода — как сейчас
  (`_chat_turn_docs`); `parse_message` → `execute_routed_goal(allow_dynamic=False)`; события
  конвейера — в журнал этого хода; результаты: `ГОТОВО` / `УТОЧНИ` / «показателя нет в отчёте» как
  `ГОТОВО` с этим итогом; при сбое стандартного пути (как сейчас вход в цикл) — **этап 2**: служба
  сама прогоняет нынешний `DynamicRun` целиком и возвращает его итог как `ГОТОВО` (ADR-0029);
  повторный вызов в ходе — тот же итог (C3.3). Подграфы внутри плана — `aifa_move` (шаг 13,
  ADR-0042 п. 4), не `aifa_goal`.
- **`aifa_wait`**: `job_id`, `wait_sec` 10–240; итог задания или `ЖДИ`; ожидание подзадачи по
  `task_id` — шаг 16 (ADR-0042).
- События `tool_call`/`tool_output` на экран — **не в этом шаге** (шаг 10, имена экрана).

## Образ целевого результата
- HTTP-клиент тестов, играющий роль плагина, вызывает `aifa_goal` для хода и получает итог; события
  конвейера лежат в журнале этого хода.
- C3.0, C3.2, C3.3, C3.4 зелёные.
- Сквозной тест: прогон хода (создан как в `POST /chat/turns`) → `aifa_goal` через HTTP → конвейер
  на фикстурном документе/`Case` → журнал хода (реплей `run_orchestrator`) → ответ `ouro_view`.
