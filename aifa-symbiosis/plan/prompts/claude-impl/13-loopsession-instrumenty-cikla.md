## Постановка задачи
Вынести состояние цикла из `DynamicRun` в `LoopSession` и открыть его инструментами
(`aifa_state`, `aifa_move`, `aifa_finish`) вместе с чтением документа (`aifa_doc`), **не меняя
правил цикла** (ADR-0029: одна переменная; правила завершения снимает шаг 13a). Ведущим
цикла пока остаётся служба (временный переключатель), поэтому поведение для пользователя не
меняется.

## Описание
- **`LoopSession`** (ADR-0023): состояние одного прогона — план, файлы-обещания, журнал ходов,
  `RunLimits`, созданные атомы, сигнатуры тупиков, время открытия; методы `state()`,
  `move(decision)`, `finish(decision)`; сохранение в базе службы после каждого хода (миграция;
  восстановление после перезапуска процесса). `DynamicRun.run()` переписывается **поверх**
  `LoopSession` (тот же цикл «модель → решение → move»), чтобы был один источник правил.
- **Решение из аргументов**: аргументы `aifa_move`/`aifa_finish` собираются в `Decision` тем же
  путём, что `parse_decision` из JSON модели (переиспользовать, не дублировать валидацию).
- **Инструменты** в `tool_api` + `ouro_view`: коды `НУЖЕН_ЦИКЛ` (у `aifa_goal` — при выключенном
  ведущем-службе), `ЛИМИТ`, `ПРИНЯТО`, отказы §3.0; `нет_цикла` без открытого цикла; события
  `dynamic_plan`/`dynamic_move` — те же эмиттеры. `aifa_state(artifact_ids)` — полное содержимое
  артефактов; `aifa_doc` — документы хода и распознанный текст по страницам и поиску (хранилище
  распознанного текста службы — переиспользовать), частями до `result_limit`. `aifa_finish` — с
  аргументами ADR-0042: решение из него не требует `answer` (правило `parse_decision` «finalize
  без answer — отказ» на этот путь не распространяется), `ПРИНЯТО` — без текста ответа, `details`
  финального `dynamic_move` — «ответ — в чате» или перечень файлов (ADR-0044 п. 2); проверка ссылок
  и опровергнутых находок остаётся (её снимает шаг 13a). Путь `loop_driver=engine` (решение из JSON
  модели с `answer`) не меняется.
- **Цикл и очередь** (§3.0, ADR-0043 пп. 4–5): цикл открывает только `НУЖЕН_ЦИКЛ`; изменяющие
  вызовы хода — по одному, ожидание в очереди входит в 240 с, иначе `ЖДИ job=`; чтение — вне
  очереди; после `ЛИМИТ` — `ЛИМИТ`, после `aifa_finish` — `цикл_закрыт`.
- **Временный переключатель** `Settings.loop_driver = "engine" | "ouroboros"`, по умолчанию
  `engine`: `engine` — `aifa_goal` при сбое гонит `DynamicRun` (как в шаге 09); `ouroboros` —
  `aifa_goal` отвечает `НУЖЕН_ЦИКЛ` + состояние. Комментарий «удаляется в шаге 19»; строка в
  `PROGRESS.md` §5.
- **Плагин**: регистрация `aifa_state`, `aifa_doc`, `aifa_move`, `aifa_finish`; `OUROBOROS_ENABLED_TOOLS`;
  снимок схем (F4) — с **предложенной** ADR на изменение снимка (F13).
- **Тесты**: перенести `tests/dynamic_run/` на API инструментов (решения — те же записанные ответы,
  теперь аргументами вызова) — в `aifa/finengine/tests/loop_tools/`; старые тесты `DynamicRun`
  остаются зелёными (он теперь поверх `LoopSession`). `aifa/contracts/loop_rules.yaml` — строка на
  каждое правило, **действующее в шаге 13** (§8 плана 34 и столбец «Правила» §3.1 без того, что
  вводят шаги 13a, 16, 17), с идентификатором теста; F8 (ADR-0044 п. 9).
- **Автор** — по-прежнему внутри службы: `aifa_move` с атомом-кодом вызывает `atom_author.py`.

## Образ целевого результата
- При `loop_driver=engine` — поведение как после шага 12 (тесты `tests/dynamic_run/` зелёные, дымовой ход
  на `aifa-sym` доходит до итога).
- При `loop_driver=ouroboros` клиент тестов, играющий планировщика, проводит цикл вызовами
  `aifa_state` → `aifa_move` … → `aifa_finish` и получает те же итоги и события, что `DynamicRun` на
  тех же записанных решениях.
- F8 зелёная: у каждого правила цикла — тест через API инструментов.
