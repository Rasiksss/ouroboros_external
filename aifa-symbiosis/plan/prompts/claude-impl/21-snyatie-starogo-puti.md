## Постановка задачи
После приёмки перевести dev-пользователей AIFA на новую систему и снять на dev старый путь через
OpenClaw — строго по согласованному владельцем способу, prod не затрагивая.

## Описание
- **Предусловия**: приёмка шага 20 — «можно снимать»; решение владельца о способе переключения
  (§2) и списке снимаемых dev-контейнеров. Нет — стоп.
- **План действий** (в отчёт до выполнения, по одной строке на действие): что останавливается
  (`openclaw-dev` и связанные dev-сервисы старого пути — по списку владельца), как dev-адрес
  начинает вести на фронтенд `aifa-sym` без изменения `finengine-caddy-1` (способ из §2), что с
  данными пользователей старого dev (не переносятся — ADR-0011/0012; если владелец решил иначе —
  по его решению), откат.
- **Выполнение** с `docker ps` до/после; каждая команда — цель без `prod`; бэкапы конфигурации
  перед изменением; `infproxy`, `finengine-caddy-1`, `workstation-svc-prod`, `finengine-prod-*`,
  `openclaw-prod-gw` — не трогать.
- **Проверка**: dev-адрес открывает новую систему; дымовые; один сценарий S-набора вживую;
  prod-контейнеры до/после совпадают и prod отвечает как прежде (только `docker ps`/статус — без
  запросов и тестов против prod).
- **Документы**: `aifa/deploy/dev/README.md` — новое состояние dev; `aifa-symbiosis/PROJECTS_STATE.md`
  — снимок dev-сервера обновлён.

## Образ целевого результата
- Пользователи dev работают в новой системе по прежнему адресу (или по адресу, решённому
  владельцем); старый путь через OpenClaw на dev остановлен; prod не затронут.

## Границы
Не делать: ничего с prod; удаление томов и данных без явной команды владельца; правки
`finengine-caddy-1`.

## Правила шага
- Любое сомнение, что действие заденет prod или общий сервис, — остановиться и спросить.
