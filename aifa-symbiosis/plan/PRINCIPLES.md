# Правила и принципы реализации

Для кодового агента (Claude Code, Sonnet 5.5 High). Действуют в каждой сессии реализации вместе с
`aifa/CLAUDE.md` (до шага 02 — часть Б `../architecture/RULES.draft.md`). Ревьюер проверяет диф по
этому же документу.

---

## А. Следование архитектуре

1. **Архитектура — закон шага.** Источники в порядке приоритета: ADR (`../architecture/adr/`) →
   `CONTRACTS.md` → `ARCHITECTURE.md` → промпт шага. Промпт не может отменить ADR; если кажется,
   что может, — это ошибка промпта: остановиться и описать.
2. **Расхождение кода с архитектурой — стоп.** Если реальный код (AIFA или ouroboros) не такой,
   как описано в ADR/контракте, или шаг нельзя сделать без отступления — не отступать молча.
   Записать в `PROGRESS.md` §4 «Проблемы»: что ожидалось (ссылка на ADR/контракт), что в коде
   (`путь:строка`), варианты с компромиссами. Закончить сессию тем, что уже целостно и зелёно.
3. **Архитектура меняется только новой ADR.** Кодовый агент может *предложить* ADR (файл со
   статусом «предложено»), но не принять: принимает владелец. Правки `ARCHITECTURE.md`,
   `CONTRACTS.md`, `FITNESS.md`, снимков `aifa/contracts/*.snapshot.json` — только в коммите с
   новой ADR (F13).
4. **ouroboros не трогаем.** Правки — только в `aifa/`, `aifa-symbiosis/`, `skills/aifa-*` (F1).
   Нужна правка ouroboros — вопрос владельцу.
5. **Границы держатся кодом, а не дисциплиной.**
   - служба не импортирует ouroboros; ouroboros не импортирует службу; плагин `aifa-engine` —
     тонкий клиент без логики (F2);
   - ответы инструментов формирует только `ouro_view`; ничего из распознанного текста, разметки,
     локаторов, паспорта, файла оригинала в ouroboros не уходит (F3, ADR-0025);
   - заголовки `X-Ouroboros-*` ставит только `ouro_client` (F12);
   - кадр WS без `attachment_ids` и без добавок к тексту пользователя (F6);
   - правило цикла держит код службы и тест, а не текст навыка (F8).
6. **Ничего «на будущее».** Шаг делает свою часть контракта, не больше. Инструмент, поле,
   настройка, которых нет в контракте шага, не появляются.
7. **Временное — помечено.** Временные переключатели (например, кто ведёт цикл до шага 14)
   — поле `Settings` с комментарием «удаляется в шаге NN» и строкой в `PROGRESS.md` §5.

## Б. Тесты

1. **Тесты до кода.** Сначала тест, который падает по правильной причине; затем код; коммит —
   шаг + его тест. Ревьюер проверит, что тест падал на родительском коммите.
2. **Базовая линия.** В начале сессии — прогон тестов затрагиваемых областей; что уже красное —
   в `PROGRESS.md` (запись сессии). В конце значимы только новые падения.
3. **Связность, а не только модули.** Для каждой границы, которую задел шаг (служба ↔ ouroboros,
   `tool_api` ↔ `loop_session`, конвейер ↔ журнал хода, служба ↔ каталог, служба ↔ Workstation,
   фронтенд ↔ служба), — минимум один тест, который проходит **через** границу с настоящими
   объектами с обеих сторон: контрактный тест из `CONTRACTS.md` (Cn.m) или сквозной тест шага.
   Модульные тесты нужны, но не заменяют его.
4. **Настоящая реализация вместо моков ради моков** (AIFA, правила кодирования 6.3). Подставляется
   только то, что внешнее и недетерминированное: модель (подставной сервер, шаг 07), сеть
   интернета, время. Ouroboros в контрактных тестах — настоящий (compose-профиль `contract`).
5. **Живое — пропускаемое.** Тесты с живой моделью, живым Workstation, стендом пропускаются без
   адреса/флага (`AIFA_LIVE_MODEL=1`, `FINENGINE_WORKSTATION_URL`, `AIFA_SYM_URL`); пропуск — не
   падение. Запасного локального исполнения кода атома в продукте нет (только фикстура тестов).
6. **Имя теста — поведение.** `test_<что_происходит>`, как в AIFA (`test_a_failed_batch_says_why_it_failed`).
7. **Номер контракта и проверки — в тесте.** Тест, закрывающий `C2.3` или `F6`, называет его в
   строке документации одной строкой — по ней ревьюер и F8 находят покрытие.

## В. Чистота и качество кода

Полностью — `aifa/finengine/docs/rules/coding_standards.md` (разделы 2, 3, 5 — обязательно) и, для
`skills/aifa-*`, `docs/DEVELOPMENT.md` ouroboros §Coding Rules. Самое важное:

- **Без вложенных функций** (2.1): помощники — на уровне модуля; колбэк с состоянием — маленький
  frozen dataclass с `__call__`.
- **Доменные имена** (2.9): `TurnGateway`, `LoopSession`, `AuthorJob` — да; `Manager`, `Handler`,
  `Helper`, `Utils` — нет.
- **Данные** — `@dataclass(frozen=True)` или `Contract`/pydantic; функции без скрытого состояния.
- **Ошибки** (2.7): бизнес-отказ — значение (код ответа инструмента, событие), системная ошибка —
  исключение; без голых `except`; без `try/except` в обычном потоке.
- **Настройки** — поле `Settings` службы, не `os.environ.get`. Секреты — только окружением, не в git.
- **Вызовы моделей** — только через шлюз моделей службы.
- **Тонкие роуты** (4.1): маршрут разбирает запрос и зовёт доменный объект; SQL — в слое данных (4.2).
- **Импорты** (3.1, 3.2): ленивые — только тяжёлые/необязательные/разрыв цикла; «неиспользуемый»
  импорт не удалять без проверки побочных эффектов.
- **Удаление** (5.2): перед удалением модуля — поиск ссылок по всему репозиторию, не только `.py`
  (Dockerfile, compose, `.md`, фронтенд, промпты).
- **Комментарии** — только «почему». Не пересказывать ADR и документы: ссылаться
  (`# ADR-0021: финал — непрогрессный кадр корня`).
- **Типы** — mypy проходит; без лишнего `Any`.
- **Логи** — структурные, без спама в циклах; без текста документов и секретов в логах.
- **Тексты для пользователя** — по-русски, понятные аналитику; без внутренних кодов и трасс.
- **Размер** — новый файл < 300 строк, если нет доменной границы; функция делает одно.
- **Точечные правки**: соседний код не «улучшать»; каждая изменённая строка прослеживается до шага.
- **Повторное использование**: прежде чем писать новое — найти, что уже есть в AIFA
  (`case_runtime`, `run_orchestrator`, `sealed_room`, эмиттеры событий) и переиспользовать.

## Г. Git и стенд

- Репозиторий `Rasiksss/ouroboros_external`, основная ветка `dev` (ADR-0030). Первое действие
  сессии: если ветка прошлого шага принята (в `PROGRESS.md` ревью и UI-тест без блокеров) и ещё не
  в `dev` — слить её в `dev` локально (`git merge --no-ff`). Затем ветка шага `sym/NN-<кратко>` от
  `dev`. `main` не трогать.
- Файлы добавляются явно; сообщения коммитов по-русски, первая строка — что изменилось.
  **Без push** без разрешения владельца.
- Коммиты: структурные изменения (перенос, переименование) — отдельно от поведенческих.
- Стенд: только compose-проект `aifa-sym`; перед каждой `docker`-операцией — цель без `prod`.
  prod не трогать никогда. Старый AIFA на dev не трогать до шага 21. Выкатка — по
  `aifa/deploy/dev/README.md` и только при сигнале владельца, записанном в `PROGRESS.md` §2.

## Д. Конец сессии

1. `aifa/scripts/check.sh` (с шага 02) зелёный, сравнение с базовой линией записано.
2. Запись в `PROGRESS.md` §3 по шаблону: диапазон коммитов, что сделано, тесты (какие контракты и
   проверки закрыты), базовая линия до/после, «Что и почему» (решения, альтернативы, компромиссы —
   менторский режим), что не сделано → §4.
3. Принятые по ходу решения по проблемам — `PROGRESS.md` §5; архитектурные — предложенная ADR.
4. Отчёт в чат — то же коротко.
