# Руководство по ревью шага

Для ревьюера (Claude Code, Opus 5.5 Medium). Сессия ревью — **чистый контекст**: ты не писал этот
код. Задача — найти проблемы, а не подтвердить качество.

---

## 1. Вход ревью (читать в этом порядке)

1. `prompts/claude-impl/NN-*.md` **целиком** — это ровно то, что получила реализация: постановка,
   описание, образ результата, правила, проверки. Ревью сверяет диф с ним, а не с твоим
   представлением о шаге.
2. `PRINCIPLES.md` — правила, по которым писался код.
3. ADR, разделы `CONTRACTS.md` и строки `FITNESS.md`, перечисленные в промпте реализации.
4. Запись реализации шага в `PROGRESS.md` §3: диапазон коммитов, заявленные тесты и базовая линия.
5. Диф: `git log --oneline <база>..<конец>` и `git diff <база>..<конец>` из записи.
6. `docs/INVARIANTS.md` ouroboros — если диф задел `skills/**`.

Ревьюер не правит код продукта и тесты. Ревьюер может (и при корпоративной недоступности — обязан, §4
п. 6) поднимать замену окружения и запускать тесты, `aifa/scripts/check.sh`,
проверять тест на родительском коммите (`git stash`/`git worktree`), читать любой код.

## 2. Вертикальное ревью — сквозь слои по пути шага

Выбери путь (или пути), который шаг меняет, — от входа пользователя или вызова до выхода — и
пройди его по всем затронутым слоям, на каждой границе сверяя с контрактом:

```text
фронтенд → ручка службы → шлюз хода → WS ouroboros → навык/плагин → внутренний API →
доменный объект (LoopSession / конвейер / AtomIntake) → хранилище / комната → события → SSE → экран
```

На каждой границе:
- данные соответствуют контракту (поля, коды, формат первой строки, пределы размера);
- ошибка на этой границе превращается в правильное значение/событие, а не теряется и не роняет ход;
- идентичность (владелец, чат, `run_id`, корень) не пересчитывается и не берётся из полезной
  нагрузки (инвариант 7 ouroboros, ADR-0014, ADR-0021);
- есть тест, который проходит через эту границу с настоящими объектами с обеих сторон.

Отдельно — **отказные пути**: отмена хода, обрыв WS, таймаут длинного вызова, отказ правила цикла,
сбой станции, недоступный каталог. Для каждого, который шаг затрагивает, — что увидит пользователь.

## 3. Горизонтальное ревью — один срез через все изменённые модули

Пройди весь диф по каждому срезу отдельно:

| Срез | Что проверять |
|---|---|
| Границы | F1 (ничего вне `aifa/`, `aifa-symbiosis/`, `skills/aifa-*`), F2 (импорты), ответы только через `ouro_view`, F6, F12, нет веток по имени навыка (ADR-0041); запуск проверок, а не чтение |
| Архитектура | каждое решение диффа прослеживается до ADR/контракта; нет инструментов, полей, настроек сверх контракта шага; временное помечено |
| Стиль и правила кода | `PRINCIPLES.md` §В: вложенные функции, имена, ошибки, настройки, импорты, тонкие роуты, комментарии «почему», размеры |
| Повторы | не написано ли заново то, что уже есть в AIFA или ouroboros; нет ли двух мест, решающих одно |
| Мёртвое | неиспользуемые функции, ветки, настройки; удалённое — со ссылками по всему репозиторию |
| Данные и состояние | что хранится, где, кто владелец; перезапуск процесса службы — что теряется |
| Безопасность | секреты не в git и не в логах; текст документа не в логах; в ouroboros — только через `aifa_doc`/`aifa_state` (ADR-0040); внутренний API — токен; порты |
| Тексты пользователю | по-русски, без внутренних кодов |

## 4. Связность тестов и контрактов

1. Составь таблицу границ, которые задел диф, и для каждой найди тест, проходящий через неё:

   | Граница | Контракт | Тест (`путь::имя`) | Настоящие обе стороны? | Падал до изменения? |
   |---|---|---|---|---|

   Пустая ячейка «тест» на задетой границе — **блокер**.
2. Для заявленных в промпте контрактов (Cn.m) и проверок (Fn) — тест существует, называет их и
   проверяет именно то, что написано в `CONTRACTS.md`/`FITNESS.md`, а не похожее.
3. Выбери 2–3 ключевых теста и проверь, что они **падали** на родительском коммите шага.
4. Моки: подставлены только модель, интернет, время. Подставной ouroboros вместо настоящего в
   контрактном тесте — блокер (кроме модульных тестов клиента).
5. Прогони `aifa/scripts/check.sh`; сравни с базовой линией из `PROGRESS.md`.
6. **Корпоративная недоступность — не причина не прогнать.** Стадию, которая не стартует из-за
   корпоративного ресурса (nexus, внутренний реестр, корпоративная сеть), ревьюер прогоняет сам на
   замене по `PRINCIPLES.md` §А.8 — для `skills/**` это ворота ouroboros (`./scripts/check.sh`
   стадия за стадией на pypi-окружении). Вердикт и строка «Definition of Done ouroboros» опираются на
   этот прогон; «не прогнано (nexus)» в отчёте ревью не принимается. Если реализация так записала
   свою стадию — это замечание уровня «важно» (неполная проверка), а не причина снять с себя прогон.

---

## 5. Уровни замечаний

| Уровень | Что это | Последствие |
|---|---|---|
| **Блокер** | нарушение ADR/контракта/инварианта; задетая граница без теста; текст документа в логах или в ouroboros в обход инструментов `aifa-engine`; правка ouroboros; красные ворота; тест не падал до изменения | шаг возвращается на доработку (`_FIX.md`) |
| **Важно** | ошибка в отказном пути, неполное покрытие, нарушение правил кода уровня MUST | исправляется в доработке, если она будет, иначе — шагом из §4 `PROGRESS.md` с номером |
| **Замечание** | стиль, имена, мелкие упрощения | в отчёт ревью; без отдельной работы |

---

## 6. Результат ревью

1. Файл `aifa-symbiosis/plan/reviews/NN.md` (при повторном ревью — `NN-r2.md`):
   - вход: какие файлы прочитаны, диапазон коммитов;
   - вертикальное ревью: путь(и) и находки по границам;
   - горизонтальное ревью: находки по срезам;
   - таблица связности тестов (§4);
   - замечания по уровням, у каждого `путь:строка`, почему это проблема, как воспроизвести;
   - вердикт: **«можно дальше»** / **«можно дальше с замечаниями»** / **«блокеры»**.
2. Строка в `PROGRESS.md` §1 (статус ревью) и запись §3; «важно» и «замечания», которые не
   закрываются доработкой, — в §4 с номером шага-закрывателя.
3. Отчёт в чат — вердикт и блокеры.
