# Симбиоз AIFA и ouroboros

Итог обсуждения 13–14.10.2026. Здесь — задача, исходное состояние обоих проектов, найденные факты,
решения владельца и высокоуровневая архитектура. Низкоуровневая архитектура — предмет следующей
сессии (раздел 9). Состояние репозиториев и стенда — в `PROJECTS_STATE.md`.

---

## 1. Задача

**Целевой образ.** Фронтенд AIFA остаётся прежним. Под ним работает ouroboros в роли оркестратора:
он принимает сообщение пользователя, планирует ходы, пишет код новых атомов и вызывает инструменты.
Всё, что сделано и проверено в AIFA-CLAW за последний месяц, переносится и продолжает работать.

**Ограничения.**
- Ядро ouroboros и его станцию (клиент Workstation) не меняем. Вся доработка — навыки, служба движка,
  настройки.
- Всё живёт в одном собственном репозитории владельца: ouroboros, finengine, фронтенд и остальное.
  Слияний в корпоративный ouroboros нет.
- Только dev. Prod (`finengine-prod-*`, `openclaw-prod-gw`, `workstation-svc-prod`,
  `finengine-caddy-1`, `infproxy`) не трогать.
- Перенос поэтапный, на каждом этапе — сравнение с опорной записью поведения нынешнего AIFA.

**Критерий готовности.** Наборы приёмки AIFA (S0–S5, А1–А8 из `34-status.md`) проходят на новой
системе так же, как на старой; экран показывает те же граф, план, ленту ходов, карточки и файлы;
путь через OpenClaw удалён.

## 3. Найденные факты, влияющие на архитектуру

1. **Станция одна и та же.** Клиент ouroboros и `sealed_room.py` AIFA ходят в один API Workstation
   (`/v1/sessions`, `/exec`, `exec:stream`, `files:*`). Ouroboros держит сессию на чат, AIFA —
   разовую комнату на запуск. Предел `code_exec` — 300 с на стороне сервиса.
2. **A2A ouroboros работает от одного настроенного владельца** (`transport/a2a/executor.py`).
   Многопользовательский вход — только браузерный транспорт с `TrustedHeaderIdentity`: заголовки
   `X-Ouroboros-Owner-Id`, `X-Ouroboros-Agent-Id`, `X-Ouroboros-Chat-Id` ставит доверенный посредник.
3. **Инструмент знает владельца, агента и чат** (`ToolContext.scope`). Отдельный ключ хода не нужен.
4. **Агент** — запись в реестре владельца (имя, описание). Своей системной инструкции нет; на агента
   задаются модели, сила рассуждения, навыки, подтверждение, накопление памяти, язык, часовой пояс.
   `main` создаётся автоматически.
5. **Ответ ouroboros приходит целиком**: посимвольной выдачи у браузерного транспорта нет.
6. **Предел описаний инструментов расширений в первом запросе** — 8000 байт на все. Инструментов
   AIFA должно быть немного и с короткими описаниями.
7. **Таймауты**: задача — 1800 с (жёсткий), инструмент — 600 с; цикл AIFA — до 1200 с, форма — дольше
   300 с. Долгие инструменты — фоновый запуск и опрос (в AIFA этот приём уже есть).
8. **Файловый каталог** принимает PDF, XLSX, DOCX, PPTX, TXT, MD, CSV, JSON, картинки; XLS и DOC — нет.
9. **Зависимости**: Python совпадает (3.12); конфликт один — `mcp==2.1.1` у ouroboros против `mcp<2` у
   finengine (нужен только MCP-серверу для OpenClaw, который удаляется). Без него всё разрешается.
   В одном репозитории — два отдельных окружения и образа.
10. **Подтверждение действий** (`OUROBOROS_TOOL_CONFIRMATION_ENABLED`) покрывает `code_exec`,
    `file_write`, `file_edit`, `apply_patch`, `data_write`.
11. **Dev-сервер**: диск заполнен на 97 %; Workstation AIFA (`workstation-svc`) и `infproxy` общие с
    процессами, которые трогать нельзя или нежелательно.

## 5. Высокоуровневая архитектура

```text
Браузер ── фронтенд AIFA (без изменений)
              │ прежние ручки и поток событий (SSE)
              ▼
┌─────────── Служба движка (finengine без OpenClaw и без своего цикла) ───────────┐
│ вход пользователей · ручки фронтенда · журнал хода и события на экран            │
│ разбор запроса · граф · атомы · Case · проверки · реестр показателей             │
└──────┬─────────────────────────────▲──────────────────────────────┬──────────────┘
       │ сообщение пользователя      │ вызовы инструментов           │ исполнение атома
       │ (WebSocket, заголовки       │ (навык aifa-engine)           │ в графе (sealed_room)
       │  владельца и чата)          │                               ▼
       ▼                             │                     ┌──────────────────────┐
┌─────────── ouroboros, агент main = AIFA ───────────┐     │ Workstation контура  │
│ цикл: модель → инструменты                         │────►│ ouroboros            │
│ навыки: aifa-planning, aifa-atom-author,           │     └──────────────────────┘
│         aifa-engine, workstation                   │
│ подзадача «автор кода»                             │
│ история чатов · файлы (S3) · PostgreSQL            │
└────────────────────────────────────────────────────┘
```

**Ход.**
1. Служба движка проверяет вход, заводит прогон для экрана, передаёт сообщение в ouroboros по
   WebSocket с заголовками владельца и чата.
2. Ouroboros по навыку планирования вызывает «выполнить цель»; служба прогоняет стандартный конвейер,
   граф и статусы узлов сразу идут на экран.
3. Если стандартный путь не справился, ouroboros ведёт цикл инструментами: «принять план», «исполнить
   шаги», подзадача-автор.
4. Автор пишет и отлаживает код в своей сессии Workstation, отчитывается о каждой попытке, затем
   вызывает «создать атом»; служба проверяет код в разовой комнате на данных `Case` и регистрирует атом.
5. «Завершить» со ссылками на доказательства; служба проверяет ссылки, публикует результат и файлы;
   текст ответа приходит по WebSocket и выдаётся на экран.

> На время MVP гарантия ниже снята, а навык подзадачи выбирает планировщик — ADR-0040, ADR-0041
> (`architecture/adr/`). Текст ниже — исходное решение 14.10.2026.

**Гарантия «числа только из доказательной базы»:** ouroboros не видит текста документа; инструменты
цикла отказывают без попытки стандартного пути; «завершить» не принимает ссылок на несуществующее.

**Данные.**

| Данные | Где |
|---|---|
| Пользователи и вход | служба движка |
| Чаты и сообщения | ouroboros |
| Оригиналы документов и файлы-результаты | каталог файлов ouroboros (S3) |
| Распознанный текст, разметка страниц, `Case`, доказательства, журналы прогонов | база службы движка |
| Задачи, настройки, расход | PostgreSQL ouroboros |

**Куда переезжает сделанное в AIFA.**

| Сделано | Куда |
|---|---|
| Промпты планировщика и фазы планирования | навык `aifa-planning` (инструкция + справочные файлы: каталог атомов, реестр) |
| Промпт автора атомов | навык `aifa-atom-author` |
| Цикл `DynamicRun` как ведущий | цикл ouroboros |
| Правила, которые держит код цикла | инструменты навыка `aifa-engine` → служба движка |
| Контракты, граф, атомы, `Case`, реестр, проверки, разбор запроса | служба движка без изменений |
| Экран | без изменений |
| Диспетчер на OpenClaw, плагины, навыки станции, MCP-сервер движка | удаляются |

## 7. Риски

- Качество планирования на цикле ouroboros ниже, чем у отлаженного `DynamicRun` — ловится сравнением
  с опорной записью на этапе 3.
- Предел описаний инструментов (8000 байт) и проверка каждого вызова лёгкой моделью (задержка) —
  учесть при проектировании инструментов.
- Подзадача-автор и сессия Workstation на чат: проверить, что подзадача видит ту же сессию.
- Каталог файлов не принимает XLS и DOC — решить, конвертировать или отказывать.
- Диск dev 97 %; Workstation и PostgreSQL/S3 для ouroboros — новые контейнеры на том же сервере.
- Два источника истины на время параллельной работы старого AIFA (нерушимое решение №10) — снимается
  этапом 6.
