# ADR-0092. Все независимые действия хода исполняются одновременно, сбой действия — трейс корню

Статус: принято (владелец, 27.10.2026) для проверки на dev; дополняет ADR-0088 и ADR-0090

## Контекст
Целевая картина владельца: ход — набор независимых действий, они исполняются параллельно, ходы идут по одному, выход хода —
вход следующего. Прогон 27.10 (ed53d54a) показал, что служба исполняет её не до конца: `_move` шёл фазами «части цели →
сценарии → шаги атомов», шаги (`web.search`) стартовали после трёх частей; граф шагов собирается обычным (не составным), и
`GraphExecutor` запускал его готовые узлы по очереди. Исключение внутри шага не перехватывалось: оно давало 500 от
`aifa_move`, а в прогоне 26.10 это роняло поток `agent-runtime` ouroboros (ADR-0090 закрыл только части цели).
Замер хода 1 (база службы): три части шли параллельно 07:49:01–07:53:45, поиск — 2 секунды, после них. Выигрыш этого
решения на нашей задаче невелик; оно нужно для общей модели хода и для ходов с несколькими медленными шагами.

## Решение (вариант D2: параллельность внутри одного `aifa_move`)
- `dynamic_run.py`, `_move`: части цели и шаги атомов исполняются одновременно (`_run_move_units`, по потоку на единицу,
  копия контекста хода, как в ADR-0088). Строки итога собираются в прежнем порядке. Тупики (`dead_end_actions`) записываются,
  только если ход в целом не дал новых результатов.
- `graph_executor.py`: параметр `run(..., parallel_ready=False)`; при `True` готовые узлы любого графа идут пулом потоков
  (до 8), как у составного. `CaseRuntime.execute(..., parallel_ready=…)` передаёт его; `_run_steps` включает режим для
  графа шагов хода. По умолчанию порядок обычных графов не меняется.
- Фразы-сценарии (`scenarios`, запуски без `aifa_move`: в цикле корня они выключены) сохраняют прежний порядок «части → сценарии →
  шаги»: шаг может опираться на их результат, одновременно идут только части цели и шаги атомов.
- Состояние цикла, которое меняют параллельные действия (`metric_attempts`, сбои атомов), — под `state_lock`.
- Сбой действия — отказ этого действия: `_failure_text` даёт «✗ Тип: сообщение» и хвост трейса (последние кадры, до 1600
  знаков), полный трейс — в лог. Так для частей цели (`_run_parts`), для единицы «шаги» (`_run_move_units`) и для хода
  целиком (`move()`): неожиданное исключение возвращается как итог хода `failed`, а не как 500. `BudgetExceeded` и отмена
  пользователем поднимаются как прежде.
- Зависимость внутри хода не поддерживается как вид исполнения: действие, которому нужен результат другого действия того же
  хода, корень переносит в следующий ход. Если оно всё же попало в один ход, шаг не увидит результата части и построит
  нужное сам (работа задвоится, идемпотентно по узлам Case) либо план шага не соберётся с понятной причиной.
  `depends_on` между частями (слои ADR-0088) сохраняется.

Не затронуто: очередь `aifa_move` по одному на `LoopSession` (ADR-0043 п. 4); параллельные вызовы `aifa_move`; единицы
учёта цикла (ходы, лимиты); схема `task_plan`. Авторы (`schedule_task`) идут вне `aifa_move`, корень запускает их без ожидания.

## Проверка
`tests/dynamic_run/test_move_units.py` (одновременность частей и шагов барьером; исключение в шагах → отказ с трейсом, части
доходят до конца; трейс в тексте отказа части; сбой хода целиком → текст, а не исключение; `BudgetExceeded` поднимается),
`tests/executor/test_parallel_ready_nodes.py` (два независимых узла одновременно при `parallel_ready`; без режима порядок
прежний). Красные до правки: четыре теста хода и один тест исполнителя.

Риск: независимые графы одного хода одновременно читают и пишут Case; запись головы и ad-hoc спецификаций идёт под замком
Case (ADR-0090), артефакты и узлы исполнения идемпотентны по ключу узла. Одновременные вызовы модели (`locate`,
`read.value`) ограничены числом единиц хода (до трёх частей и одного графа шагов).
