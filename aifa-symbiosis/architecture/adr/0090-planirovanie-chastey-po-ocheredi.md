# ADR-0090. Планы частей одного Case строятся по очереди, сбой части — отказ этой части

Статус: принято (владелец, 26.10.2026) для проверки на dev; дополняет ADR-0088

## Контекст
Прогон 26.10 (db4edbcd): первый ход из трёх частей (выручка, EBITDA, чистый долг; ADR-0089) исполнялся параллельно по
ADR-0088 и упал в 12:23:54 с `CaseConflictError: stale Case revision: expected=1, actual=2`. Причина — оптимистичная
проверка ревизии Case при записи плана: каждая часть читает ревизию, собирает граф и пишет «голову» Case с условием
«ревизия прежняя» (`_persist_plan` → `update_case_head`); параллельные части читают одну ревизию, пишет первая, остальные
получают конфликт. Исключение вышло из потока части, `aifa_move` ответил 500, ouroboros счёл это потерей исполнителя,
его поток `agent-runtime` завершился, корень получил `failed` (повтор встал в очередь, и очередь никто не разбирал).
ADR-0088 называл риск («если появятся конфликты записи Case, слой с общим входом исполняется по очереди»).
Ревизию Case меняют регистрация документа, запись плана (`update_case_head`), паспорт отчёта по итогам исполнения,
регистрация ad-hoc спецификации и правка значения; артефакты и узлы исполнения ревизию не меняют.

## Решение
- `store/cases.py`: `case_lock(owner_id, case_id)` — один `RLock` на Case в процессе.
- `skills/case_runtime.py`: `plan`, `plan_many`, `plan_steps` исполняются под замком Case (чтение ревизии, сборка графа и
  запись головы одним отрезком); запись паспорта по итогам исполнения — тоже под замком; новый `register_ad_hoc_spec`
  берёт его же. `production_runtime.py` регистрирует ad-hoc спецификации через `register_ad_hoc_spec`, а не напрямую в
  хранилище: ревизия не растёт посреди плана соседней части.
- Планы частей хода строятся по очереди (граф собирается без модели, доли секунды), исполнение графов остаётся
  параллельным: замок на нём не держится.
- `skills/spec/dynamic_run.py`, `_run_parts`: исключение внутри части (кроме `BudgetExceeded`) становится результатом
  «✗ ТипОшибки: текст» этой части; остальные части доходят до конца, ход возвращает планировщику итог, а не 500. Так же
  в цикле уже обрабатывается сценарий (`run_scenario`).
- Проверка ревизии (`expected_revision`) остаётся: она защищает от настоящей параллельной правки дела (поправка значения,
  другой экземпляр службы).

Не затронуто: параллельные вызовы `aifa_move` (по-прежнему очередь, ADR-0043 п. 4), параллельность шагов атомов,
навыки (ADR-0089 откачен на dev до проверки этого решения).

Ограничение: замок живёт в процессе. Если один Case ведут несколько экземпляров службы, конфликт между ними остаётся
возможным и поднимется как отказ части (текстом), а не как 500; тогда нужен замок на уровне базы
(`pg_advisory_lock` по Case) или повтор плана — отдельное решение.

## Проверка
`tests/dynamic_run/test_parallel_case_planning.py` (пять тестов, три красных до правки: гонка планов трёх частей на
реальной базе с паузой внутри планировщика — тот же `expected=1, actual=2`; регистрация ad-hoc спецификации посреди
плана соседней части; ошибка части становится отказом этой части; ещё общий и реентерабельный замок и непроглоченный
`BudgetExceeded`). `test_parallel_goals.py::test_an_error_in_one_part_is_a_refusal_of_that_part_only` заменил тест
ADR-0088 «ошибка части доходит до вызывающего». Живой прогон: ход из трёх частей не падает, три графа идут одновременно.
