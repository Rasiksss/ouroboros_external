# ADR-0023. Состояние цикла живёт в службе; ход цикла — вызов инструмента

Статус: принято (14.10.2026, сессия архитектуры)

## Контекст
`DynamicRun` (`skills/spec/dynamic_run.py`) сам ведёт цикл: `run()` → `_ask_planner()` (модель) →
`parse_decision()` → `_move()`; правила раздела 8 плана 34 держатся в `check_request`, `_move`,
`_ask_planner`, `_with_promised_files`, `_repeated_dead_end`, `RunLimits`. Теперь ведущий — цикл
ouroboros, а ход приходит вызовом инструмента.

## Решение
- Управление переворачивается: из `DynamicRun` выделяется `LoopSession` — состояние цикла одного
  прогона (план, файлы-обещания, журнал ходов, счётчики `RunLimits`, созданные атомы, сигнатуры
  тупиков, время открытия) и методы `state()`, `move(decision)`, `finish(decision)`. Решение
  планировщика собирается из аргументов инструмента тем же `parse_decision`-путём, что сейчас из
  JSON модели.
- Ведущий драйвер `run()`/`_ask_planner()` и вызов модели планировщика удаляются (этап 5); вся
  проверка решения остаётся.
- Состояние держится в памяти процесса службы и сохраняется в базе службы после каждого хода (для
  перезапуска и опорных сравнений); `Case` — как сейчас.
- Предел времени цикла (1200 с) считается от открытия цикла; по его исчерпанию `aifa_move`
  отвечает `ЛИМИТ` и принимает только `aifa_finish` («последнее слово», как `_stop`).

## Следствия
- Тесты `tests/dynamic_run/` переносятся на API инструментов с подставными решениями.
- Задача ouroboros (1800 с) должна вмещать стандартный путь + цикл 1200 с; предел задачи
  поднимается настройкой (ADR-0027), ядро не меняется.

## Чем проверяется
C3 (по правилу — тест), F8 (у каждого правила раздела 8 есть тест).
