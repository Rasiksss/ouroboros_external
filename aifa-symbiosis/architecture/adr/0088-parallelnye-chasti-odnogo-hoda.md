# ADR-0088. Независимые части цели одного хода исполняются одновременно

Статус: принято (владелец, 26.10.2026) для проверки на dev; дополняет ADR-0043 п. 4

## Контекст
Прогон 26.10 (9f45ce36): первый ход из трёх независимых частей (выручка, EBITDA, чистый долг) занял 5,7 минуты, потому
что `_run_goal_refs` исполнял части по очереди, хотя у каждой свой граф и готовое он берёт из Case. Исполнитель графа
параллелит готовые группы только внутри составного графа. ADR-0043 п. 4 ставит вызовы, меняющие `LoopSession`, в
очередь по одному на ход — это остаётся: ходов по-прежнему один за раз.

## Решение
Параллельность внутри одного хода; единицы учёта цикла (ходы, лимиты, журнал, «итог прошлого хода», «новые результаты
хода») не меняются.
- `dynamic_run.py`: `_dependency_layers` делит части хода на слои по `depends_on`; части одного слоя идут одновременно
  (`ThreadPoolExecutor`, не больше `PARALLEL_PARTS` = 4), слои — по порядку. Часть, чья зависимость не получена, не
  исполняется («✗ не исполнялась: часть … не получена»), её независимые соседи идут как обычно.
- Состояние цикла (`goal_status`, `metric_attempts`, строки итога) меняет только вызывающий поток после слоя, в порядке
  частей; потоку пула передаётся копия контекста хода (тумблер поиска, бюджет, трасса), как у составного графа.
- `moves.md`: независимые части собирать в один ход, зависимость называть в `depends_on` (иначе части пойдут вместе).
Не затронуто: параллельные вызовы `aifa_move` (по-прежнему очередь), параллельность шагов атомов внутри хода (исполнитель
обычного графа идёт группами по порядку), части, исполняемые вместе со шагами одного хода.

## Проверка
`tests/dynamic_run/test_parallel_goals.py` (10 тестов, пять красных до правки: одновременность барьером из потоков,
порядок слоёв, провал зависимости, попытки после слоя, контекст в потоках, ошибка части, одна часть в вызывающем потоке);
тест текста `moves.md`. Живой прогон: первый ход из трёх независимых частей короче прежних 5,7 минуты.

Риск: части одного слоя могут одновременно считать общий вход (например, одну страницу); результат идемпотентен по
узлам Case, дублирование стоит лишь времени. Если на живом прогоне появятся конфликты записи Case, слой с общим входом
исполняется по очереди.
