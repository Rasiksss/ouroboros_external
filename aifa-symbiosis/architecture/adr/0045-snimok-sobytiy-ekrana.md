# ADR-0045. Снимок событий экрана: JSON Schema каждого типа события SSE из опорных записей

Статус: предложено
Заменяет: —

## Контекст
F5 (а) (`FITNESS.md`) требует JSON Schema каждого типа события SSE «из опорной записи» и проверки,
что каждое событие нового хода ей соответствует (ADR-0005, ADR-0015). Схем не было: экран читает
поток `GET /chat/runs/{id}/events` через `unwrapRunEvents` (`aifa/web/src/lib/api.ts`), и поломку
формы, которую не заметит ни один тест фронтенда, до шага 06 нечем было поймать. Снимки контрактов
в `aifa/contracts/` меняются только с ADR (F13), поэтому схемы вводятся этой записью.

## Решение
1. Снимок — каталог `aifa/contracts/events/`, по файлу `<ключ>.schema.json` (JSON Schema 2020-12) на
   каждый тип события. Схема описывает событие так, как оно идёт по сети (конверт целиком), а не
   после `unwrapRunEvents`. Ключ: `legacy.<legacy_event.type>` для конверта `legacy`, иначе
   `event_type` (`completed`, `result`, `error`, `node_run`); событие без `event_type` — `screen.<type>`.
2. Схемы выводит `aifa/tests/golden/golden_cli.py schemas` из записей наборов приёмки
   (`golden_schema.py`): типы значений, обязательность поля — «есть в каждом образце типа»; различители
   `event_type`, `schema_version`, `legacy_event.type` закреплены значением. Лишнее поле допускается
   (экран его не читает); статусы (`completed.status`) — любая строка, потому что запись видит не все
   исходы (A11). Биения (`heartbeat`, `ping`) в запись не попадают и схем не имеют.
3. Проверка F5 (а) — `aifa/tests/contract/test_screen_events.py`: каждое событие каждой записи
   `aifa/tests/golden/<СЦЕНАРИЙ>/*-run?.json` проходит схему своего типа; события типа без схемы —
   нарушение («новых типов нет, кроме разрешённых ADR»). Тот же `golden_schema.violations` применяет
   контрактный тест нового хода (шаг 12).
4. Изменение набора схем — новая ADR, не правка этой. Появление нового типа события или поля,
   которое старая система не слала, — разрешённое различие только с номером ADR (F5 (б)).

## Следствия
- Снимок, выведенный на шаге 06 из потоков прогона 06.10.2026 (части 12 и 15 `34-status.md`) и двух
  служебных записей, неполон: нет типов, которых в этих потоках не было (`file`, `plan`, `plan_step`,
  `tool_progress`, `typed_*` и др. — по `golden/README.md`), а у редких типов один-два образца
  (`x-samples` в схеме). Принимать снимок следует после того, как `golden_cli.py schemas` будет
  повторён на записях шага 06 (13 сценариев × 2) и список типов в README сойдётся с `unwrapRunEvents`.
- F13 охраняет только `aifa/contracts/*.snapshot.json`; шаблон `SNAPSHOT` в
  `aifa/tests/architecture/test_adr_discipline.py` и текст F13 в `FITNESS.md` нужно расширить до
  `aifa/contracts/events/*.schema.json` — отдельным шагом вместе с принятием этой записи.
- Схемы зависят от того, что видела старая система: подставная модель шага 07 обязана давать те же
  формы; иначе различие придётся либо чинить, либо разрешать новой ADR.

## Чем проверяется
F5 (а): `aifa/tests/contract/test_screen_events.py`; сам вывод — `aifa/tests/golden/test_golden_schema.py`.
