# Контракты симбиоза AIFA и ouroboros

Низкоуровневые контракты между частями. Решения, на которых они стоят, — в `adr/`. Меняется
документ только вместе с новой записью ADR (F13). Схемы в виде JSON Schema и эталонные кадры
появятся в `aifa/contracts/` на этапах 0–2; здесь — их содержание.

Обозначения: **С** — служба движка (finengine), **О** — ouroboros, **Ф** — фронтенд AIFA,
**W** — Workstation контура ouroboros. `Cn.m` — контрактный тест.

---

## 1. Фронтенд ↔ служба движка (C1)

**Что не меняется.** Все ручки и формат событий, которыми пользуется `web/`: вход
(`auth_router`), `POST /chat/turns` → `{run_id, events_url}`, `GET /chat/runs/{id}/events` (SSE:
реплей журнала + живой хвост, биение 15 с), `POST /chat/runs/{id}/cancel`, `/dialogs`
(GET/PUT/DELETE), `GET /chat/history/{session_id}`, документы (`/documents/*`), источники проекта
(`/projects/{id}/sources/*`), выгрузки (`/metrics/export.xlsx`, `/export/table.xlsx`), артефакты
проекта, «Сценарии». Ни одной правки фронтенда (ADR-0015).

**Что меняется внутри службы.**

| Ручка | Было | Стало |
|---|---|---|
| `POST /chat/turns` | `agent.query_stream` → OpenClaw (или инлайн для `pinned_tool`) | ход отдаётся в О (§2); журнал хода пишут клиент хода и обработчики инструментов (§3). Ветка `pinned_tool` — открытый вопрос (`ARCHITECTURE.md` §9) |
| `GET /chat/runs/{id}/events` | журнал хода | без изменений; источники событий — §2.5 |
| `POST /chat/runs/{id}/cancel` | отмена фонового прогона | + команда `/stop` в соединение хода О, отмена фоновых заданий хода |
| `GET /chat/history/{session_id}` | сессия агента в базе службы | `GET /api/chat/history` О (чат = проект), только сообщения корневых задач ходов, формат `{role, content}` прежний (ADR-0011) |
| `/dialogs` | снимок клиента, источник истины списка чатов | оболочка проекта и кэш экрана; тексты сообщений — у О |
| `POST /documents/upload`, источники проекта | файл в хранилище службы | XLS/DOC — отказ (ADR-0026); оригинал → каталог О (§6); распознавание — служба |
| `GET /documents/{id}/file`, `/sources/{id}/file` | из хранилища службы | поток из `GET /api/files/{file_id}/content` О |
| `DELETE /documents/{id}` | удаление у себя | + `DELETE /api/files/{file_id}` О |
| файлы-результаты в `TextMessage.files` | `file_id` службы | `file_id` службы сохраняется; за ним — файл в каталоге О |

**Контрактные тесты C1.**
- C1.1 Перечень ручек, которыми пользуется `web/src` (статический разбор `fetch`/путей), совпадает
  со снимком; служба отдаёт их все (OpenAPI службы содержит каждую).
- C1.2 Реплей опорных записей (этап 1) через новую службу: поток событий после нормализации равен
  записи (F5 — тот же механизм).
- C1.3 `GET /chat/history/{session_id}` на подставном О: формат прежний, сообщения подзадач и
  уведомления отфильтрованы, чужой владелец — 404.
- C1.4 Загрузка XLS/DOC — отказ с прежним HTTP-кодом ошибки загрузки и понятным текстом.

## 2. Служба движка ↔ ouroboros: ход (C2)

### 2.1. Соединение
- `WS ws://ouroboros:<port>/ws`, одно на ход (ADR-0021).
- Заголовки рукопожатия: `X-Ouroboros-Owner-Id: <str(user.id)>`,
  `X-Ouroboros-Chat-Id: <project_id>`, `X-Trace-Id: <trace хода>`. `X-Ouroboros-Agent-Id` не
  передаётся (агент по умолчанию `main`, ADR-0002).
- Отказ личности — закрытие рукопожатия; служба закрывает ход событием `error` с текстом
  «ассистент недоступен» (без подробностей О на экран).

### 2.2. Входящий кадр (С → О)
```json
{"type": "chat", "content": "<реплика пользователя дословно>", "client_message_id": "<run_id>",
 "sender_session_id": "aifa"}
```
Запрещено: `attachment_ids`, `detached: true`, любые добавки к тексту (ADR-0025). Длина — предел
`OUROBOROS_MAX_INBOUND_MESSAGE_CHARS`; больше — служба отказывает до отправки.

### 2.3. Исходящие кадры (О → С) и что с ними делает служба

| Кадр О | Признак | Служба |
|---|---|---|
| `chat`, `role: user` | эхо, `client_message_id == run_id` | подтверждение доставки; на экран не идёт |
| `chat`, `assistant`, `is_progress: true` | прогресс («💬 …», «⏱️ …») | служебное событие в журнал; на экран не идёт (строка «размышляю» снята, ADR-0015) |
| `chat`, `assistant`, `is_progress: false`, `task_id == корень` | **финальный ответ** (ADR-0021) | `text_delta` (весь текст) + `text_segment_end`; сверка с каноническим текстом (ADR-0024); `done` |
| `chat`, `assistant`, `is_progress: false`, иной `task_id` или пустой | подзадача / уведомление | служебное событие в журнал |
| `typing` | действие | игнор |
| `heartbeat` | биение | продлевает срок соединения |
| `error` (`code`) | отказ транспорта | `message_too_long` и т. п. → `error` хода с понятным текстом |
| `confirmation_request` | не должен приходить (подтверждение выключено) | `error` хода + запись в журнал как нарушение конфигурации |
| `log`, `extension_lifecycle`, `photo` | не ожидаются | журнал |

### 2.4. Корень хода
`task_id` корня служба узнаёт из первого вызова инструмента хода (`root_task_id` пуст →
`task_id`), иначе — из первого непрогрессного кадра ассистента с непустым `task_id`.
Хранится в прогоне службы (`run.root_task_id`).

### 2.5. Как ответ и прогресс попадают в журнал хода для экрана
| Событие экрана | Кто пишет |
|---|---|
| `start`, `session_id`, `run_id` | служба при создании хода (как сейчас) |
| `tool_call` / `tool_output` | обработчик внутреннего API на каждый вызов инструмента `aifa-*` (имя для экрана — прежние названия инструментов AIFA; соответствие — в `aifa/contracts/tool_names.json`) |
| `plan_graph`, `node_run`, `plan`, `plan_step`, `typed_result`, `typed_error`, `analysis_card`, `file`, `clarify` | конвейер службы внутри `aifa_goal`/`aifa_move` — те же эмиттеры, что сейчас |
| `dynamic_plan`, `dynamic_move` | `LoopSession` внутри `aifa_move`/`aifa_finish` |
| `author_attempt` | `aifa_author_attempt` и `aifa_create_atom` |
| `text_delta`, `text_segment_end` | клиент хода по финальному кадру О |
| `usage` | служба — только свои модели; расход моделей О — открытый вопрос (§9 `ARCHITECTURE.md`) |
| `done`, `error`, `session_lost`, `interrupted` | клиент хода (финал, отказ, потеря соединения, «Стоп») |
| `thinking` | не пишется |

### 2.6. История
`GET /api/chat/history?limit=&before_ts=` с заголовками владельца и чата. Служба отбирает записи
пользователя с `client_message_id`, равным `run_id` своих ходов, и записи ассистента с тем же
`client_message_id` и `task_id`, равным корню хода.

### 2.7. Остановка и восстановление
- «Стоп»: `{"type":"command","cmd":"/stop"}` в соединение хода; ждём финального кадра или 30 с, затем
  `interrupted`.
- Обрыв: переподключение с теми же заголовками; если не удалось — опрос истории (§2.6) до
  крайнего срока; не нашли — `session_lost`.

**Контрактные тесты C2** (живой О в compose-профиле `contract` с подставным сервером модели,
отвечающим записанными решениями):
- C2.1 Рукопожатие без `X-Ouroboros-Owner-Id` закрывается; с ним — `scope.agent_id == main`.
- C2.2 Эхо приходит с `client_message_id == run_id`.
- C2.3 Финальный кадр корня несёт `task_id` и `transport.source_message_id == run_id`.
- C2.4 Ход с подзадачей: уведомление «Scheduled task» и ответ подзадачи не принимаются за финал.
- C2.5 Прогресс помечен `is_progress: true`.
- C2.6 История: записи хода находятся по `client_message_id`; записи чужого чата недоступны.
- C2.7 `/stop` останавливает корень и подзадачи хода.
- C2.8 Кадр с `attachment_ids` клиент хода не отправляет (F6 — во время исполнения).

## 3. Инструменты навыка `aifa-engine` (О → С) (C3)

### 3.0. Общий вызов
`plugin.py` переводит вызов в `POST {AIFA_ENGINE_URL}/internal/ouro/v1/<tool>`:
- заголовки: `Authorization: Bearer <AIFA_ENGINE_TOKEN>`, `X-Trace-Id` (`ctx.trace_id`),
  `X-Agent-Id` (инвариант 6 ouroboros — проставляет `aef_tracing.with_trace_header`/`with_agent_header`);
- тело: `{"ctx": {"owner_id", "agent_id", "chat_id", "task_id", "root_task_id", "task_depth",
  "run_id"}, "args": {...}}`, где `run_id` = `ctx.transport["source_message_id"]`;
- ответ службы — `text/plain`, первая строка — код, дальше — текст для модели. Плагин возвращает его
  без изменений. Сетевой сбой → `СБОЙ_СЛУЖБЫ: <кратко>; повтори вызов`.

**Привязка.** Служба находит прогон по `run_id` и проверяет: прогон её, активен, `owner_id` и
`chat_id` совпадают с прогоном. Нет — `ОТКАЗ чужой_ход`. Инструменты планировщика принимаются только
от корня (`task_depth == 0`), инструменты автора — только от подзадачи (`task_depth ≥ 1`) с
`root_task_id == run.root_task_id`.

**Коды первой строки.**

| Код | Значение |
|---|---|
| `ГОТОВО` | результат получен; дальше — содержимое |
| `ЖДИ job=<id>` | задание идёт фоном; вызови `aifa_wait` |
| `НУЖЕН_ЦИКЛ` | стандартный путь не справился; дальше — состояние цикла |
| `УТОЧНИ` | цели не хватает данных; дальше — вопрос и варианты для пользователя |
| `АВТОР job=<id>` | для атома нужен код; дальше — готовый текст задания подзадаче |
| `ЛИМИТ` | исчерпан предел цикла; принимается только `aifa_finish` |
| `ПРИНЯТО` | `aifa_finish` принят; дальше — канонический текст ответа |
| `ОТКАЗ <код>` | правило нарушено; дальше — причина в терминах навыка |
| `СБОЙ_СЛУЖБЫ` | служба недоступна (пишет плагин) |

Коды отказа: `чужой_ход`, `не_та_роль`, `нет_цикла`, `цикл_закрыт`, `неверные_аргументы`,
`повтор_тупика`, `нет_входов`, `не_dyn_тип`, `нет_единицы`, `ссылка_не_найдена`,
`файл_не_собран`, `лимит_попыток`, `лимит_атомов`, `задание_не_найдено`.

Все ответы формирует один модуль службы `ouro_view` (F3). Предел ответа — `result_limit=12000`.

### 3.1. Перечень

| Инструмент | Аргументы | Ответ | Предел, фон | Правила, которые держит код |
|---|---|---|---|---|
| `aifa_goal` | — | `ГОТОВО` (таблица результатов как «Полученные артефакты»: id, тип, концепт, период, кратко ≤ 300; файлы; ссылки) · `УТОЧНИ` · `НУЖЕН_ЦИКЛ` (+ состояние цикла) · `ЖДИ` | 240 с, затем фон; повторный вызов в том же ходе возвращает тот же итог | цель = исходное сообщение прогона, модель её не задаёт; `parse_message` → `execute_routed_goal(allow_dynamic=False)`; гейты раскрывает `GraphPlanner`; готовое не пересчитывается (`Case`); «показателя нет в отчёте» — результат, а не цикл |

| `aifa_author_brief` | `job_id` | контракт атома (`name`, `purpose`, `requires`, `output_type`, `output_schema`), формы входов, сокращённый реальный вход, прошлый код и ошибка при починке, остаток попыток, правила комнаты | синхронно | только подзадача этого хода; вход — как сейчас у автора (ADR-0025) |

Бюджет описаний: черновые схемы всех восьми — 3440 знаков JSON (238 / 302 / 209 / 1359 / 483 / 241 /
320 / 288), считая так же, как `task_graph.py`. Цель ≤ 7000, предел 8000 (F4).

**Контрактные тесты C3** (служба в процессе, HTTP-клиент тестов вместо плагина):
- C3.0 Без токена — 401; чужой `run_id`/владелец/чат — `ОТКАЗ чужой_ход`; планировщик из подзадачи и
  автор из корня — `ОТКАЗ не_та_роль`.
- C3.1 По тесту на **каждую** строку правил раздела 8 плана 34 и на каждую строку столбца «Правила»
  выше (карта правило → тест — F8).
- C3.2 Грамматика ответа: первая строка — один из кодов; размер ≤ `result_limit`.
- C3.3 `aifa_goal` идемпотентен в пределах хода.
- C3.4 Длинный вызов: `ЖДИ` → `aifa_wait` → итог; отмена хода прерывает ожидание.
- C3.5 Снимок схем инструментов (имена, аргументы, обязательные поля) совпадает с
  `aifa/contracts/tools.snapshot.json` (F4).

## 4. Подзадача-автор (C4)

**Поток** (этап 4; до него автор работает внутри службы, ADR-0029):
1. `aifa_move` с атомом-кодом → служба проверяет контракт (`check_request`), заводит задание
   автора и отвечает `АВТОР job=<id>` с готовым текстом задания:
   «Задание автора AIFA job=<id>. Прочитай навык aifa-atom-author и выполни задание.»
2. Планировщик вызывает `schedule_task(description=<текст>)` (контекст не передаёт) и ждёт
   `aifa_wait(job_id=<id>)`.
3. Подзадача (та же область видимости и сессия Workstation, ADR-0008): `skill_read` навыка →
   `aifa_author_brief(job_id)` → пишет код и отлаживает его в своей сессии W (`file_write` пример
   входа из брифа, `code_exec`) → после каждого прогона `aifa_author_attempt` → `aifa_create_atom`.
4. Служба проверяет код в разовой комнате на настоящих входах `Case`; успех закрывает задание,
   `aifa_wait` планировщика возвращает `ГОТОВО`; неудача — `ОТКАЗ` автору с ошибкой.
5. Три неудачные проверки или срок задания (600 с) — задание закрыто с отказом; планировщик решает
   (переописать атом, сменить путь, `give_up`). Висящую подзадачу планировщик снимает `cancel_task`.

**Что автор не может:** видеть документ и `Case` целиком; регистрировать атом без проверки службы;
работать по чужому заданию; вызывать инструменты планировщика.

**Контрактные тесты C4** (живой О + подставная модель):
- C4.1 Подзадача видит ту же область (чат, агент) и тот же `root_task_id`; инструменты автора от неё
  принимаются.
- C4.2 Подзадача видит ту же сессию Workstation, что корень (файл, записанный корнем, читается).
- C4.3 Четвёртая проверка — `ОТКАЗ лимит_попыток`; задание чужого хода — `ОТКАЗ задание_не_найдено`.
- C4.4 Событие `author_attempt` появляется в журнале хода на каждый отчёт и каждую проверку.
- C4.5 При `OUROBOROS_WORKER_SLOTS=1` проверка конфигурации (F9) красная — не тест поведения, а
  запрет конфигурации.

## 5. Служба движка ↔ Workstation контура (C5)

- API как у ouroboros: `POST /v1/sessions` (`X-Session-Id: aifa-eph-<16 hex>`, `X-Session-Create-Secret`,
  `X-Workstation-Protocol: 1`, тело `{"idleTimeoutSec": 300}`) → `token`; `POST /v1/sessions/{id}/exec`
  (`python3 -I -c <_room_entry>`, `cwd=/workspace`, `env: {}`, `timeoutSec: 60`, вход — stdin base64);
  `files:list` / `files:download` по `out/`; `:terminate` в `finally`.

## 6. Служба движка ↔ каталог файлов ouroboros (C6)

- Загрузка: `POST /api/files` (multipart: `file`, необязательный `folder_id`), заголовки
  `X-Ouroboros-Owner-Id` (агент — по умолчанию `main`), ответ `FileInfo`
  (`id, name, folder_id, mime, size, status, created_at, updated_at, expires_at, url`).
- Чтение: `GET /api/files/{id}/content` (поток); метаданные `GET /api/files/{id}`; удаление
  `DELETE /api/files/{id}`.
- Служба хранит `doc_id ↔ file_id` и `sha256`; распознавание читает байты через каталог.
- Папки каталога не используются (проект — понятие службы).

**Контрактные тесты C6.**
- C6.1 Круговая поездка: загрузить → прочитать → `sha256` совпадает.
- C6.2 Другой владелец — 404 на чтение чужого файла.
- C6.3 XLS/DOC отклоняет служба до обращения к каталогу; форматы из списка каталога проходят.
- C6.4 Удаление документа в службе удаляет файл в каталоге.
