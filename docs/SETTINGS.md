# Настройки Ouroboros

Публичная инструкция по переменным окружения, которыми управляется работа Ouroboros: что означает каждая переменная, как её задать, какой минимальный набор нужен для разработки и для развёртывания, и как подключаются внешние серверы MCP и другие агенты (A2A).

---

## 1. Общие сведения

### 1.1 Откуда берутся настройки

Настройки задаются двумя источниками, которые объединяются при загрузке:

1. **Переменные окружения** — основной источник.
2. **Секретные файлы** — каталог, указанный в `OUROBOROS_SECRETS_DIR`. В нём один файл на один ключ, имя файла — имя ключа (регистр букв не важен, например `dialogs_bot_token` соответствует `DIALOGS_BOT_TOKEN`), значение — содержимое файла. Секретные файлы **перекрывают** переменные окружения для тех же ключей; переменные заполняют лишь то, что не задано файлом.

**Пример: секреты из Vault (шаг за шагом).** Vault-сайдкар (или любой другой способ) монтирует секреты в каталог как один файл на ключ; приложение читает этот каталог при старте.

1. Укажите приложению каталог секретов:
   ```bash
   export OUROBOROS_SECRETS_DIR=/vault/secrets
   ```
2. Смонтируйте секреты в этот каталог, по файлу на ключ. Имя файла — имя ключа, содержимое — значение:
   ```
   /vault/secrets/ouroboros_runtime_db_url   # коннект к БД (DSN), например:
                                             # postgresql+psycopg://user:pass@pg1:5432/ouroboros?sslmode=require
   /vault/secrets/dialogs_bot_token          # ключ бота диалогов
   /vault/secrets/cloudru_foundation_models_api_key   # ключ поставщика моделей
   ```
3. Запустите приложение. При старте оно:
   - ждёт появления каталога и файлов до `OUROBOROS_SECRETS_WAIT_SEC` (по умолчанию 30 секунд; `0` — не ждать), опрашивая каталог каждые `OUROBOROS_SECRETS_WAIT_INTERVAL_SEC` (0.5 с) — Vault-сайдкары часто монтируют файлы по одному;
   - читает каждый файл и **перетирает** им переменную окружения с тем же именем: файл всегда побеждает env, а env заполняет лишь то, для чего файла нет.

Так можно передавать не только секреты: файл с любым ключом (`dialogs_grpc_endpoint` и т. п.) действует так же.

Правила имён ключей:

- Все ключи пишутся в верхнем регистре (`UPPER_SNAKE`), например `OUROBOROS_MODEL`.
- Неизвестные системе ключи допускаются только с одним из разрешённых префиксов: `GIGACHAT_`, `CLOUDRU_`, `SELFHOSTED_`, `DIALOGS_`, `OUROBOROS_`, `MCP_`, `A2A_`, `TOTAL_`, `AEF_`, `TOOL_`. Прочие имена отвергаются при загрузке.
- Ключи, изъятые из обращения (префиксы `HEIMDALL_`, `PULSE_PEOPLE_`, `NAVIGATOR_BI_`, `ASSISTANT_ASSIGNMENT_` и ряд точных имён, перечень в `ouroboros/storage/settings/retired.py`), полностью игнорируются: задавать их бесполезно.

Типы значений:

- **Флаги** (включено/выключено): истина — `1`, `true`, `yes`, `on`; ложь — `0`, `false`, `no`, `off`. Регистр букв не важен.
- **Секреты** (ключи доступа, пароли, маркеры): никогда не раскрываются в журналах. Рекомендуется передавать их секретными файлами, а не переменными окружения. В таблицах справочника такие переменные помечены словом **«секрет»** в колонке «По умолчанию» — это секретная информация, задавайте её через секретные файлы (см. пример выше).
- **Списки** (`MCP_SERVERS`, `A2A_REMOTE_AGENTS`, `OUROBOROS_SANDBOX_DENY_PATHS`): значение — JSON-массив или список; повреждённые элементы отбрасываются целиком, не прерывая загрузку.

### 1.2 Режим работы: `OUROBOROS_ENV`

Режим задаётся переменной `OUROBOROS_ENV` и принимает ровно два значения:

| Значение | Смысл |
|----------|-------|
| `production` | Режим развёртывания. **Значение по умолчанию**: если переменная не задана или задана чем-то иным, режим считается `production`. |
| `development` | Локальная разработка. Включает ключи и возможности, недоступные в `production`. |

Что меняется в режиме `production`:

- из секретных файлов и произвольных ключей не читаются префиксы `OPENAI_COMPATIBLE_`, `CLOUDRU_`, `LOCAL_MODEL_`, `USE_LOCAL_` (сами объявленные поля схемы при этом продолжают читаться из переменных окружения).

Базу данных состояния и корзину объектного хранилища (`OUROBOROS_S3_BUCKET`) процесс требует в любом окружении, а не только в `production`: без базы он отказывает при запуске первым, без корзины — сразу после этого, до проверок многопользовательского режима.

## 2. Полный справочник переменных

### 2.1 Режим, сервер, журналирование

| Переменная | По умолчанию | Назначение |
|------------|--------------|------------|
| `OUROBOROS_ENV` | `production` | Режим работы: `production` или `development` (см. 1.2). |
| `OUROBOROS_SERVER_HOST` | `127.0.0.1` | Адрес прослушивания основного HTTP-сервера. В образе контейнера по умолчанию `0.0.0.0`. |
| `OUROBOROS_SERVER_PORT` | `8080` | Порт основного HTTP-сервера. Ключ загрузки, в схему `AppSettings` не входит. |
| `OUROBOROS_LOG_LEVEL` | `INFO` | Уровень детализации журнала (названия уровней стандартные). |
| `OUROBOROS_LOG_FORMAT` | `json` | Формат журнала: `json` или `text`. Любое иное значение воспринимается как `json`. |
| `OUROBOROS_LOG_SINK` | `stdout` | Куда пишется журнал: `stdout`, `file` или `both`. Любое иное значение воспринимается как `stdout`. При недоступной директории файл-приёмник откатывается на `stdout`. |
| `OUROBOROS_LOG_DIR` | `/var/log/app` | Директория файла журнала (`app.log`) для `file`/`both`; читается сайдкаром fluent-bit. |
| `OUROBOROS_LOG_ROTATION` | `size` | Ротация файла журнала: `size` (по `OUROBOROS_LOG_FILE_MAX_BYTES`) или `time` (ежедневно в полночь UTC). Любое иное значение воспринимается как `size`. **`time` не ограничивает файл по размеру** — между полуночами он растёт без предела, поэтому для маленького тома предпочтительнее `size`. |
| `OUROBOROS_LOG_FILE_MAX_BYTES` | `52428800` | Порог ротации по размеру (байты); `0` отключает ротацию. Неразбираемое значение (например `50MB`) даёт дефолт, не `0`. Игнорируется при `OUROBOROS_LOG_ROTATION=time`. |
| `OUROBOROS_LOG_FILE_BACKUP_COUNT` | `5` | Сколько ротированных файлов хранить: `app.log.1`… при `size`, `app.log.2026-09-01` при `time`. При `size` значение `0` поднимается до `1` (с нулём stdlib не усекает файл); при `time` `0` сохраняет штатный смысл «хранить все». Неразбираемое значение даёт дефолт. |
| `OUROBOROS_LOG_ERROR_FILE_ENABLED` | `false` | Дополнительно писать копию записей уровня ERROR+ в `error.log` рядом с `app.log`. `app.log` при этом остаётся полным — fluent-bit читает только его. |
| `OUROBOROS_LOG_TRACEBACK` | `false` | Включать полный стек ошибки в записи журнала. |
| `OUROBOROS_TIMEZONE` | `Europe/Moscow` | Часовой пояс (контекст, расписания планировщика). |
| `OUROBOROS_LOCALE` | `ru-RU` | Языковой стандарт для контекста агента. |
| `OUROBOROS_POLIGON` | `DEV` | Название полигона (`DEV`, `PROM`, `IFT` и т. п.). Выбирает, из какого источника строятся списки внешних серверов MCP и удалённых агентов A2A (разделы 5 и 6). Проверка значения отсутствует. |

### 2.2 Пути и секретные файлы

Эти ключи читаются при загрузке вне схемы `AppSettings` и определяют размещение данных.

| Переменная | По умолчанию | Назначение |
|------------|--------------|------------|
| `OUROBOROS_APP_ROOT` | `~/Ouroboros` | Корень приложения. |
| `OUROBOROS_DATA_DIR` | `{корень}/data` | Каталог данных: временные файлы, блокировки, рабочие каталоги задач. В `production` — доступный для записи том. |
| `OUROBOROS_REPO_DIR` | `{корень}/repo` | Каталог репозитория: инструкции, справочники, каталог навыков `skills`. |
| `OUROBOROS_DRIVE_ROOT` | пусто | Корень данных исполняемой среды; по умолчанию — каталог данных. |
| `OUROBOROS_SECRETS_DIR` | пусто | Каталог секретных файлов (по файлу на ключ). |
| `OUROBOROS_SECRETS_WAIT_SEC` | `30` | Сколько ждать появления каталога секретов и его файлов при загрузке; `0` — не ждать. |
| `OUROBOROS_SECRETS_WAIT_INTERVAL_SEC` | `0.5` | Частота опроса каталога секретов. |
| `OUROBOROS_SETTINGS_PATH`, `OUROBOROS_PID_FILE`, `OUROBOROS_PORT_FILE`, `OUROBOROS_AGENT_PYTHON` | — | Служебные пути для локального запуска; в обычной работе не задаются. |

### 2.3 Модели

| Переменная | По умолчанию | Назначение |
|------------|--------------|------------|
| `OUROBOROS_MODEL` | `gigachat-b2bank::GigaChat-Pro` | Основная модель. Формат: `поставщик::модель` (например `cloudru::zai-org/GLM-4.7`). |
| `OUROBOROS_MODEL_LIGHT` | `gigachat-b2bank::GigaChat` | Лёгкая модель: служебные проверки, проверки безопасности. |
| `OUROBOROS_MODEL_FALLBACK` | `gigachat-b2bank::GigaChat` | Запасная модель. |
| `OUROBOROS_MODEL_BY_SKILL` | пусто | Модель (и уровень размышлений) подзадачи по навыку из её задания «Навык: <id>.»: `distribution:aifa-plan-author=cloudru::zai-org/GLM-5.2@high, <навык>=<модель>`, через запятую. Только окружение. Корень и подзадачи без записи идут на `OUROBOROS_MODEL`. |
| `OUROBOROS_MODEL_VISION` | пусто | Модель для анализа изображений (инструмент `vlm_query`). Пусто — используется основная модель. |
| `OUROBOROS_MODEL_CONTEXT_TOKENS` | `200000` | Объём контекста модели в токенах. |
| `OUROBOROS_CHAT_SUMMARY_MAX_TOKENS` | `32768` | Предельный объём сводки переписки (объединение истории). |
| `OUROBOROS_CONTEXT_COMPACTION_THRESHOLD_TOKENS` | `25000` | Порог объединения переписки по числу токенов. |
| `OUROBOROS_CONTEXT_COMPACTION_THRESHOLD_MESSAGES` | `100` | Порог объединения переписки по числу сообщений. |
| `OUROBOROS_EMERGENCY_COMPACTION_CHARS` | `0` | Аварийное сжатие контекста по числу знаков; `0` — по доле контекста (75 %). |
| `OUROBOROS_SYSTEM_PROMPT_TOKENS` | `0` | Верхний предел системной инструкции; `0` — 55 % контекста модели. |
| `OUROBOROS_EFFORT_TASK` | `medium` | Уровень усилий задачи: `none`, `low`, `medium`, `high`. Неверное значение отбрасывается при загрузке. |

При заданном ключе Cloud.ru и отсутствии учётных данных GigaChat наборы моделей заполняются автоматически значениями Cloud.ru. Когда задан `SELFHOSTED_LLM_BASE_URL`, модели без префикса поставщика направляются на локально размещённую службу.

Отбор идёт на каждый запрос, поэтому раунды одного диалога могут попасть на разные версии — это безопасно, пока рантайм не переигрывает `tools_state_id`. |

### 2.5 Задачи и пределы исполнения

| Переменная | По умолчанию | Назначение |
|------------|--------------|------------|
| `OUROBOROS_SOFT_TIMEOUT_SEC` | `600` | Предупреждающий предел задачи. |
| `OUROBOROS_HARD_TIMEOUT_SEC` | `1800` | Жёсткий предел задачи: при достижении задача прерывается. |
| `OUROBOROS_DRAIN_TIMEOUT_SEC` | `20` | Сколько уходящий инстанс ждёт свои выполняющиеся тела, прежде чем всё равно вернуть их записи в очередь. Должен быть меньше grace-периода оркестратора при остановке контейнера. |
| `OUROBOROS_TOOL_TIMEOUT_SEC` | `600` | Наименьший предел времени на вызов инструмента (действует наибольшее из этого значения и собственного предела инструмента). |
| `OUROBOROS_MAX_ROUNDS` | `200` | Наибольшее число кругов цикла агента. |
| `OUROBOROS_CHECKPOINT_PROGRESS_ENABLED` | `false` | Периодически рассылать промежуточные сводки хода задачи. |
| `OUROBOROS_DURABLE_JOBS_ENABLED` | `false` | Разрешить приём новых отделённых задач (`/new`, `detached=true`). Маршруты управления задачами browser ingress доступны независимо от флага. |
| `OUROBOROS_MAX_ACTIVE_ROOT_JOBS_PER_OWNER` | `5` | Порог приёма новых detached: считаются все незавершённые корневые задачи владельца. Обычные задачи принимаются в очередь независимо от порога. Положительное целое. |
| `OUROBOROS_MAX_RUNNING_ROOT_JOBS_PER_OWNER` | `3` | Общий предел одновременно выполняемых корневых задач владельца; не больше активного предела. |
| `OUROBOROS_MAX_INBOUND_MESSAGE_CHARS` | `50000` | Положительное целое: предел длины нового входящего текста в знаках, включая аргумент команды. Dialogs, Browser, A2A и Skill Bridge отклоняют превышение до сохранения, обработки вложений и очереди. Одинаковое значение во всех процессах внешних транспортов. Сохранённая история и внутренние сообщения повторно не проверяются. |
| `OUROBOROS_REASONING_PROGRESS_ENABLED` | `true` | Показывать ли собственный текст модели, который она пишет рядом с вызовами инструментов. Значение экземпляра: владелец меняет его для себя командой `/reasoning on` или `/reasoning off` в своём чате либо через `PUT /api/owner-settings/{agent_id}/OUROBOROS_REASONING_PROGRESS_ENABLED`, и его выбор берёт верх начиная со следующей задачи — уже идущая задача получила своё значение при запуске и доживает с ним. **Планировщик.** Три ручки диспетча расписаний — компромисс между задержкой доставки и нагрузкой на

Если в адресе (основном или запасном) не заданы `connect_timeout` и `tcp_user_timeout`, подключение получает 5 с и 15000 мс, чтобы молчащая база не держала цикл агента дольше порога liveness; значения из адреса важнее. |
| `OUROBOROS_RUNTIME_DB_URL_1` … `_N` | не заданы | Запасные адреса той же базы для отказоустойчивости (последовательные, начиная с `_1`; при заданном `_1` основной ключ не используется). |

Значение должно совпадать у всех процессов развёртывания. Учётные данные исходящих вызовов этим ключом не шифруются — для них `OUROBOROS_CREDENTIALS_ENCRYPTION_KEY`. |
| `OUROBOROS_CREDENTIALS_ENCRYPTION_KEY` | **секрет** | Ключ шифрования учётных данных исходящих вызовов: ровно 64 байта в кодировке base64 (`openssl rand -base64 64 \| tr -d '\n'`; пробелы и переводы строк внутри значения игнорируются). Им шифром AES-256-SIV (RFC 5297, ключ 512 бит) шифруются значения контекста безопасности (`security_contexts`) и личные токены MCP (`mcp_user_tokens`) и A2A (`a2a_user_tokens`), из него же выводится ключ хэндлов задач A2A. **Обязателен** для сервера, тира браузерного транспорта и тира агента при любых `MCP_ENABLED`, `A2A_EGRESS_ENABLED` и `OUROBOROS_MULTIUSER`: без правильного ключа они не запускаются, и ошибка называет настройку, но не ключ; ключ другой длины, в том числе 32-байтный ключ шифрования сообщений, не принимается. Значение должно совпадать у всех процессов транспорта, агента и реестра конфигурации (разделы 5 и 6.2) — раскатывайте их вместе. Смена ключа делает недействительными все открытые хэндлы задач A2A, а значения, сохранённые под прежним ключом, не расшифровываются: вызов с такой строкой отклоняется, и личный токен не заменяется статическим. Поэтому после смены ключа удалите строки `security_contexts`, `mcp_user_tokens` и `a2a_user_tokens`: контексты соберутся при следующем подключении браузера, личные токены владельцы запишут заново. |

В адресах базы знаки, требующие кодирования, передаются в URL-кодировке (например, пароль `p%a` — как `p%25a`). К каждому адресу PostgreSQL добавляется требование подключения к актуальному ведущему узлу.

Лимиты вложений задаются через env на уровне инстанса, недоступны через
`/api/owner-settings` и применяются после перезапуска. Размеры — положительные целые байты:

| Переменная | По умолчанию | Назначение |
|------------|--------------|------------|
| `OUROBOROS_ATTACHMENT_DOCUMENT_MAX_BYTES` | `52428800` (`50 * 1024 * 1024`, 50 MiB) | Максимальный размер документа при загрузке, чтении и отправке. |
| `OUROBOROS_ATTACHMENT_IMAGE_MAX_BYTES` | `20971520` (`20 * 1024 * 1024`, 20 MiB) | Отдельный максимальный размер изображения, включая vision/VLM и отправку. |

До определения MIME browser принимает multipart body до `max(document_limit, image_limit) + 65536`
байт (64 KiB overhead), затем применяет лимит соответствующего формата. Согласуйте
`client_max_body_size` внешнего nginx с этим размером.

Таймауты обработки вложений задаются на уровне инстанса, в целых секундах:

| Переменная | По умолчанию | Назначение |
|------------|--------------|------------|
| `OUROBOROS_ATTACHMENT_SLOT_TIMEOUT_SEC` | `45` | Ожидание свободного парсера. `0` — сразу отказать при занятости. |
| `OUROBOROS_ATTACHMENT_PARSE_TIMEOUT_SEC` | `45` | Полный бюджет разбора после получения слота, включая запуск дочернего процесса. |
| `OUROBOROS_ATTACHMENT_PARSER_CPU_SEC` | `30` | Лимит CPU-времени дочернего процесса. |
| `OUROBOROS_ATTACHMENT_PARSER_JOIN_TIMEOUT_SEC` | `1` | Ожидание на каждом этапе завершения: обычный выход, terminate, kill. Минимум 1 секунда. |
| `OUROBOROS_ATTACHMENT_READ_TIMEOUT_SEC` | `120` | Бюджет `attachment_read` на получение файла и остальные операции вне парсера. |

Значения должны быть целыми и положительными; ноль разрешён только для ожидания слота.
Таймаут `attachment_read` равен `OUROBOROS_ATTACHMENT_READ_TIMEOUT_SEC` плюс бюджет парсера
`ожидание + разбор + 3 × завершение + 1`. Для `send_file` тот же бюджет прибавляется к
его обычным 360 секундам на получение и передачу файла.
`OUROBOROS_ATTACHMENT_READ_TIMEOUT_SEC` влияет только на чтение.
Исполнитель берёт максимум полученного таймаута инструмента и `OUROBOROS_TOOL_TIMEOUT_SEC`.
Для браузерных загрузок согласуйте также `proxy_read_timeout` в nginx: он настраивается
отдельно, рекомендуемое значение — 120 секунд.

### 2.11 Входы и взаимодействие

| Переменная | По умолчанию | Назначение |
|------------|--------------|------------|
| `BROWSER_INGRESS_ENABLED` | `false` | Включить браузерный вход: общее состояние, переписка, загрузка и выгрузка файлов, обмен по WebSocket. Проверка подлинности ожидается на внешнем шлюзе. |
| `OUROBOROS_MULTIUSER` | `false` | Объявить, что этот экземпляр обслуживает нескольких владельцев. Один флаг на весь набор поведений, которые держатся только вместе: владелец берётся из заголовка `X-Ouroboros-Owner-Id` браузерного входа, а не из настроенной константы, разговор — из `X-Ouroboros-Chat-Id`, а агент — из `X-Ouroboros-Agent-Id`; хранилище ключуется по владельцу; каталог инструментов строится один раз за процесс и не обновляется на пути задачи; команда `/restart` отклоняется — перезапуск процесса остановил бы работу остальных владельцев. Включать только если порт закрыт обратным прокси, который проверяет подлинность вызывающего и перезаписывает эти заголовки поверх всего, что прислал клиент: **включение на напрямую доступном порту позволяет любому вызывающему назвать себя любым владельцем**. Разрешение отказное — отсутствующий или пустой заголовок, а также чат, который политика идентификаторов считает служебным (отрицательный диапазон: мост навыков и вывод A2A), закрывает рукопожатие и отвечает `403` на `/api/chat/history`, отката к константе нет. Заголовок агента не обязателен: пустой означает агента владельца на зарезервированном id `main`, а непустой разрешается запросом к реестру, предикат которого называет уже установленного владельца, поэтому чужой агент и выключенный агент получают `403`, а не подмену на `main`. Зарезервированный id — это имя значения по умолчанию, а не привилегия: владелец выключает его тем же `DELETE /api/agents/{agent_id}`, что и любого другого, и после этого пустой заголовок получает те же `403` — выключенного агента не оживляют только потому, что его никто не назвал. Заголовок чата не разбирается: допускается любая непустая строка не длиннее 256 символов, у которой обрезаются только окружающие пробелы, поэтому два написания одного числа — это два разных разговора. Ограничение длины стоит потому, что значение входит в два btree-индекса, и без него запись падала бы в хранилище, а не на границе, которая её пропустила. Пока режим включён, расширения не могут отправлять сообщения через `send_message` (у них нет автора), а строки журнала и события жизненного цикла расширений не рассылаются в браузер — они не несут владельца. При старте настройка проверяется целиком и процесс **отказывается запускаться**, называя найденное, причину и что менять: включённый `A2A_ENABLED` (входящий A2A выдаёт каждому вызывающему настроенного владельца), настроенный `DIALOGS_GRPC_ENDPOINT` вместе с токеном бота (транспорт Dialogs строит скоуп для каждого приходящего чата из конфигурации экземпляра, без участия сообщения, так что любой написавший боту сохранялся бы под настроенным владельцем; отказ привязан к режиму — при выключенном `OUROBOROS_MULTIUSER` поведение Dialogs не меняется). Дерево навыков не маскируется и не вызывает отказ запуска: общий `SkillSurface` скрывает `script`, `tool` и `extension`, а прочие типы остаются документацией. Для каждой задачи оставшаяся поверхность дополнительно сужается allowlist `OUROBOROS_USER_ENABLED_SKILL_IDS` владельца и агента; отсутствие берёт instance-значение (по умолчанию `[]`), а явное `[]`, повреждённое значение или ошибка чтения запрещают все навыки этой задаче. MCP-подключения общие для экземпляра и используют его credentials, но доступный поднабор серверов выбирается для каждого агента через `OUROBOROS_USER_ENABLED_MCP_IDS` в `/api/owner-settings`. Исходящий A2A в режиме разрешён; отклоняются включённый MCP-сервер или (при `A2A_EGRESS_ENABLED=true`) A2A-агент по локальному для экземпляра адресу и включённая запись `user_headers` любого из двух списков, передающая имя, не объявленное в `security_config/auth/header_collector.yaml`. Ни один вид авторизации не запрещён (разделы 5 и 6.2). |
| `OUROBOROS_SETTINGS_CACHE_BACKEND` | `none` | Кэш перед чтением переопределений владельца — десяти ключей, которые владелец задаёт своему агенту через `/api/owner-settings` (уровень усилий, язык, часовой пояс, выключатель уплотнения памяти, выключатель показа размышлений, три выбора модели, выбор MCP-серверов и выбор навыков задачи); прочие переменные читаются только из окружения. `none` — читать базу при каждом обращении. `inmemory` — кэш в памяти процесса: допустим лишь там, где пишущий и читающие — один процесс, поэтому каждый компонентный тир многопользовательского режима **отказывается запускаться** с этим значением. `redis` — общий кэш по адресу `OUROBOROS_REDIS_URL`, который пишущая сторона сбрасывает на каждую запись и очистку; недоступный Redis на чтении означает промах и обращение к базе, а неудачный сброс — ошибку запроса. Значение должно совпадать у всех процессов флота: расхождение ничем не обнаруживается, читающие держат устаревшее значение целое окно. |
| `OUROBOROS_SETTINGS_CACHE_TTL_SEC` | `300` | Срок жизни записи кэша. Истекает всегда: таблицу переопределений пишут также миграции и сопровождение, и до них сброс не доходит. |
| `OUROBOROS_BROKER_BACKEND` | `inprocess` | Брокер служебной шины: `inprocess`, `redis` или `kafka`. Одно значение выбирает бэкенд сразу для шлюза сообщений, событий агента и событий фоновой памяти — развести их по разным бэкендам нельзя. `redis` требует `OUROBOROS_REDIS_URL`; `kafka` требует ключей `OUROBOROS_KAFKA_*` и тем, которые создала инфраструктура кластера: тир, собирающий брокерный шов, при старте только описывает подключение, не обращаясь к брокеру, а при отказе останавливается до открытия хранилища. Компонентный тир многопользовательского режима **отказывается запускаться** с `inprocess`: очередь в памяти процесса разводит пишущего и читающего по разным процессам; `ouroboros-server` собирает внутрипроцессный бэкенд напрямую и этот ключ не читает. Любое другое значение отклоняется при загрузке настроек, и отката к внутрипроцессному бэкенду не бывает. Значение должно совпадать у всех процессов флота: между процессами оно не сравнивается, и расхождение ничем не обнаруживается. |
| `OUROBOROS_REDIS_URL` | пусто | Адрес Redis для общего кэша и служебной шины многопользовательского режима; содержит учётные данные — рекомендуется задавать секретным файлом. Поддерживается Sentinel: `sentinel://host:26379?service_name=<имя ведущего>`. |
| `OUROBOROS_REDIS_PREFIX` | `ouroboros` | Префикс ключей в Redis. Два развёртывания на одном Redis должны различаться этим значением; процессы одного развёртывания — совпадать. |
| `OUROBOROS_KAFKA_BOOTSTRAP_SERVERS` | пусто | Адреса брокеров Kafka через запятую, каждый в виде `host:port`; адрес IPv6 пишется в квадратных скобках, `[адрес]:port`, а запись без порта клиент читает как адрес на порту 9092. Эта и все следующие переменные `OUROBOROS_KAFKA_*` читаются только при выборе брокера Kafka. Подключение отклоняет только то, что нельзя превратить в параметры клиента: пустой список адресов и версию протокола, которая пуста или записана не в виде `MAJOR.MINOR`. Отказ останавливает процесс до построения любого клиента и называет ключи, но не адреса и не учётные данные; пустой список отклоняется с указанием и этого ключа, и `OUROBOROS_BROKER_BACKEND`. Прочие ошибки подключения — запись адреса, учётные данные не под тем протоколом, нечитаемый сертификат, префикс, который Kafka не принимает, — старт не останавливают и проявляются в журнале библиотеки при первом подключении. |
| `OUROBOROS_KAFKA_TOPIC_PREFIX` | `ouroboros` | Префикс имён тем и групп потребителей: `<префикс>.<тема>` и `<префикс>.<тема>.<группа>`. Kafka принимает в именах тем только ASCII-буквы, цифры, `.`, `_` и `-` и не длиннее 249 символов; префикс, который это нарушает, старт не останавливает — отказ приходит от кластера при первом обращении к теме. Должен совпадать у всех процессов одного развёртывания и различаться у развёртываний на одном кластере: группы Kafka общие для всего кластера, и два развёртывания с одним префиксом делили бы одну очередь. Различаться префиксы должны и после замены `.` на `_`: брокер считает имена тем, отличающиеся только этими символами, совпадающими, и второй такой набор тем создать не даст (`fleet_a` и `fleet.a` на одном кластере несовместимы). Проще всего разделять слова префикса только `-`. |
| `OUROBOROS_KAFKA_SECURITY_PROTOCOL` | `PLAINTEXT` | `PLAINTEXT`, `SSL`, `SASL_PLAINTEXT` или `SASL_SSL`. Имя пользователя и пароль передаются только под SASL-протоколами, пути TLS читаются только под `SSL` и `SASL_SSL`; значение, которое протокол не использует, не отклоняется, а недостающее проявляется отказом брокера при первом подключении. Имя хоста в сертификате проверяется всегда. |
| `OUROBOROS_KAFKA_SASL_MECHANISM` | `PLAIN` | `PLAIN`, `SCRAM-SHA-256` или `SCRAM-SHA-512`; читается только под SASL-протоколом. |
| `OUROBOROS_KAFKA_SASL_USERNAME` | пусто | Имя пользователя SASL. |
| `OUROBOROS_KAFKA_SASL_PASSWORD` | пусто | **Секрет.** Пароль SASL. Не попадает ни в отказы, ни в журнал: логгеры библиотеки `kafka` никогда не пишут ниже INFO, какой бы уровень ни был задан приложению. |
| `OUROBOROS_KAFKA_SSL_CA_PATH` | пусто | Путь к файлу удостоверяющего центра; файл читает библиотека при первом подключении, и нечитаемый путь проявляется там. |
| `OUROBOROS_KAFKA_SSL_CERT_PATH` | пусто | Путь к клиентскому сертификату; задаётся вместе с `OUROBOROS_KAFKA_SSL_KEY_PATH`. |
| `OUROBOROS_KAFKA_SSL_KEY_PATH` | пусто | Путь к ключу клиентского сертификата; задаётся вместе с `OUROBOROS_KAFKA_SSL_CERT_PATH`. |
| `OUROBOROS_KAFKA_API_VERSION` | пусто | Версия протокола брокера в виде `MAJOR.MINOR` (для 3.7.1 пишется `3.7`). Обязательна: клиент никогда не опрашивает брокер о версии, поэтому процесс собирается без доступного брокера. Пустое значение и значение не в виде `MAJOR.MINOR` отклоняются при старте; версия, которую брокер не поддерживает, проявляется отказами запросов. |
| `OUROBOROS_KAFKA_MAX_MESSAGE_BYTES` | `33554432` (32 МиБ) | Потолок размера сообщения: предел запроса каждого производителя и предел выборки каждого потребителя; положительный. Запись больше потолка производитель отклоняет сам, ошибкой библиотеки `MessageSizeTooLargeError`, до отправки и без усечения. `max.message.bytes` каждой темы, который задаёт инфраструктура кластера, должен вмещать потолок: тема с меньшим пределом отклоняет на брокере запись, прошедшую производителя, той же ошибкой и ничего не дописывает. Должен совпадать у всего флота; между процессами он не сравнивается. Встроенная фотография, чьё закодированное сообщение не помещается, отклоняется, поэтому `OUROBOROS_ATTACHMENT_IMAGE_MAX_BYTES` выше примерно трёх четвертей потолка пропускает фотографии, которые затем будут отклонены. |
| `MCP_ENABLED` | `false` | Общий выключатель подключения внешних MCP-серверов. |
| `MCP_TOOL_TIMEOUT_SEC` | `60` | Предел времени на вызов инструмента внешнего MCP-сервера. |
| `MCP_REQUEST_TIMEOUT_SEC` | `30` | Предел времени на **один** запрос протокола к MCP-серверу — рукопожатие, перечисление инструментов, проверка живости. ## 5. Выбор навыков владельцем и подключение внешних MCP-серверов

`OUROBOROS_USER_ENABLED_SKILL_IDS` — переменная окружения и owner-and-agent allowlist. Задайте
разрешённые по умолчанию скиллы деплоймента через переменную, затем укажите явный набор для
конкретного агента через JSON-массив или строку через запятую:

```http
PUT /api/owner-settings/{agent_id}/OUROBOROS_USER_ENABLED_SKILL_IDS
{"value":"[\"distribution:workstation\"]"}
```

Значения — только канонические `source_id:local_id`; короткое или отображаемое имя повреждает всю
настройку. Отсутствующая строка берёт значение из `AppSettings`, но пустой текст и `[]` означают
«не разрешён ни один скилл». Instance default тоже `[]`, поэтому deployment обязан явно перечислить
доступные скиллы. Повреждённая строка или ошибка чтения запрещает все навыки для этой задачи, не
затрагивая остальные инструменты. В многопользовательском режиме задача читает список один раз до
сборки prompt и сохраняет результат до завершения: PUT или DELETE виден следующей задаче, но не
отзывает уже прочитанные инструкции текущей. Список только сужает стартовый каталог, allowlist агента
и общий запрет `script`, `tool`, `extension`; расширить их им нельзя. Wildcard и sentinel не
поддерживаются.

Исключение из общего запрета задаёт не владелец, а развёртывание: `OUROBOROS_TRUSTED_EXECUTABLE_SKILL_IDS` называет доверенные навыки поставки (`distribution:<навык>`) исполняемых типов. Остальные исполняемые навыки по-прежнему скрыты. Названный навык ещё и должен быть в `OUROBOROS_USER_ENABLED_SKILL_IDS` владельца или агента, иначе задача его не получит.

Миграция с `OUROBOROS_USER_DISABLED_SKILL_IDS` — breaking change: переименуйте переменную и значения
owner settings, заменив перечень запрещённых id явным перечнем разрешённых. Старые строки в
`user_settings` остаются инертными; compatibility alias и автоматической инверсии нет.

### Подключение внешних MCP-серверов

MCP — протокол доступа к внешним инструментам. Подключение складывается из общего выключателя и списка серверов:

- `MCP_ENABLED=true` — включить подключение.

**Что настраивается временем, а что нет.** Из бюджетов MCP-клиента переменными окружения управляются ровно три, и все они — про то, чего код знать не может: `MCP_TOOL_TIMEOUT_SEC` (сколько ждёт вызывающий), `MCP_REQUEST_TIMEOUT_SEC` (каков их сервер) и `MCP_STREAM_READ_TIMEOUT_SEC` (какова ваша сеть). Остальные — открытие сокета, шаги лестницы переподключения, интервал проверки живости, запас на остановку — свойства протокола и SDK, а не развёртывания; они заданы в коде и меняются код-изменением. Значения по умолчанию записаны **только** в схеме настроек: пакет `ouroboros/mcp/` копии не держит, поэтому расхождения между документацией и поведением быть не может.

**Откуда берётся список.** Список всегда строится кодом `security_config/mcp.py`: этот файл входит в образ, импортируется один раз при запуске процесса, и менять его можно только код-изменением (ревью, CI, подпись образа). Записи списка — значения типа `McpServerEntry` (поля — в таблице ниже).

`OUROBOROS_USER_ENABLED_MCP_IDS` — список id серверов, разрешённых агенту по умолчанию (из окружения,
пустой список по умолчанию). Владелец может переопределить выбор для конкретного агента, задав
JSON-массив или строку id через запятую через
`PUT /api/owner-settings/{agent_id}/OUROBOROS_USER_ENABLED_MCP_IDS`. Отсутствие переопределения
возвращает значение из окружения; `[]` запрещает агенту
все MCP-инструменты; непустое значение пересекается с id из `security_config/mcp.py`. Подключения и
каталог остаются общими на процесс, а изменение применяется при следующем чтении каталога или dispatch.

В зависимости от `OUROBOROS_POLIGON` список составляется по-разному — выбор ветки происходит внутри самого файла. В поставляемом шаблоне это:

- ветка `DEV` (по умолчанию) — для локальной разработки список берётся из легаси-ключа `MCP_SERVERS` в переменных окружения; это пример локального пути, не производственный;
- остальные полигоны — список составляется кодом непосредственно в файле.

Каждая команда обязана подменить поставляемые файлы `security_config/mcp.py` и `security_config/a2a.py` своими (ветка для своего полигона и свой список) и показать их на ПСИ. Безопасность запрещает чтение `MCP_SERVERS` и `A2A_REMOTE_AGENTS` в коде продукта: эти ключи доступны только внутри `security_config/` (ветка `DEV`) и в схеме настроек; для всех полигонов, кроме `DEV`, легаси-ключи не читаются вовсе. Пустой список означает, что подключение не создаётся (информационное сообщение при запуске).

Записи списка (одна запись — один сервер; повреждённые записи отбрасываются):

| Поле | По умолчанию | Назначение |
|------|--------------|------------|
| `id` | пусто | Обязательный идентификатор. Инструменты сервера становятся доступны как `mcp__{id}__{название}`. |
| `name` | пусто | Понятное название. |
| `enabled` | `true` | Включает/выключает запись. |
| `transport` | `streamable_http` | Способ подключения: `streamable_http` (потоковый HTTP, по умолчанию) или `sse` (поток событий). |
| `url` | пусто | Обязательный адрес сервера: `http://…` или `https://…`. Запись без него отбрасывается при загрузке. |
| `auth` | `{"kind": "none"}` | Авторизация сервера — ровно одна на запись, поле `kind` выбирает вид (таблица ниже). Других полей авторизации у записи нет. |
| `allowed_tools` | пусто | Ограничение доступного набора инструментов; пусто — все инструменты сервера. |
| `retrieval_aliases` | пусто | Дополнительные поисковые псевдонимы для поиска по памяти. |
| `tool_result_limits` | пусто | Пределы объёма результата по инструментам (от 1 до 120000). |

Поля, которых нет в таблице, запись не принимает: она отбрасывается целиком. Это относится и к полям снятого транспорта `stdio` (`command`, `args`, `env`), и к прежним полям верхнего уровня `auth_header`, `auth_token` и `tls` — запись из старой настройки не подхватывается частично. Статический заголовок подлинности теперь задаётся видом `user_token`, а egress-шлюз с mTLS — видом `mtls`. Внутри `auth` неизвестные ключи тоже не принимаются: опечатка вроде `cookie` вместо `cookies` отбрасывает запись, а не молча отключает передачу.

Виды авторизации (`auth.kind`):

| Вид | Поля | Транспорт | `http://` | Что уходит на сервер |
|-----|------|-----------|-----------|----------------------|
| `none` | нет | любой | разрешён | Ничего. |
| `user_headers` | `headers` — имена заголовков, `cookies` — имена cookie | только `streamable_http` | запрещён | В каждом вызове инструмента — заголовки и cookie пользователя, собранные при WebSocket-подключении к браузерному транспорту. |
| `user_token` | `auth_header` — имя заголовка (обязательно); `auth_token` — статический токен развёртывания (секрет, необязательно) | `streamable_http`; `sse` — только со статическим `auth_token` | запрещён | В заголовке `auth_header`: личный токен пользователя для этого сервера и агента, если он есть, иначе статический `auth_token`, иначе вызов отклоняется. |
| `mtls` | нет | любой | разрешён | Ничего: `url` указывает на egress-шлюз развёртывания, который сам устанавливает взаимный TLS со своим сертификатом; агент подключается так же, как при `none`, и сертификата не держит. |

**Правила.** Запись отбрасывается (в ветке `DEV` — с именем записи в журнале; в коде полигона — ошибкой при запуске), если:

- `url` начинается с `http://`, а вид — `user_headers` или `user_token`: учётные данные по открытому каналу не передаются, по `http://` ходят только `none` и `mtls`; адрес в сообщении об отказе не выводится;
- вид `user_headers`, а `transport` равен `sse`: SSE-клиент SDK не передаёт заголовки отдельного сообщения, а отказ одному пользователю обрывает общую для всех сессию;
- вид `user_token`, `transport` равен `sse`, а `auth_token` не задан: личный токен по `sse` доставить нельзя;
- в `user_headers` не названо ни одного заголовка или cookie, имя не является HTTP-токеном, либо повторяется без учёта регистра; в `user_token` не задан `auth_header` или он не HTTP-токен;
- в `headers` или в `auth_header` названо защищённое имя (без учёта регистра): `host`, `content-length`, `content-type`, `transfer-encoding`, `connection`, `keep-alive`, `proxy-connection`, `proxy-authorization`, `te`, `trailer`, `upgrade`, `expect`, `accept`, `cookie` (cookie передаются только через `cookies`), `last-event-id`, `X-Trace-Id`, `X-Agent-Id`, а также любое имя с префиксом `mcp-`, `sec-websocket-`, `a2a-` или `x-a2a-`;
- `auth_token` содержит символы, недопустимые в заголовке (вне табуляции, пробела и видимого ASCII, либо пробел или табуляция по краям); значение в сообщении не выводится. Пустой `auth_token` означает, что статического токена нет.

**`user_headers`.** Из хранилища читаются и передаются только названные заголовки и cookie, и ровно в том виде, в каком их прислал браузер. Собираются только имена, объявленные в `security_config/auth/header_collector.yaml` (ниже); сервер (а в многопользовательском режиме — каждый тир) не запускается при `MCP_ENABLED=true`, если включённая запись `user_headers` передаёт заголовок или cookie, которых там нет с тем же типом, и называет каждое такое имя вместе с id записи в виде `<id> <тип>:<имя>` (имя заголовка — в нижнем регистре); выключенные записи не проверяются. Коллектор при подключении берёт заголовок, только если браузер прислал его ровно один раз, и сохраняет значение как есть; повторяющийся заголовок не сохраняется вовсе, а в лог пишется предупреждение с его именем (без значений). Из повторяющихся cookie берётся первая; при вызове cookie уходят одним заголовком `Cookie` с одними названными, в порядке объявления. Каждое новое подключение того же пользователя к тому же агенту заменяет сохранённый набор целиком: заголовка или cookie, которых в нём не было, больше нет и у уже идущих задач. Каждое значение живёт свой срок `ttl_sec` из объявления; просроченное значение не отдаётся, но и не удаляется — строку убирает только следующее подключение того же пользователя к тому же агенту, поэтому шифротекст того, кто больше не подключается, остаётся в таблице. Если у вызова нет нужных учётных данных — запрос пришёл не из браузера, пользователь ещё не подключался или срок значения истёк, заголовка или cookie нет, значение пустое, значение содержит недопустимые для заголовка символы, хранилище недоступно, — вызов не отправляется и возвращает ошибку инструмента. Хранилище — таблица `security_contexts` общей базы данных состояния, значения в ней зашифрованы ключом `OUROBOROS_CREDENTIALS_ENCRYPTION_KEY`, поэтому в многопользовательском режиме тир агента читает то, что записал тир транспорта, и записи этого вида не запрещены.

**`user_token`.** Личный токен ищется по тройке «id сервера, владелец, агент» в таблице `mcp_user_tokens` базы данных состояния, где он хранится зашифрованным ключом `OUROBOROS_CREDENTIALS_ENCRYPTION_KEY`; истёкший токен не используется. Поиск идёт для запросов из браузера, диалогов и моста навыков, но не для A2A: там сразу используется статический токен, а без него вызов отклоняется. В диалогах и мосту навыков владелец и агент — настроенные, поэтому и личный токен — токен настроенного владельца. Если хранилище недоступно или личный токен содержит недопустимые для заголовка символы, вызов отклоняется, а не переходит на статический токен. Статический токен на `streamable_http` уходит и в заголовках самого подключения (согласование, получение списка инструментов, проверка живости), и в каждом вызове; личный токен заменяет его только в запросе своего вызова. На `sse` статический токен уходит только заголовком подключения, и таблица не читается. Записывает таблицу только поверхность настроек владельца: `GET /api/owner-settings/{agent_id}/mcp-servers` показывает включённые серверы развёртывания (пустой список при `MCP_ENABLED=false`) и срок действия личного токена, но не адрес и не сам токен; `PUT /api/owner-settings/{agent_id}/mcp-servers/{server_id}/token` с телом `{"token": "...", "ttl_sec": N}` сохраняет токен на `ttl_sec` секунд (от 60 до 7 776 000, то есть до 90 дней) и возвращает только `expires_at`; `DELETE` по тому же адресу удаляет его. Личный токен принимают только записи `user_token` на `streamable_http`: запись для остальных отвечает 400, выключенного или неизвестного сервера — 404; удаление проверок сервера не делает и снимает токен, даже когда сервер выключен или `MCP_ENABLED=false`, — иначе забытый токен снова ушёл бы в вызовы после включения. Настроенному владельцу (`global`) запись запрещена (403), а удаление разрешено: от его имени работают диалоги и мост навыков, и токен ушёл бы в вызовы всех их собеседников. Запрос без заголовка `X-Ouroboros-Owner-Id` в экземпляре без `OUROBOROS_MULTIUSER` приходит от имени настроенного владельца, поэтому такой запрос токен не запишет. Токен не попадает ни в ответы, ни в сообщения об ошибках, ни в лог; обновления и напоминания об истечении нет — после срока токен нужно записать заново. **Требование к ключу:** правильный `OUROBOROS_CREDENTIALS_ENCRYPTION_KEY` и база, обновлённая до актуальной ревизии, нужны серверу, тиру транспорта и тиру агента всегда — этим же ключом шифруется контекст безопасности; без ключа процесс не запускается, и ошибка называет настройку, но не ключ. Тиру реестра конфигурации тот же ключ нужен для маршрутов личных токенов: без правильного ключа они отвечают 503 с именем настройки.

**Общее для `user_headers` и `user_token` на `streamable_http`.** Учётные данные вызова уходят только в HTTP-запросе самого `tools/call` — не в отмене вызова, не в возобновлении потока, не в ответах на запросы сервера — и только на тот же адрес (схема, хост, порт), что в `url`: при перенаправлении на другой адрес снимаются все передаваемые заголовки (и статический токен), а при перенаправлении на тот же адрес остаются заголовки, но не `Cookie`. Такое подключение не хранит cookie, выставленные сервером (в том числе cookie привязки сессии балансировщика), и вызов ждёт окончания получения списка инструментов, не запрашивая его сам.

**Что собирается: `security_config/auth/header_collector.yaml`.** Файл входит в образ и разбирается при запуске; повреждённый файл останавливает процесс. Команда подменяет его вместе с `security_config/mcp.py`. Формат — один ключ `parameters`, список записей ровно с тремя ключами:

| Ключ | Назначение |
|------|------------|
| `type` | `header` — заголовок запроса или `cookie`. |
| `name` | Имя: HTTP-токен. Заголовок сравнивается без учёта регистра, cookie — с учётом. Заголовок с именем `cookie` не принимается — cookie объявляются типом `cookie`. |
| `ttl_sec` | Срок хранения собранного значения в секундах: целое положительное число (не строка, не дробное, не `true`). |

Одно и то же имя одного типа дважды объявить нельзя; заголовок и cookie с одинаковым именем допустимы. `parameters: []` — ничего не собирать; пустой файл не принимается. Собирается только объявленное: остальные заголовки и cookie подключения не сохраняются. Поставляемый файл:

```yaml
parameters:
  - type: header
    name: X-Sudir-Token
    ttl_sec: 3600
  - type: cookie
    name: sudir_session
    ttl_sec: 3600
```

Срок `3600` — заготовка: реальное время жизни токена СУДИР не определено. Срок короче жизни WebSocket-подключения означает, что после его истечения вызовы отклоняются до переподключения браузера.

Пример записи (для ветки `DEV` — значение легаси-ключа; в коде ветки своего полигона запись строится как `McpServerEntry` с теми же полями):

```json
[
  {
    "id": "research",
    "name": "Служба поиска",
    "transport": "streamable_http",
    "url": "https://mcp.example.com",
    "auth": {"kind": "user_token", "auth_header": "Authorization", "auth_token": "Bearer ..."},
    "allowed_tools": ["search", "fetch"]
  },
  {
    "id": "hr",
    "name": "Кадровая служба от имени пользователя",
    "transport": "streamable_http",
    "url": "https://hr-mcp.example.com/mcp",
    "auth": {"kind": "user_headers", "headers": ["X-Sudir-Token"], "cookies": ["sudir_session"]}
  },
  {
    "id": "archive",
    "name": "Архив через egress-шлюз",
    "transport": "streamable_http",
    "url": "http://egress-gateway.internal/archive-mcp",
    "auth": {"kind": "mtls"}
  }
]
```

## 6. Взаимодействие с другими агентами (A2A)

A2A — протокол взаимодействия агентов. Участие делится на два независимых направления: приём запросов от других агентов (входящий сервер) и обращения к другим агентам (исходящие подключения).

### 6.1 Входящий сервер

- `A2A_ENABLED=true` — включить сервер. Он запускается после готовности службы управления задачами (предел ожидания — `OUROBOROS_SUPERVISOR_STARTUP_TIMEOUT_SEC`).
- `A2A_HOST` (по умолчанию `127.0.0.1`) и `A2A_PORT` (по умолчанию `18800`) — адрес и порт прослушивания. При открытии адреса наружу защиту обеспечивает внешний шлюз.
- `A2A_AGENT_NAME`, `A2A_AGENT_DESCRIPTION` — имя и описание агента (запасные; документ личности имеет приоритет).
- `A2A_PUBLIC_URL` — внешний адрес службы, публикуемый в карточке агента (переопределяет вычисленный адрес).
- `A2A_MAX_CONCURRENT` — число одновременных задач.
- `A2A_TASK_TTL_HOURS` — срок жизни записей о задачах.

### 6.2 Исходящие подключения

- `A2A_EGRESS_ENABLED=true` — разрешить обращения к другим агентам.
- `A2A_TOOL_TIMEOUT_SEC` — предел ожидания ответа удалённого агента.

**Откуда берётся список.** Как и для MCP (раздел 5): список всегда строится кодом `security_config/a2a.py` (часть образа, импорт один раз при запуске), а ветвление по `OUROBOROS_POLIGON` происходит внутри файла. Ветка `DEV` (по умолчанию) для локальной разработки делегирует легаси-ключу `A2A_REMOTE_AGENTS` из переменных окружения; остальные полигоны составляют список кодом. Команда обязана подменить поставляемый файл своим (ветка для своего полигона и свой список агентов) и показать его на ПСИ. Чтение `A2A_REMOTE_AGENTS` в коде продукта запрещено — ключ доступен только внутри `security_config/` и схемы настроек; для всех полигонов, кроме `DEV`, он не читается вовсе. Пустой список означает, что исходящие подключения не создаются (информационное сообщение при запуске).

Записи списка (одна запись — один агент; повреждённые записи отбрасываются):

| Поле | По умолчанию | Назначение |
|------|--------------|------------|
| `id` | пусто | Обязательный идентификатор. Агент становится доступен как инструмент `a2a__{id}`; запись с пустым `id` не подключается, а из нескольких записей с одним `id` подключается только первая (остальные называются в журнале). |
| `name` | пусто | Понятное название. |
| `enabled` | `true` | Включает/выключает запись. |
| `url` | пусто | Обязательный адрес службы агента: `http://…` или `https://…`. Запись без него отбрасывается при загрузке. |
| `auth` | `{"kind": "none"}` | Авторизация агента — ровно одна на запись, те же виды, что у MCP-сервера (таблица ниже). Других полей авторизации у записи нет. |
| `featured_skills` | пусто | Навыки, упоминаемые в описании инструмента (на исполнение не влияют). |
| `retrieval_aliases` | пусто | Дополнительные поисковые псевдонимы для поиска по памяти. |
| `tool_result_limit` | `0` | Предел объёма результата (от 1 до 120000); `0` — действует предел исполняемой среды. |
| `poll_interval_sec` | `2` | Частота опроса результата задачи (от 0.05 до 300 секунд). |

Поля, которых нет в таблице, запись не принимает: она отбрасывается целиком. Это относится и к прежним полям верхнего уровня `auth_header` и `auth_token` — **запись старого вида после обновления не подключается**: в ветке `DEV` она отбрасывается, а журнал называет её `id` и лишнее поле, но не значения; в коде полигона такая запись — ошибка при запуске. Перенесите пару внутрь `auth` (`{"kind": "user_token", "auth_header": ..., "auth_token": ...}`, адрес — `https://`) и после развёртывания проверьте журнал на отброшенные записи. Внутри `auth` неизвестные ключи тоже не принимаются.

Виды авторизации (`auth.kind`):

| Вид | Поля | `http://` | Что уходит агенту |
|-----|------|-----------|-------------------|
| `none` | нет | разрешён | Ничего. |
| `user_headers` | `headers` — имена заголовков, `cookies` — имена cookie | запрещён | В каждом запросе операции — заголовки и cookie пользователя, собранные при WebSocket-подключении к браузерному транспорту; только для запросов из браузера. |
| `user_token` | `auth_header` — имя заголовка (обязательно); `auth_token` — статический токен развёртывания (секрет, необязательно) | запрещён | В заголовке `auth_header`: личный токен пользователя для этого агента и своего агента, если он есть, иначе статический `auth_token`, иначе операция отклоняется. |
| `mtls` | нет | разрешён | Ничего: `url` указывает на egress-шлюз развёртывания, который сам устанавливает взаимный TLS со своим сертификатом; агент подключается так же, как при `none`, и сертификата не держит. |

**Правила** те же, что у MCP-сервера (раздел 5), кроме правил транспорта — у записи A2A транспорта нет: `http://` с видом `user_headers` или `user_token` запрещён (адрес в отказе не выводится), имена должны быть HTTP-токенами без повторов, защищённые имена запрещены — к списку раздела 5 относятся и имена с префиксами `a2a-` и `x-a2a-` (например, `A2A-Version`), — `auth_token` должен помещаться в заголовок. Значение токена не выводится ни в `repr` записи, ни в сообщениях об отказе.

**Что и когда уходит агенту.** Одна операция — это один вызов инструмента `a2a__{id}`, `a2a_task_status` или `a2a_task_cancel`. Учётные данные операции вычисляются один раз, в начале, в пределах её `A2A_TOOL_TIMEOUT_SEC`, и уходят в каждом её запросе: в отправке сообщения, в каждом опросе задачи, в отмене после истечения срока, в чтении задачи после неудавшегося продолжения. Общий HTTP-клиент агента учётных данных в своих заголовках не держит ни при каком виде. Действуют те же ограничения по источнику запроса, что и для MCP: `user_headers` — только для запросов из браузера, личный токен ищется для браузера, диалогов и моста навыков, а запрос, пришедший через входящий A2A, отправляет только статический токен и таблицу не читает. Если учётных данных нет или хранилище недоступно, запрос не отправляется, и результат — `⚠️ A2A_ERROR (<id>): cannot be authorized: <причина>`; если учётные данные не получены за срок операции — `⚠️ A2A_ERROR` о том, что ничего не отправлено (такую операцию можно повторить). Отозванный токен перестаёт действовать со следующей операции: уже идущая операция доживает до своего срока.

**Карточка агента и адрес.** Карточка запрашивается при запуске без пользователя: в запросе только статический токен записи `user_token` (если он задан), для остальных видов — ничего, хранилища не читаются. Карточка сужается до интерфейсов на том же адресе (схема, хост, порт; порт по умолчанию равен его отсутствию), что в `url`, при любом виде авторизации: если на этом адресе нет интерфейса JSON-RPC, агент не подключается, а журнал называет настроенный адрес и адреса из карточки только как `схема://хост[:порт]`, без пути, запроса и учётных данных. Недоступная карточка заменяется запасной, указывающей на `url`. Перенаправления не выполняются; cookie, выставленные агентом, не сохраняются ни при каком виде; передаваемые имена снимаются с любого запроса на другой адрес.

**Отказ в авторизации.** Ответ HTTP 401 или 403 на отправку, опрос, чтение или отмену задачи, как и задача в состоянии `auth-required`, возвращается как `⚠️ A2A_ERROR` без текста SDK и без значений, с подсказкой по виду авторизации: `none` и `mtls` — развёртывание не отправляет агенту учётных данных, запись в `security_config/a2a.py` должен изменить оператор; `user_headers` — пользователю нужно войти заново; `user_token` — владелец может сохранить новый личный токен для этого агента в настройках владельца, либо оператор должен исправить статический токен. Задача в `auth-required` не отменяется, её хэндл остаётся в результате.

**Личные токены A2A.** Личный токен ищется по тройке «id агента, владелец, агент» в таблице `a2a_user_tokens` базы данных состояния, где он хранится зашифрованным ключом `OUROBOROS_CREDENTIALS_ENCRYPTION_KEY`; истёкший токен не используется. Токен MCP-сервера с тем же `id` агенту A2A не отправляется: это разные таблицы. Записывает таблицу только поверхность настроек владельца:

- `GET /api/owner-settings/{agent_id}/a2a-agents` — подключаемые агенты развёртывания (включённые, с `id`, первые для каждого `id`): `id`, `name`, `auth_kind`, `personal_token_supported` (вид `user_token`), `personal_token_writable`, `has_static_token` и `personal_token_expires_at`, но не адрес и не сам токен; при `A2A_EGRESS_ENABLED=false` — пустой список;
- `PUT /api/owner-settings/{agent_id}/a2a-agents/{remote_agent_id}/token` с телом `{"token": "...", "ttl_sec": N}` сохраняет токен на `ttl_sec` секунд и возвращает `{remote_agent_id, expires_at}`;
- `DELETE` по тому же адресу удаляет токен и возвращает `{remote_agent_id, cleared}`.

Ограничения и отказы — как у маршрутов личных токенов MCP (раздел 5): токен от 1 до 8192 символов, допустимых в заголовке, иначе 400; `ttl_sec` от 60 до 7 776 000 (до 90 дней), иначе 422; тело с лишним или отсутствующим полем — 422 без повтора введённого; неизвестный, выключенный агент и любой агент при `A2A_EGRESS_ENABLED=false` — 404 `no such A2A agent`; агент не вида `user_token` — 400 `A2A agent <id> takes no personal token`; настроенному владельцу запись запрещена (403), удаление разрешено; неизвестный владельцу агент — 404; неправильный ключ — 503 `personal A2A tokens cannot be sealed: OUROBOROS_CREDENTIALS_ENCRYPTION_KEY is not 64 bytes of base64`. Удаление проверяет только агента владельца, но не удалённого агента: токен снимается и у выключенного удалённого агента, и при `A2A_EGRESS_ENABLED=false`. Токен не попадает ни в ответы, ни в сообщения об ошибках, ни в лог.

**Агента перенесли на другой адрес — дайте ему новый `id`.** Личные токены хранятся по `id` записи, а не по адресу: если у записи сменить `url`, сохранённые владельцами токены уйдут на новый адрес.

**Хэндлы задач.** Каждый `task_id`, который возвращает результат, — хэндл `<id задачи>~<32 шестнадцатеричных символа>`: HMAC-SHA256 над `["a2a-task", id агента, id задачи, владелец, агент]` под ключом, выведенным из `OUROBOROS_CREDENTIALS_ENCRYPTION_KEY`. Хэндл привязан к владельцу, агенту и удалённому агенту, но не к чату и не к источнику: задачу, начатую в одном чате, можно продолжить из другого чата того же владельца и агента. `a2a_task_status`, `a2a_task_cancel` и продолжение задачи принимают только такой хэндл, проверяют его до чтения хранилищ и до любого запроса и отклоняют чужой, изменённый или голый `id` задачи. Удалённому агенту уходит только сам `id` задачи. Задачи, начатые до развёртывания этой версии, продолжить нельзя; смена `OUROBOROS_CREDENTIALS_ENCRYPTION_KEY` делает недействительными все открытые хэндлы — завершите или оставьте долгие делегирования до развёртывания и до смены ключа. Неправильный ключ останавливает запуск, и ошибка называет настройку, но не ключ.

**Объявление собираемых имён.** Запись `user_headers` может передавать только заголовки и cookie, объявленные в `security_config/auth/header_collector.yaml` с тем же типом (раздел 5): при `A2A_EGRESS_ENABLED=true` сервер, а в многопользовательском режиме каждый тир, не запускается, называя `security_config/a2a.py` и каждое такое имя в виде `<id> <тип>:<имя>`; выключенные записи не проверяются. В многопользовательском режиме также отклоняется включённый агент по локальному для экземпляра адресу (`localhost`, loopback, `0.0.0.0`); ни один вид авторизации не запрещён.

Пример записи (для ветки `DEV` — значение легаси-ключа; в коде ветки своего полигона запись строится как `A2aRemoteAgentEntry` с теми же полями):

## 7. Что нельзя настроить переменными

- **Изменение документа личности агента** — выключено намеренно и не имеет переменной: никакая переменная, файл или вызов инструмента не откроет документ для перезаписи.
- **Списки внешних MCP-серверов и удалённых агентов в `production`** — часть образа (`security_config/mcp.py`, `security_config/a2a.py`), изменение проходит проверку и вступает в силу при следующем запуске.
- **Какие заголовки и cookie браузерного подключения собираются и сколько хранятся** — файл `security_config/auth/header_collector.yaml` в образе (раздел 5), а не переменная.
- **Инструкции команды в системном промпте** — файл `security_config/PROMPT.md` в образе, а не переменная: его текст идёт в промпт сразу после `prompts/SYSTEM.md` под заголовком `## Deployment instructions` и может только дополнять и сужать базовые правила. Поставляемый файл пуст (секции нет); команда подменяет его своим так же, как `mcp.py`. Секция больше 27 000 символов — предупреждение в журнале, текст отправляется целиком.
- **Состав навыков** — только каталог навыков репозитория; установка навыков из внешних источников недоступна.
