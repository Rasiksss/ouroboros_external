# CLAUDE.md — симбиоз AIFA и ouroboros

Правила для любой работы в `aifa/`, `skills/aifa-*`, `aifa-symbiosis/`. `AGENTS.md` рядом — то же
для других агентов; менять оба одинаково. Правила ouroboros (корневые `AGENTS.md`, `CLAUDE.md`,
`.rules/`, `docs/INVARIANTS.md`) действуют на его пути и на `skills/**` — их не правим.

## 0. Чтение в начале сессии
1. Этот файл.
2. `aifa-symbiosis/architecture/adr/README.md` (указатель) и записи, названные в промпте.
3. Разделы `aifa-symbiosis/architecture/ARCHITECTURE.md` и `CONTRACTS.md`, названные в промпте;
   строку своего этапа в `ARCHITECTURE.md` §8.
4. `aifa-symbiosis/plan/PROGRESS.md` — предусловия, записи прошлых шагов, проблемы своего шага;
   правила роли: реализация — `aifa-symbiosis/plan/PRINCIPLES.md`, ревью — `REVIEW_GUIDE.md`.
5. Для правок в `skills/aifa-*`: `uv run python scripts/resolve_rules.py <файлы>` и названные им
   правила ouroboros (`.rules/skills.md`), `docs/INVARIANTS.md`.
6. Для правок в `aifa/finengine`: `aifa/finengine/docs/build-plan/01-nerushimye-resheniya.md`; при
   работе с циклом — разделы плана 34 (`aifa/finengine/docs/build-plan/34-*.md`), названные в
   промпте.
Код — только файлы и диапазоны из промпта. Модули «на всякий случай» не открывать.

## 1. Архитектура меняется только новой записью решения
- Решение, контракт, набор инструментов, раскладка, конфигурация ouroboros — только через новый
  файл `aifa-symbiosis/architecture/adr/NNNN-*.md` (шаблон в `adr/README.md`). Принятую запись не
  переписывают; у заменённой меняют лишь строку статуса.
- `ARCHITECTURE.md`, `CONTRACTS.md`, `FITNESS.md`, снимки в `aifa/contracts/` меняются только в
  одном коммите с новой ADR (проверка F13).
- Код расходится с ADR или контрактом — **остановиться и описать расхождение**, не отступать
  молча. Решение принимает владелец; итог — новая ADR.
- Решения раздела 4 `SYMBIOSIS.md` (ADR-0002…0018) не пересматриваются без владельца.

## 2. Границы (держатся проверками F1–F13)
Сейчас работают F1, F2, F11 (замок ouroboros) и F13 — `aifa/tests/architecture/`; остальные
появляются по «Порядку появления» в `FITNESS.md`.
- Файлы ouroboros вне `skills/aifa-*` не правим (F1). Нужна правка — это вопрос владельцу и ADR.
- Служба не импортирует ouroboros, ouroboros не импортирует службу; плагин `aifa-engine` — тонкий
  клиент без логики (F2, ADR-0022).
- Ничего из текста документа не уходит в ouroboros; ответы инструментов — только через
  `ouro_view` (F3, ADR-0025).
- Заголовки владельца ouroboros ставит только `ouro_client` (F12).
- Ouroboros настраивается только окружением; изменение набора — ADR (F9, ADR-0027).

## 3. Менторский режим (из правил AIFA)
- Не реализовывать молча: объяснять решения, паттерны и компромиссы, почему подход верен именно
  здесь; показывать варианты, если их несколько.
- В сессиях этапов объяснения — в отчёте, в разделе «Что и почему»; по ходу — работа.
- Вопросы по настоящим развилкам — сразу, одним блоком.

## 4. Думать до кода, простота, точечные правки (из правил AIFA)
- Называть допущения; неясно — спросить. Путь проще — сказать.
- Минимум кода; без абстракций для одноразового и без «на будущее».
- Трогать только нужное задаче; соседний код не «улучшать»; замеченный мёртвый код — назвать.
- Каждая изменённая строка прослеживается до задачи.

## 5. Тесты до кода, базовая линия
- Каждый шаг этапа: сначала тест, который падает; затем код; коммит — шаг + тест.
- В начале сессии прогнать тесты затронутых областей и записать, что уже падает; в конце значимы
  только новые падения. Известные красные (AIFA на Windows; три теста `test_ingress_v2.py`) не
  чинить, если это не задача.
- Многошаговая задача — план «шаг → чем проверяется».
- Живые вызовы моделей и Workstation — только тестами, которые без адреса/флага пропускаются.

## 6. Ворота (Definition of Done)
- `aifa/scripts/check.sh` зелёный (включает `./scripts/check.sh` ouroboros, тесты службы, проверки
  симбиоза, фронтенд).
- Для правок в `skills/aifa-*` — ещё и Definition of Done ouroboros: независимое ревью диффа в
  чистом контексте (`/code-review`), сверка с `docs/INVARIANTS.md`.
- Для изменений поведения — сравнение с опорной записью (F5 (б)); различия — только разрешённые ADR.
- Отчёт: что сделано; тесты; сравнение с базовой линией; «Что и почему»; что не сделано.

## 7. Прогресс и незавершённое — в `aifa-symbiosis/plan/PROGRESS.md`
- §1 статус шага, §3 запись сессии, §4 проблемы, которые не удалось решить (что не сделано; почему;
  конкретный следующий шаг), §5 принятые решения по проблемам.
- Решённая проблема не удаляется: статус «решено» и ссылка на решение. Других журналов не ведём
  (`34-status.md` AIFA больше не дополняем; `BACKLOG.md`, `HANDOFF.md` ouroboros — не наши;
  `PROJECTS_STATE.md` — снимок состояния, не журнал).
- Роли и цикл сессий (реализация → ревью → пользовательский тест) — `aifa-symbiosis/plan/README.md`.

## 8. Сообщай, что заметил
Архитектурно значимое (альтернативный путь, флаг с откатом, экспериментальный режим по умолчанию,
расхождение кода с ADR) — сказать сразу, хоть одной строкой.

## 9. Git
- Репозиторий `Rasiksss/ouroboros_external` (`origin`), основная ветка `dev`; `main` — старая
  внешняя копия: не сливать в `dev`, не пушить (ADR-0030).
- Ветки шагов `sym/NN-<кратко>` от актуального `dev`; в `dev` сливаются локально (`--no-ff`) после
  ревью без блокеров (ADR-0033). Файлы добавляются явно.
- База ouroboros — тег `base/ouroboros-1.5.1` (= `17b3f93`); от него считают F1 и F11.
- **Без push**, пока владелец явно не разрешит.
- Коммит — шаг этапа и его тест; сообщение по-русски, первая строка — что изменилось.

## 10. Стенд
- dev: выкатка — работа агента, но момент задаёт владелец («выкатывай»). Только compose-проект
  `aifa-sym` и его контейнеры; перед любой `docker`-операцией — цель без `prod` в имени.
- **prod не трогать никогда:** `finengine-prod-*`, `openclaw-prod-gw`, `workstation-svc-prod`,
  `finengine-caddy-1`, `infproxy`, `deploy/.env.prod`, `deploy/prod-*`. Тесты против prod не гонять.
- Старый AIFA на dev (`finengine-*`, `openclaw-dev`, `workstation-svc`) до этапа 6 не трогать: он
  — опора сравнения и работает параллельно.
- Порядок выкатки AIFA (сверка md5, бэкап, накладывание поверх серверного состояния) — раздел 7а
  `CLAUDE.md` AIFA (в этот репозиторий не перенесён, ADR-0032 п. 3; исходник —
  `Baltazar2795/AIFA-CLAW`); для `aifa-sym` — `aifa/deploy/dev/README.md` (пишется на этапе 0).

## 11. Бюджет сессии
Одна сессия — один шаг или один этап, 150–200 тыс. токенов. Бюджет кончается — довести целостный
кусок до зелёных тестов, остаток — в `plan/PROGRESS.md` §4.
