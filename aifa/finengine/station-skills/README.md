# station-skills — exec-профиль навыков (исполнение В Workstation)

Это **exec-профиль** наших навыков: агент исполняет логику **внутри песочницы
пользователя** (Workstation) через `exec`, а не зовёт MCP-тул. Так задуман
банковский AIFA CLAW: внутренняя модель, без публичного интернета, вся
бизнес-логика — скрипт-в-скилле, синкается в станцию, редактируется аналитиком.

Отличие от `agent-workspace/skills/` (**MCP-профиль**, деливерабл Расулу для
НАТИВНОГО OpenCLAW): там SKILL.md только **зовёт fe_* MCP-тулы** (скриптов нет);
здесь SKILL.md **несёт рядом сам движок** (`scripts/*.py`) и запускается через
`exec` в станции.

**Живые потребители этого каталога:**
- `deploy/Dockerfile.backend` → копируется в образ бэкенда (`/app/station-skills/`);
- `deploy/workstation-aifa/Dockerfile` → запекается в образ Workstation-станции.

⚠️ **Дрейф-риск (#72):** имена навыков пересекаются с MCP-профилем
(aifa-analyze / aifa-extract*), содержимое разное по построению. Меняя
СЕМАНТИКУ навыка (параметры движка, depth/role, контракт вывода) — правь ОБА
профиля: регрессию #76 (снятие role из анализа) чинили в двух местах именно
из-за этого.

```
station-skills/
  _runner/
    launch.sh              — общий лаунчер run.sh навыков (полка/громкий отказ/отпечаток)
  aifa-metric/           — основной UI ingress: 7 GoalType из буквального запроса через intent.parse
  aifa-extract/          — извлечение показателей по ячейке и роли
    SKILL.md / run.sh / scripts/extract.py
    scripts/extract_run.sh — обёртка воркера: доставка текста в комнату + запуск
  aifa-calc/             — коэффициенты реестра по таблице прогона
    SKILL.md / run.sh / scripts/calc_run.py
  aifa-analyze/          — ДЕРЕВО: корень + ветки по отрасли
    SKILL.md             — корень: порядок, заземление, таблица призм
    nf/SKILL.md          — ветка «нефинансовая компания» (дельта к корню)
    bank/SKILL.md        — ветка «банк» (дельта к корню)
```

## Раздел по ЧИТАТЕЛЮ, а не по важности

В каталоге навыка лежат файлы двух сортов, и едут они РАЗНЫМИ трактами:

| Кто читает | Что | Как доезжает |
|---|---|---|
| **гейтвейная модель** | `SKILL.md` навыка и `SKILL.md` его веток | `deploy/sync_workspace_skills.sh` → воркспейс гейтвея |
| **код станции** | `scripts/`, `method/`, всё остальное | полка (`station_driver._build_shelf()`) → комната |

Это не смягчение запрета на вторую копию кода: код по-прежнему живёт в одном
месте. Просто ПОРЯДОК нужен модели, а МЕТОДИКА и СКРИПТ — коду, и возить их
одним трактом незачем. Обоснование целиком — `docs/ANALYSIS_SKILLS_STRUCTURE.md` §0.

Отсюда правило: файл, на который ссылается тело навыка, обязан называться
`SKILL.md` и лежать не глубже ветки — иначе он останется в репозитории, а модель
прочитает пустоту. Сторож — `tests/test_method_tree_parity.py`.

## Призмы (виды разбора) живут в `method/lens/`

Призма — это кредитный, риск-, факторный анализ и план-факт: куски, которые
полный финансовый разбор ПЕРЕИСПОЛЬЗУЕТ, а не дублирует (канон §3, §8). Файл
призмы — методика, значит его читает код и едет он полкой; а решение «включать
или нет» принимает модель — значит триггер живёт в теле навыка, в таблице призм
корневого `aifa-analyze/SKILL.md`, и больше нигде.

На 14.08 призм НЕТ НИ ОДНОЙ: механизм построен, методика не написана. Пустая
таблица честнее объявленной призмы без содержания. Три множества (файлы,
группы `lens:` в `_order.md`, строки таблицы) обязаны совпадать — это и
проверяет сторож паритета.

⚠️ **Тело `aifa-analyze/SKILL.md` опережает маршрут ровно на одно окно.** Оно
велит запускать разбор через `exec` в станции, а сегодня разбор ещё идёт тулом
`fe_analyze` — карта «намерение → инструмент» в `llm/openclaw.py` снимается для
извлечения (К4) и для анализа отдельно, вторым окном. Пока карта на месте,
модель до тела не доходит и расхождение безвредно; но снимать карту анализа и
переписывать это тело надо ОДНИМ заходом. Ровно так уже обожглись в #165.

## Единственный механизм оркестрации

Срез 14 удалил прежний `skill.yaml` + общий `steps.py` runner и model-declared
`_runner/plan.py`. Они задавали ручной порядок шагов рядом с каноническим
`Target/ProducerResolver/PlanGraph/GraphExecutor`. В `skills/spec/` остаются
только контракты и реализация графа; `update_plan` — проекция прогресса для UI,
а не источник порядка исполнения.

Общая выдача station extraction (периоды, markdown, Excel) по-прежнему живёт в
`finengine.skills.extract_present` и охраняется `tests/test_extract_present.py`.

## Поток в банке (как это работает)
```
1. Гейтвей: агент получил PDF + «извлеки/проанализируй»
2. Гейтвей → MCP-тул IDP-OCR(pdf) → текст            (OCR — единственный тул-сервис)
3. Гейтвей кладёт текст файлом в станцию + инжектит скилл в контекст агента
4. Станция: агент по SKILL.md запускает `python scripts/extract.py --text ocr.txt --registry data/registry.json`
   → скрипт зовёт ВНУТРЕННЮЮ модель → отдаёт JSON + markdown-таблицу
5. Станция → результат → гейтвей → пользователь
```
Egress станции наружу = только внутренняя LLM. Секретов в станции нет (модель внутренняя).

## Модель (endpoint) — через env
Скрипт не привязан к провайдеру. Берёт endpoint из переменных окружения:
```
AIFA_LLM_BASE_URL   напр. http://internal-llm/v1  ИЛИ https://openrouter.ai/api/v1 (для нашей проверки)
AIFA_LLM_API_KEY
AIFA_LLM_MODEL      напр. qwen/qwen3.6-plus
```
В банке это укажет на их внутреннюю модель; у нас — на OpenRouter для прогона.
