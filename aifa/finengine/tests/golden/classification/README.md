# tests/golden/classification/

Эталонный набор для `ClassificationResult`/`detect_profile()`
(`src/finengine/skills/extractors/_classifier.py` — уже рабочая основа,
02-tekushee-sostoyanie §2.1), C0.1: не менее 50 однозначно размеченных
отчётов, покрывающих все действующие профили, плюс отдельный набор
неоднозначных случаев.

## Профили (`PROFILE_IDS` из `_classifier.py`)

`ifrs_nf_ru`, `ifrs_bank_ru`, `rsbu_nf_ru`, `rsbu_bank_ru`, `us_gaap_nf_en`,
`us_gaap_bank_en`, `ifrs_nf_en`, `ifrs_bank_en`, `ind_as_nf_en`, `ind_gaap_bank_en`.

## Откуда взяты данные

Все записи — реальные, скачанные из интернета отчёты (не выдуманные и не
перенесённые из старого `tests/golden/extract/` — тот набор принадлежит
снесённому движку и не переиспользован). Источники:

* SEC EDGAR (`data.sec.gov/submissions`, `www.sec.gov/Archives/edgar`) — для
  `us_gaap_nf_en`/`us_gaap_bank_en`, официальный первоисточник.
* Банк России (`cbr.ru/banking_sector/credit/coinfo/f806`, `.../f807`) — для
  `rsbu_bank_ru`, официальный регулятор, формы 0409806/0409807.
* `financemarker.ru` — сторонний агрегатор, зеркалирующий реально поданные
  МСФО/РСБУ отчёты российских эмитентов MOEX; для `ifrs_nf_ru`,
  `ifrs_bank_ru`, `rsbu_nf_ru`. Помечено `source_note` в каждой записи —
  это не первоисточник, а зеркало.
* Официальные сайты эмитентов (unilever.com, nestle.com, hsbc.com, sc.com,
  ril.com, tcs.com, hdfc.bank.in, ...) — для `ifrs_nf_en`, `ifrs_bank_en`,
  `ind_as_nf_en`, `ind_gaap_bank_en`.

**Метод подтверждения.** Профиль каждой компании известен независимо от
классификатора — из публичной идентичности компании (юрисдикция листинга,
тип регулятора, форма отчёта: 10-K → US GAAP, 20-F/официальный МСФО-отчёт →
IFRS, форма 0409806/7 → РСБУ банка и т.д.), а не подобран так, чтобы
классификатор согласился. `cross_check` в каждой записи — результат
реального прогона `detect_profile()` по сохранённому тексту; несовпавшие
кандидаты **не попали** в набор (см. `_build_cases.py`, вывод `rejected`),
а не были подогнаны под желаемый результат.

## Формат (`cases.json`)

Список объектов:

| Поле            | Описание |
|-----------------|----------|
| `id`             | `cls-NNN` |
| `company`        | название компании/банка |
| `profile_id`     | подтверждённый профиль (ground truth) |
| `source_url`     | точный URL, откуда взят текст |
| `source_note`    | заполнено, если источник — зеркало, не первоисточник |
| `cross_check`    | `{detected_profile, confidence_low, reason}` — результат живого `detect_profile()` на момент сбора |
| `excerpt`        | реальный текст отчёта (до 200k символов — тот же `_HEAD_WINDOW`, что использует сам классификатор) |

## Неоднозначные случаи (`ambiguous_cases.json`)

Случаи, где независимая (по идентичности компании) правда есть, но живой
классификатор либо ошибается, либо помечает результат `confidence_low=true`
— то есть именно то поведение, которое будущий тест на этом наборе обязан
проверять (не "классификатор всегда прав", а "низкая уверенность корректно
сигнализирует неоднозначность"). Формат — тот же, плюс `note`, объясняющий
источник неоднозначности.

## Служебные `_fetch_*.py` / `_build_cases.py`

Скрипты, которыми это было собрано: `_fetch_edgar.py` (SEC EDGAR, US GAAP),
`_fetch_cbr.py` (Банк России, RSBU-банки), `_fetch_financemarker.py`
(российские МСФО/РСБУ через агрегатор), `_fetch_generic.py` (разовые
международные источники), `_build_cases.py` (слияние + сжатие excerpt'ов до
минимального размера, сохраняющего тот же вердикт). Это метод, а не кнопка
«воспроизвести один в один»: манифесты внутри `_fetch_*.py` правились по
ходу сбора (часть кандидатов не подтвердилась и заменялась — см. `rejected`
в выводе `_build_cases.py`), поэтому текущее содержимое каждого файла — это
последний использованный манифест для этого источника, а не объединение
всех раундов. Промежуточные `_*_raw*.json` и снимок
`sec.gov/files/company_tickers.json` не сохранены — только итог
(`cases.json`, `ambiguous_cases.json`).
