# Правила кодирования (Coding Standards)

Правила для GigaCode-агента при ревью запросов на слияние в репозиторий
Finengine. Цель — каждый влитый PR соответствует принятым в проекте стандартам
качества: чистота кода, дисциплина коммитов, отсутствие рефакторинг-регрессий.
Контекст: Python ≥ 3.12, FastAPI, SQLAlchemy 2 + psycopg3, OpenSearch, Docker
(D19), линтер/форматтер — ruff (line-length 100, target py312).

## 1. Коммит-гигиена

### 1.1 Структурные изменения — отдельными коммитами (🔴 MUST)

Рефакторинг (перенос файлов, сплит модулей) и «grooming» (форматирование,
сортировка импортов) НЕЛЬЗЯ смешивать в одном коммите — иначе `git bisect` и
`git revert` невозможно точечно применить.

**Нарушение**: 109 файлов в одном коммите, где сплит `main.py` на роут-модули
смешан с сортировкой импортов в 50+ файлах.

**Правильно**:
- коммит 1: `refactor(api): split monolithic main.py into modular routes`
- коммит 2: `chore: apply ruff format + import sorting across src/`

### 1.2 Один логический change на коммит (🟡 SHOULD)

Если в сообщении коммита требуется союз «И» — коммит надо разбить. Исключение:
механические переименования, затрагивающие много файлов.

**Правильно**: `refactor(api): extract auth module to routes/auth/`
**Неверно**: `refactor api AND fix lint AND update deps`

### 1.3 Префиксы типов коммитов (🟡 SHOULD)

Conventional Commits: `feat(...)`, `fix(...)`, `docs(...)`, `refactor(...)`,
`chore(...)`, `test(...)`. Для крупных фич — трекер-номер в scope.

## 2. Стиль кода

### 2.1 Нет вложенных функций (🔴 MUST)

Вложенные `def` — анти-паттерн для этого проекта. Новый/правимый код пишется
БЕЗ вложенных функций — хелперы выносятся на уровень модуля с параметрами.

**Легитимные исключения** (в новый код не вводить): SSE-генераторы, фабрики,
`re.sub`-колбэки, рекурсия, worker-задачи с shared state.

**Нарушение**:
```python
async def drive_run(run_id: str):
    def _log(msg):  # вложенная функция
        logger.info(f"[{run_id}] {msg}")
    ...
```

**Правильно**:
```python
def _log_run(run_id: str, msg: str) -> None:
    logger.info(f"[{run_id}] {msg}")

async def drive_run(run_id: str):
    _log_run(run_id, "started")
```

### 2.2 Без `try/except` в обычном потоке; без лишнего `Any` (🟡 SHOULD)

Избегать `try/except` в обычном потоке — использовать явные проверки и
доменные исключения. Исключения обязательны там, где проект их требует:
изоляция startup-задач (R4.2) и best-effort инструментальные пути (feedback/
spend/traces — R11.1). `Any` не использовать без необходимости — конкретные
типы, `TypeVar` или сужение через isinstance-проверки.

### 2.3 Функциональный стиль вместо циклов (🟡 SHOULD)

Предпочитать list comprehensions / `filter`/`map` над ручными `for`-циклами с
аккумулятором; на `filter` — type guards (предикаты с `isinstance`/`TypeGuard`)
для сохранения вывода типов. Тернарники и early return вместо
переприсваивания; избегать `else` после `return`.

### 2.4 Полагаться на type inference; без лишних аннотаций (🟢 NICE-TO-HAVE)

Избегать избыточных аннотаций, повторяющих очевидный тип (например, тип в
аннотации константы, который выводится). Переменные, используемые один раз,
инлайнить. (Правила для веб-части — в `web/CLAUDE.md`.)

### 2.5 Комментарии — только WHY (🟢 NICE-TO-HAVE)

Комментарий, пересказывающий код, — заменить на имя/выделение метода.
Комментарии резервируются под неочевидные причины, кросс-ссылки
(`file:line`) и решения, которые будущий читатель мог бы откатить.

### 2.7 Обработка ошибок: бизнес vs системные; без голых `except` (🔴 MUST)

Ожидаемые/бизнес-ошибки — явные типизированные исключения (например,
`DialogOverwriteBlocked` → HTTP 4xx). Системные ошибки ловятся узко. Голый
`except Exception: pass` допустим ТОЛЬКО в best-effort инструментальных путях
(feedback, spend, traces) — и обязан быть закомментирован как таковой. Никогда
не глотать ошибки молча в основном бизнес-потоке (R11.1).

### 2.8 Structured logging; без лог-спама в циклах (🟡 SHOULD)

Логировать события на уровне use-case, ошибки — на уровне инфраструктуры.
Не логировать по каждому элементу в hot-циклах — использовать счётчики/
агрегаты (R11.3). Логи — в stdout через `logging_config.py`.

### 2.9 Доменные имена, не «plumbing»-суффиксы (🔴 MUST)

Использовать Ubiquitous Language финансовой отчётности. Избегать суффиксов
`Manager`, `Handler`, `Helper`, `Processor`, `Data`, `Info` — имя должно
говорить, какую реальную сущность представляет символ. (Приватные `_…` —
это маркер видимости, не имя концепта.)

## 3. Импорты

### 3.1 Lazy-импорты — только три причины; НЕ поднимать и НЕ добавлять без нужды (🔴 MUST)

Lazy (функциональные) импорты допустимы ровно для трёх причин:
1. тяжёлые модули (`import fitz` — PyMuPDF медленный);
2. опциональные/дополнительные зависимости (`try: import sentry_sdk`);
3. разрыв циклических импортов.

Следствия для обоих направлений правок:
- **НЕ поднимать** существующий lazy-импорт, не проверив причину (см. три причины выше): при сомнении — оставить inline.
- **НЕ добавлять** lazy-импорт «ради удобства»: PyInstaller собирает только то, что видит статический анализ. Опциональные драйверы (`boto3`, `psycopg`) концентрируются в одном именованном access-модуле (`storage/client.py`, `storage/rdb.py`, DAO) с комментарием `# lazy — optional driver`.

### 3.2 Не удалять «неиспользуемый» импорт без проверки сайд-эффектов (🔴 MUST)

Некоторые импорты существуют ради сайд-эффектов: регистрация класса, патч
модуля, наполнение реестра. Проверка: `grep -rn "symbol" src/ --include="*.py"`
— если символ только в импортирующем файле, удаление безопасно; если в
`__init__.py` или реестрах — оставить с `# noqa: F401`.

### 3.4 Порядок импортов (🟡 SHOULD)

stdlib → third-party → local, внутри групп по алфавиту. Автоматически —
`ruff check --fix`.

## 4. Роуты и слой данных

### 4.1 Тонкие роуты; без накопления логики в хендлерах (🟡 SHOULD)

Эндпоинт декодирует+валидирует запрос и делегирует. Он НЕ накапливает сырые
SQL, блокировки, запись файлов или ветвления по бэкенду — это путь от
300-строчного хендлера к 1000-строчному монолиту. Работу выполнять в
одно-ответственном классе (например, `storage/dao.py::SqlDao`), роут вызывает
один тонкий метод.

**Запах**: `if settings.database_url:` + `text(...)` + guard-логика внутри тела
роута вместо делегата.

### 4.2 Нет сырого SQL в роутах; централизовать в data-access слое (🔴 MUST)

`sqlalchemy.text(...)`, диалект-специфичный SQL (`CAST(... AS jsonb)`),
advisory locks, атомарные инкременты — в ОДНОМ data-access классе
(`storage/dao.py`), не копипастом по роутам. Роуты вызывают тонкие методы и
мапят доменные исключения (например, `DialogOverwriteBlocked`) на HTTP-коды (409).

**Правильно**: `dao.add_spend(uid, cost)` — SQL, блокировки и guard в DAO.
**Нарушение**: `text("UPDATE users SET spent_usd=spent_usd+:cost")` в `billing.py`.

## 5. Рефакторинг и жизненный цикл

### 5.1 Не удалять сайд-эффект стартапа без замены (🔴 MUST)

При сплите монолитного startup (например, `warmup()` или `on_event("startup")`)
явно перечислить каждый сайд-эффект и убедиться, что он сохранён в новой
структуре. Чеклист: (1) список всех вызовов старого startup; (2) сверка с новым
lifespan — каждый вызов имеет match; (3) если вызов убран намеренно — почему,
в сообщении коммита.

**Нарушение**: `recover_orphan_runs()` и `_email_intake.start()` были в старом
`warmup()`, но не появились в новом `lifespans.py`.

### 5.2 Проверить ВСЕ внешние ссылки перед удалением публичного модуля (🔴 MUST)

Перед удалением Python-файла, импортируемого где-либо, — поиск по всему репо и
ВСЕМ типам файлов, не только `.py`:

```bash
grep -rn "old.module.path" --include="*.py" --include="*.sh" \
  --include="*.md" --include="*.yml" --include="*.toml" .
```

Grep должен вернуть 0 результатов ДО удаления файла. Включая docs/, deploy/,
web/, scripts/.

### 5.3 Сохранять git-историю через `git mv` (🟡 SHOULD)

При перемещении файлов использовать `git mv`, чтобы `git log --follow`
отслеживал историю. `git rm` + `git add` ломает blame.

### 5.4 Новый файл < 300 строк, если нет явной доменной границы (🟢 NICE-TO-HAVE)

Роут-модули должны быть < 300 строк. Если файл растёт — выносить
под-роуты/хелперы.

## 6. Тесты

### 6.1 Все тесты — изолированно в Docker (🔴 MUST, D19)

Локальный `.venv` для тестов не использовать (сломанная пара torch/
transformers — исторический артефакт; torch больше не зависимость). Тесты
запускаются в `finengine-backend:latest`:

```bash
docker run --rm -v "$PWD:/app" -w /app --add-host host.docker.internal:host-gateway \
  finengine-backend:latest sh -c "pip install -q pytest pytest-asyncio && \
  FINENGINE_DATABASE_URL='postgresql+psycopg://finengine:finengine@host.docker.internal:5432/finengine' \
  FINENGINE_OPENSEARCH_URL=http://host.docker.internal:19200 \
  python -m pytest <paths> -q"
```

### 6.2 Тесты на реальной инфраструктуре, без компромиссов (🔴 MUST, D23)

Поведение тестируем так же, как в проде: нужна БД — реальный Postgres, нужны
векторные хранилища — реальный OpenSearch. НИКАКИХ файловых или
empty-config компромиссов (никаких `database_url=""` / `vector_backend="faiss"`).
Тесты, которым реально нужна инфраструктура, — `pytest.skip` с понятной причиной.

### 6.3 Тестировать реальную реализацию; без моков ради моков (🟡 SHOULD)

Моки не использовать без необходимости — тестировать реальную реализацию.
Вопрос ревьюера: «принял бы это CI?» (Моки допустимы там, где реальная
инфраструктура невозможна — например, детерминированный in-test fake для
эмбеддинг-провайдера.)

### 6.4 Тест стартап-сайд-эффектов и smoke-тест роутов (🟡 SHOULD)

После сплита startup-функции — тест, что все ожидаемые сайд-эффекты сработали
(`TestClient`). После рефакторинга роутов — smoke-тест, бьющий каждый роутер
(пропущенный `include_router` или неверный префикс должны падать быстро).

## 7. Документация

### 7.1 Обновлять ВСЕ ссылки при переименовании публичного модуля (🔴 MUST)

README, CONTRIBUTING, ONBOARDING, ARCHITECTURE, CLAUDE.md, AGENTS.md, scripts,
configs. Grep должен вернуть 0 результатов (см. 5.2).

### 7.2 Команды в доках должны быть исполняемыми (🟡 SHOULD)

Любая shell-команда в документации — copy-paste исполняемая из корня репо.
Проверить, что путь модуля существует.
