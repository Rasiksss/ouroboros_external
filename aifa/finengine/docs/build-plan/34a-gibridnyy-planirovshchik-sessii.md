# Гибридный планировщик — разбивка на сессии Claude Code

Реализация плана `34-gibridnyy-planirovshchik-dynamic-run.md` (дальше — **План**) за шесть
сессий. Каждая сессия:
- даёт работающий кусок функционала с тестами;
- укладывается в 150–200 тыс. токенов;
- после неё идёт отдельная сессия ревью со свежим контекстом.

## Как пользоваться

1. Открыть **новую** сессию Claude Code в корне репозитория и вставить промпт реализации части.
2. После её завершения открыть **ещё одну новую** сессию и вставить промпт ревью этой части.
   Ревью в отдельной сессии проводится намеренно: автор кода не проверяет сам себя, а свежий
   контекст не несёт допущений, сделанных при реализации.
3. Переходить к следующей части только после ревью без блокирующих замечаний.
4. Перед частью 6 — выкатить код частей 1–5 на dev. Выкатку делает **агент** (сессия) по сигналу владельца
   «выкатывай», способом из CLAUDE.md, раздел 7а; prod не трогать. `FINENGINE_WORKSTATION_URL` на dev уже
   задан в окружении backend (`http://workstation-svc:8080`, проверено 01.10.2026); если его нет — задать
   в dev-окружении (План, 4.4).

| Часть | Что появляется | Оценка токенов |
|---|---|---|
| 1 | `DynamicArtifact` хранится в `Case`; backend исполняет код в комнате станции | ~100 тыс. |
| 2 | Временный атом с готовым кодом работает внутри обычного графа | ~150 тыс. |
| 3 | Автор атомов пишет и чинит код по контракту; атом-загрузка скачивает публичный файл | ~140 тыс. |
| 4 | Цикл `DynamicRun` проходит сценарий из нескольких ходов на подставных моделях; ход может включать сценарии AIFA (исполнитель подставной) | ~180 тыс. |
| 5 | Цикл подключён к чату вместо П8, П8 удалён; сценарии исполняются настоящим путём чата | ~170 тыс. |
| 6 | Живая проверка на dev с реальной моделью и комнатами станции, доводка промптов, записанные прогоны становятся регрессионными тестами | ~130 тыс. |

## Бюджет токенов и чтение

Сессия читает: `CLAUDE.md`, разделы Плана своей части, названные файлы кода в указанных
диапазонах строк и `docs/build-plan/34-status.md` (журнал прошлых частей). Старые планы,
методика срезов и `Nedodelano.md` не читаются и не дополняются: План самодостаточен, а нужное из
старого кода описано в его разделе 3. Исключения — `01-nerushimye-resheniya.md` (короткий
список продуктовых решений) и правила кода проекта `docs/rules/coding_standards.md`, которые
читаются только в сессиях ревью.

## Как здесь устроены тесты

- **Хранилище `Case`** в тестах — SQLite во временном каталоге, как в
  `tests/integration/test_case_runtime_sqlite.py`. Postgres не нужен.
- **Остальные хранилища** (документы, диалоги и т.д.) требуют Postgres: без
  `FINENGINE_TEST_DATABASE_URL` их тесты пропускаются с причиной — это не падение. Базовая линия
  фиксирует и число пропусков.
- **Комната станции** локально недоступна. Код атомов в тестах исполняет фикстура `local_room`
  (`tests/dynamic_run/conftest.py`): она подменяет `sealed_room.run_code` запуском той же точки
  входа `_room_entry.py` локальным интерпретатором. Клиент HTTP-API станции проверяется на
  `httpx.MockTransport`.
- **Живые вызовы** (реальная модель, реальная комната) — только тестами с условием пропуска
  по переменной окружения: `FINENGINE_WORKSTATION_URL` для комнаты, `AIFA_LIVE_MODEL=1` для
  модели. По умолчанию они пропускаются.

## Два вида ревью

**Вертикальное** — один путь сверху вниз. Берётся функционал части и прослеживается реальным
вызовом от точки входа до записи в хранилище. Проверяется:
- работает ли путь на самом деле, а не только в моках;
- проверяют ли тесты поведение, а не реализацию;
- обработаны ли ошибки на каждом слое;
- что увидит следующий слой.

**Горизонтальное** — поперёк слоя. Новый код сравнивается с соседним существующим кодом того
же уровня. Проверяется:
- стиль и имена;
- повторное использование уже существующих функций вместо копий;
- одинаковая обработка ошибок;
- отсутствие дублирования;
- соблюдение правил из раздела 8 Плана;
- соблюдение правил проекта: `docs/rules/coding_standards.md`, разделы 2, 3 и 5 (в том числе
  «нет вложенных функций», доменные имена, ленивые импорты, удаление модулей);
- не сломаны ли соседние модули и их тесты;
- нет ли мёртвого кода и лишних абстракций.

## Общие правила для всех частей (уже включены в промпты)

- **Ветка.** Вся работа по гибридному планировщику — в одной ветке `feature/Claw-v2-1.0` (решение
  владельца 01.10.2026, CLAUDE.md, раздел 8). Отдельные `hybrid/pN-…` не заводим; части различаются
  коммитами.
- **Базовая линия тестов.** В начале сессии прогнать тесты затрагиваемых областей и записать, что
  уже падает и что пропущено. В конце — сравнить. Значение имеют только **новые** падения. В
  репозитории есть известные красные тесты, их не чинить.
- **Порядок работы.** Сначала тесты, потом код, осмысленные коммиты.
- **Незавершённое.** Всё, что не сделано, — в `docs/build-plan/34-status.md`, раздел
  «Часть N»: что не сделано, почему, следующий шаг. Других журналов не ведётся.
- **Номера строк в промптах** сняты с кода 30.09.2026. После правок прошлых частей они могут
  сдвинуться на несколько строк: это ориентир, а не точный адрес.

## Часть 1. `DynamicArtifact` и комната станции

**Функционал.** Результат временного атома можно сохранить в `Case` под его `dyn:*`-типом и
найти на следующем шаге через `AvailableIndex`. Backend исполняет произвольный код в
запечатанной комнате станции через её HTTP-API и возвращает результат или понятную ошибку.

**Разделы Плана:** 2.5, 3, 5.1, 5.2, 5.7 (только `_payload_output_type`), 5.11, 9 (шаги 1–2).

**Тесты:**
- `tests/dynamic_run/test_dynamic_artifact.py`:
  - валидатор `dyn:`;
  - roundtrip через хранилище `Case` на SQLite;
  - поиск в `AvailableIndex` по `dyn:*`;
  - соседние артефакты читаются как раньше;
  - `EphemeralAtomSource` сохраняется и читается, в том числе с пустым `code`.
- `tests/dynamic_run/test_room_entry.py` — точка входа локальным интерпретатором:
  - успешный результат;
  - исключение → код 1 и traceback в `stderr`;
  - NaN → ошибка;
  - `run()` вернула не `dict` → ошибка;
  - `print` в коде атома не попадает в `stdout`;
  - в тексте точки входа нет слов `sudo`, `mount`, `iptables`, `docker`, `podman`.
- `tests/dynamic_run/test_sealed_room.py` — клиент на `httpx.MockTransport`:
  - порядок вызовов: создание комнаты → `exec` → `terminate`;
  - тело `exec`: `python3 -I -c <точка входа>`, `cwd=/workspace`, пустой `env`, `stdin` в base64
    раскодируется в `{code, inputs}`;
  - у каждого вызова свой `X-Session-Id`;
  - комната закрывается и при HTTP-ошибке `exec`;
  - `timedOut`, ненулевой `exitCode` (хвост `stderr`), вывод больше лимита, не JSON → ошибка;
  - HTTP 409 от сервиса → понятная ошибка, а не исключение;
  - пустой `FINENGINE_WORKSTATION_URL` → ошибка без обращения к сети;
  - живой тест против настоящей комнаты — пропускается без `FINENGINE_WORKSTATION_URL`.
- `tests/dynamic_run/conftest.py`: фикстура `local_room` (понадобится с части 2) и условия
  пропуска живых тестов.

## Часть 2. Временные атомы с кодом внутри графа

**Функционал.** Временный атом с **заранее написанным** кодом (модели ещё нет) становится
обычным `AtomDef`. Ему нужен `ExtractedMetric` — `GraphPlanner` сам достраивает извлечение с
обязательными гейтами. Атом исполняется в комнате станции (в тестах — `local_room`), результат
ложится в `Case` как `DynamicArtifact` с правильным `origin`. Исправленная версия атома не
подменяется результатом старой.

Атомы-загрузки в этой части описаны контрактом (`AtomRequest.url`, `check_request`), но их
исполнитель и `download_public_file` — часть 3.

**Разделы Плана:** 3, 5.3 (без `_download` и `_download_profile`), 5.7 (`with_atoms`), 5.8, 8,
9 (шаг 3).

**Тесты:**
- `tests/dynamic_run/test_ephemeral_atoms.py`:
  - каждое правило `check_request` — отдельный отрицательный тест, включая правила загрузки
    (загрузка с `requires`, не-http адрес) и атом с кодом без `requires`;
  - стабильность и изменение `version`;
  - поля `to_atom_def` для атома с кодом;
  - вычисление `origin`;
  - `group_inputs`;
  - `_execute` не передаёт в код `ctx.inputs` — текст и байты документа;
  - нарушение схемы результата → ошибка узла.
- `tests/dynamic_run/test_ephemeral_in_graph.py` на подставных атомах извлечения из существующих
  тестовых фикстур:
  - граф `eph`-атома содержит путь извлечения и гейты;
  - исполнение через `CaseRuntime.with_atoms(...)` кладёт `DynamicArtifact` в `Case`;
  - повторный план находит его листом и не исполняет заново;
  - новая версия атома делает старый результат несовместимым;
  - `generated`-атом под профилем без `code_execution` или с сетью → `SandboxViolation` → узел
    `blocked`;
  - план и исполнение через один снимок `with_atoms` проходят сверку `registry_fingerprint`.

## Часть 4. Цикл `DynamicRun`

**Функционал.** Цикл ведёт задачу по ходам:
- планировщик отвечает JSON-решением;
- новые атомы с кодом пишет автор, атомы-загрузки создаются сразу;
- ход собирается через `with_atoms` + `plan_steps` и исполняется;
- итог хода возвращается планировщику;
- `finalize` ссылается только на существующие артефакты;
- лимиты останавливают цикл с понятной причиной;
- ход может содержать `scenarios` — стандартные задачи AIFA текстом. `DynamicRun` исполняет их до
  шагов хода через переданный извне `run_scenario` (План 2.4, 5.6). В этой части исполнитель
  подставной, настоящий появится в части 5.

Проверяется сценарием из Плана (2.3) на подставных моделях и подставных атомах извлечения, без
сети: загрузка идёт через `httpx.MockTransport`, код атомов исполняет `local_room`.

**Уточнение к Плану (5.9).** Проверка «все шаги ведут к корню» не удаляется из `plan_with_atoms`

1. **Сбой станции — не отказ автора.** `AtomAuthor.write` возвращает `(None, StationFault(текст))`, если
   станция не настроена или не исполнила код (`StationFault` — подкласс `str`; отличать через `isinstance`).
   `_ensure_atom` в этом случае говорит планировщику «комната станции недоступна, код не проверить: …», а не
   «автор не написал код»; **не** записывает причину в `self.failures` (чинить код нечего) и не считает атом
   созданным. Причину в `failures` писать только для ошибок кода в графе. Повторять тот же ход бессмысленно,
   пока станцию не починят: что делать при повторе (например, `stopped` после двух таких итогов подряд) —
   решить в сессии и назвать в отчёте.
2. **`self.failures` снимается только после успеха.** В прежнем листинге 5.6 `failures.pop(...)` стоял до
   вызова автора: если автор не справился или упала станция, ошибка прошлого запуска терялась, и следующая
   починка шла вслепую. Брать `failures.get(...)`, удалять после принятого атома (листинг 5.6 исправлен).
3. **Вызов из потока.** `write()` и `_ask_planner` используют `asyncio.run`, `DynamicRun.run` синхронный.

   ответила» и спишет попытку. Вызывающий (часть 5) обязан звать `run` через `asyncio.to_thread`. В этой части —

## Часть 5. Подключение к чату и удаление П8

**Функционал.** Запрос из чата, для которого детерминированный путь не собрал граф, идёт в
`DynamicRun`:
- в UI приходят графы ходов (`plan_graph` / `node_run`);
- при `finalized` приходят карточки типизированных результатов и манифест для диспетчера чата;
- при `gave_up` / `stopped` — типизированный отказ с тем, что успели получить;
- сценарии из ходов планировщика исполняются настоящим путём чата (`ScenarioChannel`:
  `parse_message` → `execute_routed_goal(allow_dynamic=False)`). Вложенного цикла нет,

## Часть 6. Живая проверка и доводка промптов

**Функционал.** Цикл проходит задачи на dev: реальная модель, реальные комнаты станции,
публичный отчёт. Записанные ответы моделей из удачных и показательных прогонов становятся
регрессионными тестами: проигрываются без сети. Промпты планировщика и автора доводятся по
реальным ошибкам — только теми правками, которые подтверждены прогонами.

**Предусловие.** Владелец дал сигнал «выкатывай» (CLAUDE.md, 7а); код частей 1–5 выкатывает на dev сама
сессия до начала прогонов; в окружении backend dev задан `FINENGINE_WORKSTATION_URL`. Сессия не пушит
(без явного разрешения) и не трогает prod.

**Как гоняем.** Два уровня:
- **Уровень цикла.** Скрипт `tests/dynamic_run/live/run_on_stand.py` исполняется внутри
  контейнера backend dev: `ssh … docker exec -i finengine-backend-1 python - < скрипт`, по
  образцу `tests/run_on_stand.sh`. Скрипт оборачивает `finengine.llm.openrouter.complete`
  записью всех вызовов (кто вызвал, промпт, ответ, токены), разбирает запрос через
  `parse_message` и зовёт `execute_routed_goal` для документа, уже загруженного на dev. Печатает
  JSON: вызовы моделей, события, манифест, время. В код продукта ничего для записи не
  добавляется.
- **Уровень чата.** Тот же запрос через API dev по образцу
  `docs/qa/compound-metric-matrix-2026-09-29/rerun-after-clean-redeploy-2026-09-29/run_smoke.py`
  (логин, `/chat/turns`, события прогона): что видит UI.

**Известное из части 3 (проверять прогонами, править только по фактам).** Источник — `34-status.md`,
«Часть 3», живой прогон на dev 01.10.2026:
- схема класса контракта в промпте автора обрезана до 3000 символов и кончается раньше `scalar_fact`;
- сокращение реального входа (`_REAL_INPUT_PREVIEW`, 6000 символов) режет JSON по символам: один большой
  `payload.text` загрузки вытесняет остальные группы (например, `ExtractedMetric`) — при проявлении сокращать
  по группам;
- автор без реальных входов не справлялся (пустой `example_inputs` против правила 4); в части 4 такой случай
  закрыт кодом (автор не вызывается без входов) — убедиться, что планировщик следует правилу из 6.1 и не
  пытается описать атом с кодом в том же ходе, что и получение его входов;
- имена концептов автору теперь даны (часть 4) — проверить, что регистр больше не угадывается.

**Задачи для прогона** — проверка механики, а не продуктовые сценарии:
1. задача, решаемая только атомами каталога за два и более хода;
2. задача, где часть — стандартный процесс AIFA: планировщик должен выбрать сценарий, а не
   собирать его из атомов (например, «извлеки показатели и сопоставь с внешним рядом»);
3. задача, требующая атома с кодом над извлечёнными показателями;
4. задача с атомом-загрузкой публичного ряда и отдельным атомом сопоставления;
5. задача, где источник недоступен (неверный адрес), — ожидается `give_up`, а не переписывание
   атома по кругу.

Каждая задача — три прогона.

**Тесты:** `tests/dynamic_run/test_replay.py` проигрывает записанные прогоны: ответы моделей из
фикстур, атомы извлечения — подставные, код — `local_room`, загрузка — `httpx.MockTransport` с
записанным файлом. Проверяются статус, число ходов и ссылки `finalize`.
