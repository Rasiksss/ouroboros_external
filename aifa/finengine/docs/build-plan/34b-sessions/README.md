# Промпты сессий доводки гибридного планировщика (части 7–12)

План: `docs/build-plan/34b-gibridnyy-planirovshchik-dovodka.md` (дальше — **План доводки**).

## Как пользоваться

1. Открыть **новую** сессию Claude Code в корне репозитория и вставить содержимое блока
   из файла `part-NN-impl.md`.
2. После завершения открыть **ещё одну новую** сессию и вставить блок из `part-NN-review.md`.
   Ревью в отдельной сессии — намеренно: автор не проверяет сам себя.
3. К следующей части — только после ревью без блокеров.
4. До старта ответить на вопросы раздела 8 Плана доводки и вписать ответы в промпт части
   (строка «РЕШЕНИЯ ВЛАДЕЛЬЦА») либо в сам План доводки.

## Контракты между слоями и полные прогоны (части 9–12)

**Зачем.** Ревью части 8 (`34-status.md`, «Часть 8 — ревью») показало: все шесть найденных проблем
жили не внутри функций, а на стыках — промпт ↔ код, гейт ↔ модель, финализация ↔ сводка, код ↔
трасса, сводка ↔ пользователь. Тесты части были зелёными, потому что каждый слой проверялся с
подставными соседями. Поэтому в промптах частей 9–12 добавлены два обязательных вида проверки.
Это часть критерия «готово», а не остаток: если бюджет кончается, сначала доводятся они, а
второстепенное уходит в `34-status.md`.

**Контрактный тест** — проверка стыка между двумя слоями. Правила:
1. Стык назван: «производитель → потребитель» и что именно обещано (поле, порядок событий, текст
   сообщения, список типов, формат числа).
2. Тест берёт **настоящий выход** производителя (вызов его кода либо общая фикстура
   `tests/dynamic_run/fixtures/sse/`), а не вручную собранный объект, и проверяет то, что получит
   **потребитель**: что нарисует экран, что увидит модель в промпте, что решит агент.
   Подставными остаются только внешние границы: модель, станция, сеть.
3. Тест падает при поломке **любой** из сторон. Проверка обязательна: откатить правку
   производителя (или потребителя) локально, убедиться, что тест падает по этой причине, вернуть.
4. Один источник истины: списки типов, словари подписей, форматы живут в одном месте; контрактный
   тест сверяет оба слоя с ним, а не две копии друг с другом.
5. У потребителя несколько путей (чат и сводка; детерминированный путь и цикл; живой поток и
   реплей) — контракт проверяется на каждом.
6. Сообщение, которое читает модель (отказ гейта, итог хода), — тоже контракт: тест проверяет, что
   из текста следует действие, а не только что текст есть.

**Полный прогон** — сквозная проверка того, что устранена именно проблема, на которую направлена
часть:
1. Идёт от настоящей точки входа (`execute_routed_goal`, обработчик хода чата, редьюсер
   frontend) до того, что видит пользователь. Подставные — модель, станция, сеть; исполнитель и
   хранилище (SQLite `Case`) настоящие.
2. По каждому дефекту части — прогон сценария из handoff (S0–S5), воспроизводившего дефект. Сначала
   показать, что до исправления прогон красный (тесты до кода), затем зелёный.
3. Утверждения — о пользовательском исходе («в сообщении есть формула и CV»), а не о
   внутренностях. Критерий — «Готово, когда» части и соответствующий пункт раздела 3 Плана доводки.
4. До части 12 выкатки нет: прогоны локальные. Если экран глазами проверить нельзя (render-теста
   компонента нет), сказать об этом прямо и перечислить, что должен посмотреть владелец.
5. Результат — в `34-status.md`, раздел части, двумя таблицами: «Контракты» (стык / обещание / тест /
   падает ли при поломке стороны) и «Полные прогоны» (дефект / сценарий / команда / до / после).

**В ревью** к этому добавляется: найти стыки, которых нет в таблице; самому сломать одну сторону
каждого контрактного теста и убедиться, что он падает; независимо повторить полные прогоны и
сравнить с журналом. Стык без теста — по умолчанию «важно».
