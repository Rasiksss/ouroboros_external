# Заявка на инфраструктуру: Ouroboros MU + AIFA + Workstation

Дата: 03.11.2026. Основание: локальный файл `../../html`, инструкция AEF v8 от
30.09.2026, и текущие исходники репозитория. Это инструкция по заказу ресурсов,
а не подтверждение работоспособности развёртывания. Ресурсы не создавались,
подключения и нагрузочные испытания не выполнялись.

Фронт AIFA перенесён в `deferred/aifa-web/`; его развёртывание отложено.

## 1. Целевая схема и границы заявки

MU означает отдельных пользователей с отдельными чатами, задачами и данными
в одном общем агентном сервисе. Отдельный экземпляр агента на каждого пользователя
не нужен. Корпоративная инструкция реализует этот сервис несколькими компонентами.

| Компонент | Назначение | Имя в примере AEF | Python-модуль |
|---|---|---|---|
| Transport | Приём сообщений, WebSocket/HTTP, доставка ответов и файловые API | transport | multiuser_config.transport.browser |
| Supervisor | Приём и организация задач, очередь, обработка событий выполнения | supervisor | multiuser_config.supervisor |
| Agent Runtime | Агентный цикл, модели, инструменты | gigaagent | multiuser_config.agent_runtime.run |
| Background Memory | Фоновая обработка памяти | memory | multiuser_config.background_memory.run |
| Config Registry | Реестры агентов, чатов, настройки владельцев | config-registry | multiuser_config.config_registry |
| AIFA Backend | Авторизация, проекты, документы, анализ и инструменты службы | Отдельное приложение | Образ из aifa/ |
| Workstation | Изолированное выполнение кода и файловые сессии | Отдельное приложение | Образ workstation |

При одной реплике каждого — семь прикладных Pod. Это план первого функционального
стенда, не схема гарантированной высокой доступности. У каждого Pod могут быть
дополнительные контейнеры платформы/mesh. Внешние PostgreSQL/S3/Kafka/Redis сюда
не входят. HTML дополнительно показывает BFF/helper: его роль относительно входа
через AIFA необходимо согласовать, автоматически добавлять второй вход не следует.

Текущий `compose.corporate.yml` запускает монолитный Ouroboros; для этой схемы MU
нужно подготовить отдельные конфигурации AEF. Один образ ядра может использоваться
пятью компонентами с разными командами.

## 3. PostgreSQL

### 3.1. Что заказать

Можно использовать один существующий корпоративный кластер PostgreSQL.
Рекомендуемое разделение — отдельные базы и роли приложений:

| База, условное имя | Роль, условное имя | Действие |
|---|---|---|
| ouroboros | ouroboros_app | Таблицы уже созданы: проверить доступ, версию схемы и настройки |
| finengine | aifa_app | Подготовить 22 таблицы AIFA и их ограничения/индексы |
| workstation | workstation_app | Применить миграции Workstation |

Полный состав базы `finengine` вынесен в
[«База finengine: все 22 таблицы»](FINENGINE-DATABASE.md): 181 SQL-атрибут,
типы PostgreSQL, допустимость NULL, значения по умолчанию приложения, назначение
полей, первичные ключи, индексы, UNIQUE и объявленные внешние ключи.
Это приложение к пункту 3.1 для передачи DBA; девять настроек подключения AIFA
не означают девять отдельных баз. Создать нужно структуру целиком по текущей
версии моделей, а не только пустые таблицы с совпадающими именами.

Альтернатива — отдельные схемы и роли в общей базе. Для AIFA схема задаётся
`FINENGINE_PG_SCHEMA`; она должна существовать до инициализации таблиц.
Не выдавать приложениям superuser и доступ к чужим базам/схемам без необходимости.

### 3.2. Параметры, которые должна выдать команда БД

- DNS/порт подключения и порядок переключения при отказе.
- Имя базы, имя схемы и её владелец.
- Логин; пароль передаётся через секреты.
- Режим TLS, CA, требования к клиентским сертификатам.
- Лимиты соединений для каждой роли и доступный бюджет соединений.
- Ограничения длительности запросов/транзакций и особенности connection pooler,
  если он используется. Совместимость с приложением должна быть проверена.
- Резервное копирование, срок хранения, RPO/RTO и порядок восстановления.

DSN приложения — адрес подключения к существующей БД, не имя контейнерного образа:

```dotenv
OUROBOROS_RUNTIME_DB_URL=postgresql+psycopg://ouroboros_app:PASSWORD@PG_HOST:PORT/ouroboros
FINENGINE_AUTH_DATABASE_URL=postgresql+psycopg://aifa_app:PASSWORD@PG_HOST:PORT/finengine
DATABASE_URL=postgresql+asyncpg://workstation_app:PASSWORD@PG_HOST:PORT/workstation
```

Это шаблоны. Спецсимволы паролей нужно корректно кодировать для URL. Настройки TLS
добавляются по требованиям выданного сервиса; не отключать проверку сертификата
для обхода ошибки. В mesh фактический hostname/порт клиента может отличаться от
реального endpoint — их должен согласовать владелец интеграции.

### 3.3. Таблицы AIFA и настройки подключения

Все девять URL ниже могут указывать на одну выделенную базу AIFA.

| Переменная | Таблицы |
|---|---|
| FINENGINE_AUTH_DATABASE_URL | users, invites |
| FINENGINE_DOCUMENTS_DATABASE_URL | document, document_chunk |
| FINENGINE_DIALOGS_DATABASE_URL | dialog_owner, dialog |
| FINENGINE_RUNS_DATABASE_URL | station_run |
| FINENGINE_STATE_DATABASE_URL | state, analysis_case, analysis_case_document, analysis_case_artifact, analysis_plan_run, analysis_plan_node_run, analysis_override_event, subject_profile_history |
| FINENGINE_JOURNALS_DATABASE_URL | journal |
| FINENGINE_ARTIFACTS_DATABASE_URL | artifact |
| FINENGINE_SCENARIOS_DATABASE_URL | scenarios |
| FINENGINE_NEWS_DATABASE_URL | sources, raw_items, digest_runs, digest_items |

Структура определяется моделями текущей версии в `../finengine/src/finengine/`:
`auth/db.py`, `store/{documents,dialogs,runs,state,journals,artifacts,cases}.py`,
`skills/scenarios/store.py`, `skills/news/db.py`. Не создавать только таблицы без
первичных ключей, дополнительных индексов, уникальности и объявленных FK.

AIFA использует `create_all()` при инициализации хранилищ; это не полноценное
обновление уже существующих таблиц. Команда `python -m finengine.store.ensure_schema
--apply` создаёт схему, а не весь набор таблиц. `python -m
finengine.store.migrate_cases` относится к таблицам кейсов. Установочный шаг должен
подготовить все хранилища текущей версии до открытия доступа пользователям.

Если DDL рабочей роли запрещён, согласовать отдельную установочную роль и
проверить запуск с ограниченной рабочей ролью: приложение содержит проверки
структуры и отдельные обновления. Для обычной работы нужны CONNECT/USAGE,
SELECT/INSERT/UPDATE/DELETE и необходимые права на последовательности.

### 3.4. Ouroboros и Workstation

Для ядра проверить Alembic head относительно образа. Уже существующие таблицы
не гарантируют соответствие новой версии. Общая схема должна быть доступна всем
пяти компонентам. Миграцию планировать как отдельный согласованный шаг.

В текущем `gigaagent/entrypoint.sh` есть автоматический `alembic upgrade head`.
При подготовке MU-манифестов определить, кто выполняет миграцию: не рассчитывать,
что пять одновременно запускаемых экземпляров сами обеспечат безопасный порядок.

Для Workstation нужны `sessions`, `audit_events` и служебная таблица Alembic.
Использовать его миграции. Метаданные сессий в PostgreSQL не заменяют файловую
систему rootfs, описанную ниже.

### 3.5. Соединения и объём

AIFA создаёт подключения для нескольких хранилищ, даже если URL одинаковые.
Компоненты ядра также имеют свои пулы. Лимит PostgreSQL нужно считать по сумме
пулов всех процессов и реплик, с запасом на миграции и probes, а не по числу людей.
Численный бюджет рассчитывает команда приложения совместно с DBA.

## 4. S3

### 4.1. Что заказать

Две приватные корзины на окружение, например `ouroboros-prod` и `aifa-prod`.
Это логические корзины существующего S3, не новые серверы и не Docker-контейнеры.

| Корзина | Данные | Кто получает credentials |
|---|---|---|
| ouroboros-prod | Пользовательские вложения и опубликованные файловые результаты | Компоненты ядра, которым нужны файлы |
| aifa-prod | Документы службы, извлечённый текст, OCR JSON, файлы источников и экспорта | AIFA Backend |

Оригиналы, проходящие через файловый каталог Ouroboros, AIFA читает через API
ядра. Не выдавать AIFA прямой доступ к корзине ядра только ради этой операции.
Структурированные результаты также сохраняются в SQL: S3 не заменяет PostgreSQL.

### 4.2. Что получить

- Endpoint из сети приложения, region и точное имя корзины.
- Access key/secret key и порядок их ротации.
- CA и требования TLS; сетевой доступ от клиентов.
- Квоту, ограничения размера объекта и особенности S3-совместимости.
- Срок хранения, versioning/backup и порядок восстановления.
- Если обязательно шифрование с корпоративным KMS — согласованную policy и
  необходимые дополнительные права; проверить совместимость реального хранилища.

Нужные операции текущих клиентов: `s3:ListBucket`, `s3:GetObject`,
`s3:PutObject`, `s3:DeleteObject`. Проверка HEAD объекта использует права чтения.
ListBucket выдаётся на корзину, остальные — на объекты. При ограничении префиксом
нужны согласованные object policy и условия ListBucket.

### 4.3. Размещение и хранение

AIFA создаёт ключи вида:

```text
documents/<doc_id>/<filename>
documents/<doc_id>/text.txt
documents/<doc_id>/idpocr.v2.json
users/<user_id>/projects/<project_id>/sources/...
```

Пример пространства пользовательских файлов ядра:

```text
tenants/<tenant>/<optional-prefix>/uploads/owners/<owner>/agents/<agent>/...
```

Папки создавать не нужно, это префиксы объектов. Корзины на каждого пользователя
не нужны. Не все служебные scopes ядра являются пользовательскими; изоляция
владельца для `uploads` не означает одинаковый способ разделения всех scopes.

У всех компонентов ядра должны совпадать bucket, tenant и prefix. Пространство
сверяется с записью в БД: перенос уже работающего окружения требует миграции.

Не включать короткий lifecycle удаления на всю корзину: в БД останутся ссылки
на исчезнувшие документы. Сроки хранения разделить по данным и согласовать с
очисткой приложения. Публичный доступ не требуется. `s3-init` не нужен: корзины
подготавливает корпоративная команда.

## 5. Kafka рабочих сообщений MU

### 5.1. Для чего

Kafka связывает отдельные процессы ядра: Transport передаёт сообщения Supervisor,
Agent Runtime публикует события, ответы возвращаются Transport, фоновая память
получает свои события. Пользователь/AIFA общаются с Transport по HTTP/WebSocket.
Kafka здесь не ограничивается трейсингом.

В HTML, раздел 3.3.2, явно задано `OUROBOROS_BROKER_BACKEND=kafka` и отдельное
подключение `cortex`. На схеме внешних сервисов указано `Kafka(mu) (broker)`.

### 5.2. Что заказать

Доступ к существующему Kafka-кластеру, пять топиков своего окружения и ACL.
Отдельный физический кластер на пользователя или на топик не требуется.

При `OUROBOROS_KAFKA_TOPIC_PREFIX=ouroboros-prod`:

| Топик | Назначение |
|---|---|
| ouroboros-prod.inbound | Входящие сообщения пользователей |
| ouroboros-prod.outbound | Ответы для доставки в чаты |
| ouroboros-prod.agent-events | События выполнения |
| ouroboros-prod.memory-events | События фоновой памяти |
| ouroboros-prod.task-stops | Сигналы остановки задач |

Читающие группы текущего кода включают:

```text
ouroboros-prod.inbound.supervisor
ouroboros-prod.agent-events.supervisor
ouroboros-prod.memory-events.background-memory
```

Потоки ответов и остановок также используются широковещательными читателями;
не считать, что все подписки сводятся только к трём consumer groups.

### 5.3. Что получить от Kafka-команды

- Bootstrap servers и правила сетевого подключения ко всем адресам брокеров,
  которые возвращает Kafka metadata, с учётом схемы mesh.
- Точные имена топиков; права Describe/Read/Write по нужным операциям и
  разрешения на соответствующие consumer groups. Создание топиков — установочный
  шаг администраторов, не обязательное право рабочей роли.
- Security protocol, SASL mechanism/credentials либо клиентские сертификаты и CA.
- Версию протокола для `OUROBOROS_KAFKA_API_VERSION` в формате MAJOR.MINOR.
  `3.9` из HTML — пример, не автоматически верное значение вашего сервиса.
- Partitions, replication factor, retention и лимиты сообщений — согласованную
  конфигурацию с эксплуатацией, а не значения по умолчанию без проверки.
- Метрики доступности, lag, диска, ошибок публикации и правила эскалации.

Текущий код явно использует partition 0. У топиков она должна существовать;
увеличение partitions не является готовым способом масштабирования этой версии.
Для рабочих потоков ориентироваться на хранение журнала с retention; не включать
компактацию без проверки семантики сообщений и ключей приложения.

В настройках клиента предел сообщения по умолчанию 33 554 432 байта. Согласовать
ограничения producer/broker/topic/consumer с выбранным прикладным пределом,
учитывая накладные расходы. Не требовать ровно тот же численный лимит на каждом
слое без проверки. Содержимое больших файлов хранится в S3.

Retention определяет, какое окно простоя читателя допустимо без исчезновения
непрочитанных сообщений. Kafka не обеспечивает автоматически отсутствие дублей
или гарантированное восстановление всей задачи: это зависит и от кода приложения.

## 6. Redis/RADISH в выбранной конфигурации не нужен

Кеш ядра отключён: OUROBOROS_SETTINGS_CACHE_BACKEND=none. Межпроцессные сообщения
MU идут через Kafka, настройки читаются из PostgreSQL. Redis/Radish не заказывать,
credentials и сетевые соединения для него не оформлять.

AIFA: одна реплика, один worker, FINENGINE_REDIS_URL пуст. При увеличении числа
реплик/worker потребуется отдельное решение общей шины; в текущую раскатку это
не входит. Redis-интеграция Workstation выключена (REDIS_ENABLED=false).
Удалить старые Redis URL из SecMan, если они там уже есть: файл имеет приоритет
над окружением.

## 7. Наблюдаемость: отдельные назначения Kafka

Рабочие пять топиков выше не заменяют инфраструктуру AEF-наблюдаемости.

| Блок HTML | Что запросить |
|---|---|
| AEF_TRACING_* | Подключение AEF tracing, топик, доступы и необходимые SDK-настройки |
| AGENT_SYSTEM_CONFIGURATION_KAFKA_* | Bootstrap servers, топик и права записи сведений о системе |
| FLUENT_BIT.APP_LOG | Кластер/топик и настройки доставки прикладных логов |
| FLUENT_BIT.ISTIO_LOGS | Доступ и настройки доставки mesh-логов/метрик |

Эти назначения могут использовать разные существующие кластеры. Часть endpoints
в примере относится к другим namespace; имена нельзя копировать как действующие.
В примере есть ссылка на имя кластера, которое надо сверить с объявленными
интеграциями: все ссылки должны разрешаться в целевой конфигурации.

Согласовать, какие подключения обязательны по правилам платформы. Сам отказ
телеметрии и отказ рабочего брокера — разные события с разным влиянием.
Логи/трейсы могут содержать пользовательские данные: доступ и сроки хранения
должны соответствовать принятым требованиям окружения.

## 8. Namespace, AEF и ресурсы

### 8.1. Заказ платформенной команде

- Namespace и разрешённый способ управления через AEF Operator.
- Service accounts/RBAC; полномочия команды на установку и просмотр диагностики.
- ResourceQuota/LimitRange и правила requests/limits.
- Внутренние Services, DNS, ingress/gateway, mesh и NetworkPolicy.
- Доставку секретов, CA и сертификатов, доступ registry для загрузки образов.
- Поддержку WebSocket и длительных HTTP/SSE-ответов.
- Записываемые временные каталоги для приложений и выделенный диск Workstation.

### 8.2. Числа из HTML — только пример

| Компонент | Реплики | CPU request/limit на Pod | RAM request/limit на Pod |
|---|---:|---|---|
| Agent Runtime | 4 | 500m / 1000m | 1024Mi / 2048Mi |
| Transport | 2 | 100m / 100m | 256Mi / 256Mi |
| Supervisor | 2 | 100m / 100m | 256Mi / 256Mi |
| Background Memory | 2 | 100m / 100m | 256Mi / 256Mi |
| Config Registry | 2 | 100m / 100m | 256Mi / 256Mi |

Суммарно только эти пять deployments: 12 Pod, requests 2.8 CPU / 6 GiB RAM,
limits 4.8 CPU / 10 GiB RAM. Без sidecar, AIFA, Workstation, helper и запаса на
rolling update. Это арифметика примера, не рекомендованная квота нашего стенда.

Для первого стенда — по одной реплике пяти компонентов, AIFA Backend с одним
worker, Frontend и один Workstation. Финальные ресурсы согласовать после проверки
старта и измерений. Квота должна учитывать sidecar и временное увеличение Pod
при обновлении. Requests не равны фактическому потреблению или гарантии вместимости.

До расчёта чисел определить: зарегистрированных/одновременных пользователей,
одновременные задачи и подзадачи, размеры документов/число страниц, время ответа,
срок хранения, требования к отказоустойчивости. WORKER_SLOTS — параллелизм задач,
а не число пользователей и не число Pod. Квоты моделей также ограничивают параллелизм.

## 9. Workstation: вычисления и временный диск

Заказать совместимое Linux-окружение для текущего sandbox-бинарника и образа,
проверить архитектуру CPU и поддержку механизмов изоляции ядром/политиками Pod.
Не считать, что любой Python-образ и любой seccomp-профиль подходят.

Нужны:

- Шаблон rootfs `/opt/workstation/template`.
- Записываемый каталог сессий `ROOTFS_ROOT`, сейчас `/tmp/workstation/sessions`.
- Лимиты CPU, RAM, процессов, времени выполнения и ephemeral storage.
- Очистка истёкших сессий и мониторинг диска/inodes.
- Запрет лишней исходящей сети песочницы, отсутствие секретов сервисов в rootfs.
- Проверка Landlock/seccomp и реально применяемых ограничений; декларация ENV
  сама по себе не доказывает, что ограничения активны.

Для первого стенда один экземпляр. PostgreSQL хранит метаданные, а rootfs лежит
на конкретном экземпляре. Несколько реплик требуют маршрутизации по сессии и
решения размещения файлов. При временном диске рестарт может потерять рабочую
сессию; сохраняемые результаты должны публиковаться в постоянные хранилища.
Если нужно продолжать сессию после рестарта — отдельно проектировать её сохранение.

AIFA также материализует файлы во временные каталоги: даже с S3 ей нужен writable
temporary storage. Размер диска включает оригиналы, распакованные/промежуточные
данные и несколько параллельных операций, а не только размер одного PDF.

## 10. Сеть и доверенная идентичность

| Откуда | Куда | Протокол/назначение |
|---|---|---|
| Пользователь | AIFA Frontend | HTTPS |
| Frontend/gateway | AIFA Backend | HTTP(S), API, загрузки, потоковые ответы |
| AIFA Backend | Transport/gateway ядра | HTTP(S)/WebSocket, чат и файловые API |
| Доверенный клиент/gateway | Config Registry | HTTP(S), API реестров и настроек |
| Agent Runtime | AIFA Backend | HTTP(S), внутренние инструменты |
| AIFA Backend и Agent Runtime | Workstation | HTTP(S), сессии, файлы, исполнение |
| Компоненты ядра | PostgreSQL ядра | PostgreSQL/TLS по выданной схеме |
| AIFA Backend | PostgreSQL AIFA | PostgreSQL/TLS |
| Workstation | PostgreSQL Workstation | PostgreSQL/TLS |
| Файловые клиенты ядра | S3 ядра | S3 API/HTTPS либо согласованный mesh endpoint |
| AIFA Backend | S3 AIFA | S3 API/HTTPS либо согласованный mesh endpoint |
| Участники брокера ядра | Kafka | Kafka/TLS/SASL по выданной схеме |
| Agent Runtime, Supervisor, Background Memory | Шлюз моделей | HTTPS API |
| AIFA Backend | Шлюз моделей | HTTPS API |
| Наблюдаемость | Корпоративные коллекторы/Kafka | По выданной интеграции |

Межкомпонентные адреса должны быть доступны из Pod. `localhost` внутри Pod — это
сам Pod, не соседний сервис. Порты 8000/8002/19096 из mesh-примеров не являются
универсальными реальными портами PostgreSQL/Redis/Kafka.

Перед ядром нужен доверенный вход. AIFA после аутентификации передаёт
`X-Ouroboros-Owner-Id` и `X-Ouroboros-Chat-Id`; внешнему пользователю нельзя
разрешать подставить чужие значения. Не публиковать внутренние API ядра/инструментов
без согласованной авторизации. Config Registry также требует доверенной идентичности.

Если AIFA использует один базовый URL ядра, внутренний gateway должен направлять
WebSocket/браузерные API и `/api/files*` в Transport, а API реестров — в Config Registry.
Не направлять весь трафик на probe-порт Agent Runtime.

Таймауты gateway согласовать с длительными задачами и потоками. HTML показывает
600 секунд между операциями обмена; это не универсальный предел длительности
агентной задачи. Нужны корректная работа streaming, лимиты upload и отсутствие
неподходящей буферизации. Для поиска/новостей заказать отдельный согласованный
egress или корпоративный поисковый API, если эти функции входят в запуск.

## 11. Шлюз моделей

Заказать OpenAI-совместимый API, доступный из сетей AIFA и ядра:

- Base URL и требования к TLS/аутентификации.
- Точные ID моделей, поддерживаемые инструменты/tool calling и streaming.
- Максимальный контекст/ответ, таймауты и ограничения запросов.
- Квоты requests/tokens/concurrent requests и ответственных за их изменение.
- Правила учёта нагрузки, доступные метрики и обработку 429/недоступности.

Модели нужны не только Agent Runtime: Supervisor имеет модельные операции,
Background Memory может обращаться к LLM. У AIFA есть собственные модельные вызовы.
Суммарную квоту считать по всей связке. Внешние OpenRouter/Cloud.ru не требуются,
если выдан подходящий корпоративный API; названия адаптеров в ENV не заменяют
проверку совместимости фактического шлюза.

## 12. Секреты и сертификаты

| Секрет/настройка | Потребитель |
|---|---|
| PostgreSQL credentials/сертификаты ядра | Компоненты ядра |
| PostgreSQL credentials AIFA | AIFA Backend |
| PostgreSQL credentials Workstation | Workstation |
| S3 credentials ядра | Файловые клиенты ядра |
| S3 credentials AIFA | AIFA Backend |
| Kafka credentials/сертификаты | Участники соответствующих потоков |
| LLM credentials | Компоненты с модельными вызовами |
| FINENGINE_AUTH_SECRET | AIFA Backend |
| FINENGINE_ADMIN_PASSWORD | Bootstrap администратора AIFA |
| AIFA_ENGINE_TOKEN | AIFA Backend и вызывающий инструменты Agent Runtime |
| OUROBOROS_CREDENTIALS_ENCRYPTION_KEY | Компоненты ядра, использующие защищённые данные |
| OUROBOROS_CHAT_ENCRYPTION_KEY при включении | Компоненты, работающие с зашифрованными сообщениями |
| Workstation-токены/настройки доступа | Соответствующие клиенты и сервис |

Ключи ядра постоянные и одинаковые на всех нужных репликах. Не генерировать их
при каждом рестарте; ротация требует совместимого плана. Ключ шифрования
credentials имеет требуемый приложением формат: 64 байта в base64.

Секреты не хранить в Git, заявках и общедоступных логах. Заказать путь в SecMan,
права service account, формат env/file, путь монтирования, обновление и перезапуск
при ротации. Настройки Workstation create-secret из env не считать доказательством
проверки всех ручек новым сервисом; проверка auth и сетевая изоляция обязательны.

## 13. Сборка внутри контура

Готовые внешние образы пользователь переносить не может. Нужны:

- Репозиторий исходников внутри контура и доступ CI.
- Корпоративный registry и права build/push/pull.
- Разрешённые базовые образы для Python, Node и sandbox/runtime Workstation.
- Внутренние зеркала Python/Node/OS-зависимостей, в том числе бинарных пакетов.
- Совместимые платформы сборки и исполнения; сборочные инструменты для sandbox.
- Credentials, CA и сетевой доступ build-агента к этим источникам.
- Согласованные проверки и публикация версий/дигестов артефактов.

Исходники ядра находятся в `gigaagent/`, AIFA — в `aifa/`, Workstation — в
`workstation/`. Пути `/` из исходного COMMON.yaml нужно адаптировать. Присутствие
исходников не означает готовность offline-сборки без зеркал зависимостей.

## 14. Настройка AEF Operator

1. `COMMON.yaml`: описать пять компонентов ядра, источники и сборку.
2. `agents/stand.yaml`: отдельные AGENT_NAME/AGENT_CUSTOM_ARGS, ENV, ресурсы,
   реплики; `/ready` и `/live` на настроенном порту, в примере 9090.
3. `integrations/stand.yaml`: реальные PG/S3/Kafka/model endpoints и mesh.
4. `namespace/stand.yaml`: namespace, SecMan, сертификаты, ingress и наблюдаемость.
5. Собрать дистрибутив через `buildDistrib.groovy`.
6. Установить через `cd_customResources.groovy`, передав CONFIG_REPO,
   CONFIG_BRANCH, DISTRIB, STAND, template_version и installTimeout.
7. При первой установке в новый namespace инструкция требует
   `updateRoleBindings=true` для прав и метки `aef.operator/managed: 'true'`.
8. Статус/ошибки проверять в AEFAgent/AEFMesh и фактических Pod/логах.

Раздел 7 HTML содержит альтернативу ArgoCD/Helmfile. Выбрать один согласованный
механизм управления. CI pipeline/Operator должны уже предоставляться платформой;
скрипты из описания не считать автоматически присутствующими в нашем репозитории.

## 15. Что не решается заказом инфраструктуры

**Обновление интеграции отдельного MU-runtime:** доверенный `aifa-engine`
подключён через общий startup-загрузчик, зарегистрированы 9 инструментов.
Локальные тесты проверяют compose_process, реальную регистрацию и доставку
контекста через HTTP route AIFA; бизнес-обработчик в HTTP-тесте тестовый.
Полный распределённый стенд с реальной моделью этим не проверен.

Примеры Operator находятся в `gigaagent/deploy/mu/`: 7 компонентов, команды,
broker/cache ENV и управление миграциями. Требуются реальные bindings и SecMan.

В HTML есть устаревшие/примерные значения: SQLite fallback ядра, пути исходников,
адреса чужих стендов, Sentinel ENV и отсутствующее включение Redis-кеша.
Текущий runtime требует PostgreSQL. Параметры памяти из HTML нельзя автоматически
переносить поверх согласованного AIFA-профиля, где distillation сейчас отключена.

## 16. Порядок подготовки и критерии готовности

### Этап A. Выдать ресурсы

- [ ] Namespace, AEF, права команды и service accounts.
- [ ] PG-подключения; схема ядра соответствует версии; AIFA/Workstation подготовлены.
- [ ] Две S3-корзины с отдельными policy и credentials.
- [ ] Kafka: пять рабочих топиков, ACL, доступы к брокерам.
- [x] Кеш ядра отключён; Redis/RADISH в выбранном профиле не требуется.
- [ ] Подключения наблюдаемости и моделей.
- [ ] Сеть, DNS, PKI и выдача секретов.
- [ ] Registry, зеркала зависимостей и сборочный pipeline.

### Этап B. Подготовить приложение

- [x] Подключена и локально проверена загрузка aifa-engine в отдельном Agent Runtime.
- [ ] Подготовлены MU-манифесты и маршрутизация входа AIFA.
- [ ] Согласованы миграции, профиль памяти, допуски навыков и инструменты.
- [ ] Workstation совместим с платформой и применяет ограничения.

### Этап C. Проверить после развёртывания

Эти проверки должны выполняться из фактической сети приложения, а не только
с ноутбука администратора. Это план приёмки, сейчас проверки не запускались.

- [ ] Все нужные компоненты проходят readiness/liveness.
- [ ] Подключения PostgreSQL работают с выданными ролями без лишних прав.
- [ ] S3: запись/HEAD/чтение/list/delete в разрешённом пространстве проходят.
- [ ] Рабочие Kafka-сообщения публикуются и читаются; проверен реальный путь
  сообщения и ответа, а не только TCP-connect или доступность tracing-топика.
- [ ] Проверено чтение настроек без кеша, AIFA работает одной репликой/worker.
- [ ] Модели доступны с нужными ID и поддерживают требуемые вызовы инструментов.
- [ ] AIFA-инструменты доступны в Agent Runtime; выполняется реальная операция.
- [ ] Workstation создаёт сессию, выполняет код, возвращает файл и очищает сессию.
- [ ] Два аккаунта видят отдельные чаты/файлы/результаты; ответ не попадает соседу.
- [ ] Проверены длительный ответ, отмена, ошибка зависимости и перезапуск компонента.
- [ ] Логи/трейсы доступны эксплуатационной команде.
- [ ] Определены процедура восстановления, ответственные и ограничения первого стенда.
